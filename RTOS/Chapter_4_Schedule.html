01
Core Concept

RTOS Fundamentals

EXPLANATION

Trước khi học Task Management, bạn cần hiểu vấn đề mà RTOS giải quyết. Một CPU chỉ có một bộ thanh ghi và một con trỏ lệnh (Program Counter) — nghĩa là tại một thời điểm, nó chỉ thực thi được đúng một dòng lệnh. Mọi cảm giác "chạy nhiều việc cùng lúc" đều là ảo giác được tạo ra bằng cách chuyển đổi rất nhanh giữa các công việc.

Bare-metal: một vòng lặp, mọi thứ tuần tự

Trong lập trình bare-metal cổ điển, toàn bộ chương trình thường là một hàm main() gọi tuần tự các hàm xử lý bên trong một vòng lặp while(1) lớn. Nếu một hàm xử lý cảm biến mất 40ms để chạy xong, thì trong 40ms đó, phần code xử lý giao tiếp mạng hay đèn LED đều phải chờ.

Bare-metal

main {
  init();
  while(1) {
    readSensor();   // 40ms
    updateControl(); // 5ms
    sendNetwork();  // 15ms
    blinkLED();     // 1ms
  }
}

Mọi việc phải đợi theo hàng — nếu sendNetwork() bị treo (chờ mạng), blinkLED() không bao giờ chạy được nữa.

Với RTOS

Mỗi công việc trở thành một task độc lập. Scheduler — một thành phần của kernel — đứng giữa CPU và các task, quyết định tại mỗi thời điểm task nào được chạy, dựa trên priority và trạng thái sẵn sàng của từng task.

Sensor Task Control Task Network Task LED Task

Network Task bị chờ mạng (Blocked) không còn chặn LED Task chạy — Scheduler đơn giản chuyển CPU sang task khác đang Ready.

Vì sao RTOS tồn tại?

Giả sử hệ thống của bạn cần: đọc cảm biến mỗi 20ms, xử lý điều khiển mỗi 10ms, và gửi log mỗi 500ms — với các mốc thời gian không được lệch quá nhiều (real-time). Không có RTOS, bạn phải tự tay chia nhỏ code, dùng cờ (flag) và kiểm tra thời gian thủ công ở khắp nơi, code nhanh chóng rối rắm khi số lượng công việc tăng. Có RTOS, mỗi việc là một task riêng biệt, scheduler xử lý toàn bộ việc chia thời gian CPU dựa trên priority và tick, giúp code từng task đơn giản như thể nó "sở hữu" CPU một mình.

Liên hệ CPU / RAM / Scheduler

Một CPU lõi đơn (single-core) — như trên nhiều nền tảng embedded — tại một thời điểm chỉ thực thi một dòng lệnh của một task. RAM lưu trữ code, dữ liệu, và quan trọng nhất với chương này: stack riêng của từng task cùng Task Control Block (TCB) — cấu trúc dữ liệu kernel dùng để theo dõi từng task. Scheduler là đoạn code kernel chạy định kỳ (thường tại tick interrupt) hoặc khi có sự kiện, để quyết định lại xem task nào nên chiếm CPU tiếp theo.

INFERENCE

Nội dung so sánh bare-metal vs RTOS ở trên là kiến thức nền RTOS phổ quát, được trình bày để chuẩn bị bối cảnh trước khi vào Chapter 4 — bản thân đoạn này không phải trích dẫn trực tiếp từ tài liệu Chapter 4.

Tự kiểm tra nhanh

❓ Nếu CPU chỉ chạy được một lệnh tại một thời điểm, "đa nhiệm" (multitasking) thực chất là gì? — Gợi ý: xem lại phần "ảo giác" ở đầu bài, rồi qua Lesson 04 để thấy scheduler tạo ảo giác đó bằng cách nào.

What Is a Task?

SOURCE

Theo tài liệu Chapter 4 (mục "Tasks"), một task trong FreeRTOS được viết như một hàm C thông thường, nhưng với một ràng buộc quan trọng: nó phải chứa một vòng lặp vô hạn và không bao giờ được return. Nếu logic bên trong thực sự cần kết thúc, task phải tự xóa chính nó bằng vTaskDelete() (xem Lesson 14) thay vì thoát khỏi hàm bằng return.

C
void vTaskFunction( void *pvParameters )
{
    for( ;; )
    {
        // … thực hiện công việc của task …
    }
    // KHÔNG BAO GIỜ chạy tới đây — không được return
}

Phân biệt: Task Function vs Task (Instance)

Đây là một trong những nhầm lẫn phổ biến nhất của người mới học. Task Function là đoạn code C bạn viết — một bản thiết kế. Task (instance) là một thực thể cụ thể mà kernel tạo ra khi bạn gọi xTaskCreate(), với TCB và stack riêng.

Ví dụ đời thường: hãy nghĩ vTaskFunction() giống như một bản vẽ thiết kế nhà (blueprint). Từ MỘT bản vẽ, bạn có thể xây ra ba căn nhà cụ thể: SensorTaskA, SensorTaskB, SensorTaskC — mỗi căn nhà là một task instance độc lập, có địa chỉ (TCB) và nội thất (stack) riêng, dù dùng chung một bản vẽ.

Ví dụ C — cùng một hàm, ba task instance

C
xTaskCreate( vTaskFunction, "SensorA", 1000, (void*)"Sensor A", 1, NULL );
xTaskCreate( vTaskFunction, "SensorB", 1000, (void*)"Sensor B", 1, NULL );
xTaskCreate( vTaskFunction, "SensorC", 1000, (void*)"Sensor C", 1, NULL );

Ba task này chạy cùng một đoạn code (vTaskFunction), nhưng là ba thực thể độc lập trong scheduler — mỗi cái có tham số pvParameters, TCB và stack riêng, và có thể ở ba trạng thái khác nhau tại cùng một thời điểm.

Nhầm lẫnNghĩ "một hàm = một task"
Chính xácMột hàm có thể sinh ra nhiều task instance độc lập

Task Function

SOURCE

Prototype bắt buộc của mọi task function:

void vTaskFunction( void *pvParameters );

Tham số pvParameters là một con trỏ void* tự do — kernel không quan tâm nó trỏ tới gì, chỉ truyền nguyên vẹn giá trị bạn đưa vào xTaskCreate() tới đúng instance đó khi task chạy lần đầu. Đây là cách phổ biến để một hàm chung phân biệt "tôi là bản instance nào".

Cạm bẫy: biến static bên trong task function

Một biến khai báo bình thường bên trong task function (ví dụ long lStackVariable;) nằm trên stack riêng của từng instance — hoàn toàn độc lập. Nhưng nếu bạn khai báo static long lSharedVariable; bên trong cùng hàm đó, biến này chỉ được linker cấp phát một lần duy nhất và bị mọi instance dùng chung — kể cả khi ba task chạy từ cùng một vTaskFunction() nhưng là ba TCB khác nhau.

void vTaskFunction( void *pvParameters )
{
    long lStackVariable;        // riêng cho mỗi instance (trên stack)
    static long lSharedVariable; // DÙNG CHUNG giữa mọi instance!
    for( ;; ) { /* ... */ }
}
INFERENCE

Đây là hệ quả trực tiếp của ngữ nghĩa static trong C (được cấp phát tĩnh bởi linker, không phải theo từng lời gọi hàm) áp dụng vào bối cảnh multitasking — tài liệu Chapter 4 nêu rõ cảnh báo này ở phần Listing tương ứng, nhưng phần diễn giải "vì sao nguy hiểm khi nhiều task chạy song song" là suy luận mở rộng của khoá học.

Ba loại ví dụ minh hoạ

Đời thực

Giống ba nhân viên dùng chung một cuốn sổ tay hướng dẫn công việc (code), nhưng nếu họ viết ghi chú lên MỘT tấm bảng chung (biến static) thay vì sổ tay riêng của mình (biến local/stack), ghi chú của người này sẽ xoá mất ghi chú người kia.

C code

Xem ví dụ code phía trên: lStackVariable an toàn, lSharedVariable nguy hiểm.

CPU Timeline

Task A ghi lSharedVariable = 1 → bị context-switch → Task B ghi lSharedVariable = 99 → context-switch về Task A → Task A đọc lại thấy 99, không phải 1 như nó vừa ghi.

Task States

SOURCE

Tài liệu mô tả một task tại bất kỳ thời điểm nào cũng ở một trong các trạng thái sau. Một task đang thực thi trên CPU gọi là Running; mọi task không phải Running được gộp vào một siêu-trạng thái gọi là Not Running — Not Running không phải "task đã dừng", mà chỉ đơn giản là "hiện không chiếm CPU". Bên trong Not Running, tài liệu chia tiếp thành Ready, Blocked và Suspended.

Bảng đầy đủ 8 chuyển đổi trạng thái

Từ → ĐếnNguyên nhân
Ready → RunningScheduler chọn task priority cao nhất trong Ready
Running → ReadyBị preempt bởi task priority cao hơn, hoặc hết time slice (cùng priority)
Running → BlockedvTaskDelay(), chờ queue/semaphore, hoặc API blocking khác
Blocked → ReadySự kiện đến hoặc hết thời gian timeout
Running → SuspendedvTaskSuspend()
Ready → SuspendedvTaskSuspend() gọi lên một task đang Ready (không nhất thiết phải Running)
Blocked → SuspendedvTaskSuspend() gọi lên một task đang chờ (Blocked)
Suspended → ReadyvTaskResume() / xTaskResumeFromISR()

Ví dụ cụ thể (Example 4.9 trong tài liệu): hai task chuyển đổi Ready ⇄ Running qua lại — nếu một trong hai gọi vTaskDelay(), nó rời khỏi chu trình đó để vào Blocked, trong khi task còn lại chiếm Running liên tục cho tới khi có tranh chấp priority khác; Suspended hoàn toàn tách biệt, không tự động quay lại nếu không có lệnh resume rõ ràng.

Vì sao kernel cần TCB?

CPU chỉ có một bộ thanh ghi vật lý. Khi scheduler chuyển từ task A sang task B, nó phải cất giữ toàn bộ ngữ cảnh (register, stack pointer...) của A vào đâu đó để khôi phục chính xác sau này — TCB cùng vùng stack riêng chính là "hồ sơ lưu trữ" đó cho từng task.

INFERENCE

Danh sách field TCB ở trên là các trường khái niệm mà tài liệu và kiến trúc TCB/Stack ngụ ý (Chapter 3-4) — không khẳng định đây là toàn bộ struct nội bộ thật của kernel, vốn có thể có thêm nhiều field khác không được tài liệu mô tả đầy đủ.

Luồng tạo task

Chế độ Dynamic: bộ nhớ TCB và Stack được lấy từ heap FreeRTOS tại thời điểm gọi hàm — tiện lợi nhưng phụ thuộc heap còn đủ chỗ hay không.

Ví dụ code — Dynamic vs Static

SOURCE 
xTaskCreate(
    vTaskCode,
    "NAME",
    STACK_SIZE,
    NULL,
    tskIDLE_PRIORITY,
    &xHandle
);
SOURCE 
static StaticTask_t xTaskBuffer;
static StackType_t xStack[STACK_SIZE];

xTaskCreateStatic(
    vTaskCode, "NAME", STACK_SIZE,
    NULL, tskIDLE_PRIORITY,
    xStack, &xTaskBuffer
);
EXPLANATION

Điểm quan trọng dễ bị hiểu lầm: xTaskCreate() chỉ đưa task vào Ready, chờ scheduler chọn — nó KHÔNG chạy ngay lập tức, kể cả khi gọi từ bên trong main() trước khi vTaskStartScheduler() được gọi.

Task Parameters

xTaskCreate() nhận các tham số: task function, tên (debug only), stack depth, pvParameters, priority, và con trỏ ra TaskHandle_t. Tham số dễ gây lỗi nhất là stack depth.

SOURCE

Cạm bẫy: usStackDepth tính theo WORD, không phải BYTE

usStackDepth không phải số byte bạn muốn cấp cho stack — nó là số word. Trên CPU 32-bit, 1 word = 4 byte.

usStackDepth truyền vàoBộ nhớ thực tế cấp (32-bit)
10004000 byte
128512 byte
EXPLANATION

Nếu bạn nhầm tưởng usStackDepth=1000 là 1000 byte và đặt số quá nhỏ để "tiết kiệm RAM", stack thực tế cấp có thể lớn hơn dự tính 4 lần trên vi điều khiển 32-bit — hoặc ngược lại, nếu bạn "quy đổi ngược" sai và đặt số quá nhỏ, stack sẽ không đủ và dẫn tới stack overflow âm thầm (Lesson 23 — Debugging).

configSTACK_DEPTH_TYPE

SOURCE

Loại dữ liệu của tham số stack depth có thể cấu hình qua configSTACK_DEPTH_TYPE (mặc định thường là uint16_t). Nếu hệ thống của bạn cần stack lớn hơn giới hạn của uint16_t cho phép, bạn cần định nghĩa lại macro này thành một kiểu rộng hơn (ví dụ uint32_t), nếu không giá trị truyền vào có thể bị tràn (overflow) âm thầm.

pvParameters — liên hệ ngược Lesson 02

Đây chính là cơ chế giúp nhiều task instance dùng chung một task function nhưng vẫn hành xử khác nhau — mỗi lần gọi xTaskCreate() bạn truyền một giá trị pvParameters khác nhau (ví dụ tên cảm biến, số ID, con trỏ cấu hình...).

Task Priority

SOURCE

Quy tắc cốt lõi: mỗi task được gán một số nguyên priority, từ 0 (thấp nhất) đến configMAX_PRIORITIES − 1 (cao nhất). Tại bất kỳ thời điểm nào có nhiều hơn một task đang Ready, scheduler luôn chọn task Ready có priority cao nhất để chạy.

Ví dụ chi tiết: hai task liên tục, khác priority

xTaskCreate( vTaskFunction, "Task 1", 1000, "Task 1 ", 1, NULL );
xTaskCreate( vTaskFunction, "Task 2", 1000, "Task 2 ", 2, NULL );

Task 2 (priority 2) chiếm CPU liên tục vì nó không bao giờ gọi bất kỳ API blocking nào — Task 1 (priority 1) chỉ ở Ready, không bao giờ được scheduler chọn, vì luôn có một task priority cao hơn đang sẵn sàng.

EXPLANATION

Đây KHÔNG phải lỗi của scheduler — đây chính xác là hành vi được thiết kế. Priority chỉ quyết định "ai thắng khi có tranh chấp giữa các task Ready"; nó không tự động đảm bảo công bằng thời gian CPU. Muốn Task 1 có cơ hội chạy, Task 2 phải chủ động nhường CPU (ví dụ gọi vTaskDelay() — xem Lesson 09).

Tự kiểm tra

❓ Task A priority=1 đang Blocked, Task B priority=3 đang Ready. Ai chạy? — Đáp: Task B — vì Task A không Ready nên không tham gia tranh chấp.

Tick & Scheduler

SOURCE

Tick là một ngắt phần cứng định kỳ (periodic hardware timer interrupt). Tần số của nó được cấu hình qua configTICK_RATE_HZ — ví dụ 1000 nghĩa là 1 tick mỗi 1ms. Mỗi lần tick xảy ra, kernel xem xét lại việc lập lịch: kiểm tra xem có task nào đang Blocked vừa hết hạn timeout hay không, và (khi bật time slicing) quyết định có nên đổi task cùng priority hay không.

TickType_t xTaskGetTickCount( void );
TickType_t pdMS_TO_TICKS( TickType_t xTimeInMs );

pdMS_TO_TICKS() luôn được dùng để chuyển mili-giây sang số tick tương ứng với configTICK_RATE_HZ hiện tại — tài liệu khuyến nghị luôn dùng macro này thay vì tự tính tay, để code không bị hỏng nếu sau này đổi giá trị configTICK_RATE_HZ.

Scheduler quyết định điều gì tại mỗi lần được gọi?

  1. Task nào đang Ready?
  2. Trong số đó, ai priority cao nhất?
  3. Nếu có nhiều task cùng priority cao nhất, có time slicing không? (Lesson 18)

Sơ đồ quyết định đầy đủ của scheduler — bao gồm cả trường hợp round-robin cùng priority — được trình bày chi tiết ở Lesson 20 (Complete Scheduler Flow).

EXPLANATION

Tick không phải là thứ duy nhất kích hoạt scheduler — một ISR gọi API đánh thức task, hoặc chính task gọi API blocking/yield, cũng khiến scheduler được đánh giá lại ngay lập tức (xem Lesson 17 — Preemption).

vTaskDelay()

SOURCE

vTaskDelay() chuyển task gọi nó từ Running sang Blocked trong một số tick chỉ định, giải phóng CPU cho task khác thay vì giữ CPU bận (polling).

vTaskDelay()SOURCE
Purpose
Đưa task hiện tại vào Blocked trong khoảng thời gian tương đối, tính từ lúc gọi.
Prototype
void vTaskDelay( TickType_t xTicksToDelay );
Parameters
xTicksToDelay — số tick cần chờ (dùng pdMS_TO_TICKS() để đổi từ ms).
Return Value
Không có (void).
State Transition
Running → Blocked → (hết hạn) → Ready
Important Note
Thời gian delay tính tương đối từ lúc gọi — nếu thân task tốn thời gian thay đổi mỗi vòng lặp, chu kỳ tổng sẽ trôi dần (drift). Xem Lesson 10 để so sánh với vTaskDelayUntil().
Ví dụ đời thường: giống việc bạn tự nói "việc này cần vải khô, tôi cất sang bên, quay lại sau 10 phút" rồi chủ động rời bàn làm việc — thay vì đứng đó chờ vô ích.

vTaskDelayUntil()

SOURCE

Vấn đề của vTaskDelay(): nếu thân task (đọc cảm biến, in log...) tốn thời gian thực thi thay đổi mỗi vòng, vì delay luôn tính từ lúc gọi, chu kỳ tổng sẽ trôi dần thay vì cố định. vTaskDelayUntil() giải quyết bằng cách tính theo mốc tuyệt đối.

vTaskDelayUntil()SOURCE
Prototype
void vTaskDelayUntil( TickType_t *pxPreviousWakeTime, TickType_t xTimeIncrement );
Parameters
pxPreviousWakeTime — con trỏ biến lưu mốc thức dậy trước đó (được kernel tự cập nhật); xTimeIncrement — chu kỳ mong muốn tính bằng tick.
State Transition
Giống vTaskDelay(): Running → Blocked → Ready, nhưng mốc thức dậy kế tiếp = mốc trước + chu kỳ cố định, không phụ thuộc thời điểm gọi.
Important Note
Vẫn không đảm bảo chạy ngay đúng mốc đó nếu một task priority cao hơn đang chiếm CPU — chỉ đảm bảo mốc thức dậy (Ready) không bị trôi.

Core Concept

Blocking vs Polling

SOURCE

Tài liệu trình bày hai cách một task chờ dữ liệu sẵn sàng: polling (vòng lặp kiểm tra cờ liên tục) và blocking (gọi API blocking như vTaskDelay() hoặc chờ queue/semaphore).

Polling

for( ulCount = 0; ulCount < 5; ulCount++ )
{
    while( !ucDataReady ) { /* bận chờ */ }
    processData();
}

Blocking

vTaskDelay( pdMS_TO_TICKS(100) );
processData();
EXPLANATION

Khi một task polling, nó vẫn ở trạng thái Running — CPU bị coi là "bận" dù không làm việc có ích. Blocking chủ động nhường CPU bằng cách chuyển sang Blocked, cho phép task khác — kể cả priority thấp hơn — có cơ hội chạy.

Idle Task

SOURCE

Tài liệu nêu rõ luôn phải có ít nhất một task sẵn sàng chạy tại mọi thời điểm — nếu tất cả task ứng dụng đều Blocked hoặc Suspended, CPU vẫn cần thực thi cái gì đó. Kernel tự động tạo Idle Task ở priority 0 (thấp nhất có thể) để lấp đầy khoảng trống đó.

Idle Task Hook

void vApplicationIdleHook( void )
{
    // được gọi tự động mỗi vòng lặp Idle Task
    // (yêu cầu configUSE_IDLE_HOOK == 1)
}

Ba công dụng phổ biến: đưa CPU vào chế độ tiết kiệm điện (low-power), đo mức tải nhàn rỗi qua bộ đếm, hoặc thực hiện việc dọn dẹp nền nhẹ nhàng.

INFERENCE

Idle Task hook có thể được gọi rất nhiều lần giữa hai lần task ứng dụng chạy (hàng triệu lần nếu hệ thống rảnh lâu) — con số cụ thể phụ thuộc tốc độ CPU thực tế, không phải hằng số cố định trong tài liệu.

2 quy tắc bắt buộc khi viết Idle Hook

SaiGọi vTaskDelay() hoặc bất kỳ API blocking nào bên trong hook
ĐúngHook phải luôn trả về nhanh, không bao giờ block
SaiGọi vTaskDelete() bên trong hook
ĐúngKhông xoá task từ trong chính vòng lặp dọn dẹp của Idle Task

Ai dọn dẹp bộ nhớ sau khi xoá?

Đây là điểm dễ hiểu lầm nhất: vTaskDelete() không giải phóng heap ngay lập tức nếu task được tạo bằng cấp phát động (xTaskCreate()). Theo tài liệu, việc giải phóng bộ nhớ kernel đã cấp cho TCB và Stack là trách nhiệm của Idle Task, thực hiện ở lượt chạy kế tiếp của nó.

Core Concept

Thread Local Storage & Reentrancy

SOURCE

Một hàm reentrant có thể được nhiều task gọi "cùng lúc" (xen kẽ do context switch) mà không gây lỗi dữ liệu, vì nó không phụ thuộc trạng thái dùng chung nào ngoài stack/tham số riêng của lần gọi đó. Một hàm non-reentrant thường dùng biến static hoặc toàn cục dùng chung giữa mọi lần gọi.

Ví dụ kinh điển: errno

Nếu errno là một biến toàn cục dùng chung: Task A gọi strtol() bị lỗi, ghi errno, nhưng trước khi Task A kịp đọc lại errno, Task B cũng ghi đè giá trị khác — Task A đọc nhầm lỗi của Task B.

EXPLANATION

Giải pháp: mỗi task cần một bản sao errno riêng, lưu trong Thread Local Storage (TLS) của chính TCB task đó, thay vì một vùng nhớ toàn cục dùng chung.

Hai cơ chế TLS được tài liệu đề cập

  1. configUSE_C_RUNTIME_TLS_SUPPORT / configUSE_NEWLIB_REENTRANT / configUSE_PICOLIBC_TLS — tích hợp với C runtime (newlib, picolibc) để tự động cấp context reentrant riêng cho mỗi task.
  2. TLS pointer thủ công qua API kernel:
void vTaskSetThreadLocalStoragePointer( TaskHandle_t xTaskToSet, BaseType_t xIndex, void *pvValue );
void *pvTaskGetThreadLocalStoragePointer( TaskHandle_t xTaskToQuery, BaseType_t xIndex );

Mỗi task có một mảng con trỏ void* tự do trong TCB của nó — bạn tự quyết định lưu gì vào đó (bộ đếm riêng, con trỏ cấu hình riêng...).

ReentrantNon-reentrant
Chỉ dùng biến local/stack, hoặc TLS riêng từng taskDùng biến static/global dùng chung giữa mọi task

Preemption

SOURCE

Preemptive scheduling nghĩa là: bất cứ khi nào một task priority cao hơn chuyển sang Ready, scheduler ngay lập tức tước CPU khỏi task priority thấp hơn đang Running, dù task đó chưa hoàn thành công việc.

EXPLANATION

Từ khoá quan trọng: "ngay lập tức". Preemption có thể xảy ra tại bất kỳ thời điểm nào — không chỉ tại tick interrupt. Một ISR gọi API đánh thức một task priority cao (ví dụ giải phóng semaphore) có thể kích hoạt preemption ngay khi ISR kết thúc, không cần chờ tick kế tiếp.

Vì scheduler đánh giá lại ngay khi có thay đổi, vTaskPrioritySet() được gọi để nâng priority một task đang Ready lên cao hơn task đang Running cũng khiến preemption xảy ra ngay lập tức (xem lại Lesson 13).

18
Core Concept · Flagship Diagram

Time Slicing

SOURCE

Time Slicing chỉ có ý nghĩa khi từ hai task cùng priority trở lên đang Ready đồng thời. Khi bật (configUSE_TIME_SLICING=1), mỗi tick scheduler sẽ luân phiên (round-robin) giữa các task đó, thay vì để một task chiếm giữ liên tục.

SOURCE

Tài liệu lưu ý: round-robin không đảm bảo chia đều tuyệt đối 50/50 nếu số lượng tick giữa các sự kiện khác không đồng đều — nó chỉ đảm bảo mỗi task cùng priority lần lượt được cấp một "lượt" CPU.

configIDLE_SHOULD_YIELD: khi bật, nếu có một task ứng dụng khác cũng ở priority 0 (Idle) đang Ready, Idle Task sẽ nhường lượt của nó sớm hơn thay vì dùng hết time slice — tránh Idle Task "ăn hết" một tick trọn vẹn của một task ứng dụng cùng priority thấp nhất.

Core Concept · Flagship Diagram

Cooperative Scheduling

SOURCE

Khi configUSE_PREEMPTION=0, kernel không tự động tước CPU khỏi task đang Running, bất kể có task priority cao hơn chuyển sang Ready hay không. Task đang Running phải chủ động nhường CPU bằng cách gọi taskYIELD(), hoặc tự block (vTaskDelay, chờ queue...).

Đánh đổi

Với preemptive, nếu Task 1 đang thao tác một cấu trúc dữ liệu dùng chung và bị ngắt giữa chừng bởi task priority cao hơn, dữ liệu có thể ở trạng thái dở dang nếu không có cơ chế bảo vệ (mutex/critical section). Với cooperative, bạn tự kiểm soát chính xác thời điểm nhường CPU nên tránh được kiểu lỗi đó — nhưng đổi lại, đáp ứng thời gian thực (real-time responsiveness) kém hơn vì một task có thể giữ CPU rất lâu nếu quên gọi taskYIELD().

SaiQuên gọi taskYIELD() → toàn hệ thống treo, các task khác không bao giờ chạy
ĐúngLuôn đảm bảo mọi vòng lặp trong task cooperative có điểm nhường CPU rõ ràng

Cheat Sheet

Task Lifecycle

Created → Ready → Running → (Blocked / Suspended) → Ready → ...

Priority

Priority cao hơn → luôn thắng khi cùng đang Ready. Không đảm bảo tổng thời gian CPU nhiều hơn.

Delay

vTaskDelay() → Blocked → Timeout → Ready. vTaskDelayUntil() giữ mốc tuyệt đối, tránh trôi.

Preemption

Task priority cao hơn Ready → Switch ngay lập tức, bất kỳ thời điểm nào.

Time Slicing

Cùng priority + nhiều task Ready + time slicing bật → CPU chia đều theo tick.

Cooperative

Task phải chủ động yield/block — OS không tự tước CPU.

Idle Task

Priority 0, luôn tồn tại, dọn heap sau vTaskDelete().

API nhanh

xTaskCreate · vTaskDelay · vTaskDelayUntil · vTaskPrioritySet · vTaskDelete · taskYIELD

Top 20 Điều Cần Nhớ

  1. Task function phải có vòng lặp vô hạn, không được return.
  2. Stack depth tính theo word, không phải byte.
  3. xTaskCreate() chỉ đưa vào Ready, không chạy ngay.
  4. Chỉ 1 task Running tại 1 thời điểm trên mỗi lõi CPU.
  5. Ready ≠ Running.
  6. Blocked ≠ Suspended.
  7. vTaskDelay() giải phóng CPU, không giữ CPU bận.
  8. vTaskDelayUntil() tránh trôi chu kỳ.
  9. Priority cao chỉ thắng khi đang Ready.
  10. Priority cao không đồng nghĩa tổng CPU nhiều hơn.
  11. Idle Task luôn tồn tại, priority thấp nhất.
  12. Idle Task dọn bộ nhớ sau vTaskDelete().
  13. Không gọi API blocking trong Idle Hook.
  14. Time slicing chỉ áp dụng khi cùng priority.
  15. Không time slicing + cùng priority = một task có thể chiếm CPU liên tục.
  16. Preemption có thể xảy ra bất kỳ lúc nào, không chỉ tại tick.
  17. Cooperative scheduling cần task tự nhường CPU.
  18. TLS tránh xung đột biến toàn cục giữa các task.
  19. Config macro quyết định triết lý lập lịch toàn hệ thống.
  20. Đọc timeline luôn cần: trạng thái — ưu tiên — sự kiện kích hoạt.

Top 20 Lỗi Người Mới Học Thường Gặp

  1. Nhầm đơn vị stack (byte thay vì word).
  2. Tưởng xTaskCreate() chạy task ngay lập tức.
  3. Dùng polling thay vì blocking API.
  4. Nghĩ Ready = Running.
  5. Nghĩ Blocked = Suspended.
  6. Nghĩ vTaskDelay() giữ CPU bận.
  7. Nghĩ priority cao luôn được chạy dù đang Blocked.
  8. Nghĩ cùng priority luôn chia đều 50/50.
  9. Nhầm time slicing với preemption.
  10. Nghĩ tick là thứ duy nhất kích hoạt scheduler.
  11. Viết code nặng trong ISR như trong task thường.
  12. Nhầm taskYIELD() với vTaskDelay().
  13. Dùng vTaskDelay() khi cần chu kỳ chính xác.
  14. Gọi API blocking trong vApplicationIdleHook().
  15. Quên rằng vTaskDelete() không giải phóng heap ngay.
  16. Dùng biến static/global chia sẻ giữa nhiều task.
  17. Đặt stack quá nhỏ mà không kiểm tra overflow.
  18. Tin cooperative "an toàn hơn" mà quên phải tự yield.
  19. Không phân biệt task function với task instance.
  20. Kết luận hành vi hệ thống chỉ từ priority, bỏ qua trạng thái hiện tại.
