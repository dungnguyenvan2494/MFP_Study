01Overview

⚠ Nguồn thực tế khác với đề bài Đề bài yêu cầu ưu tiên Linux v5.4.x. Source tree thật sự có trên máy (Kernel/K-S800/Src) là Linux v5.10.241 (xem Makefile: VERSION=5 PATCHLEVEL=10 SUBLEVEL=241), ARM64, một BSP (board support package) có vendor patch riêng. Theo đúng nguyên tắc "dùng chính xác version được cung cấp", toàn bộ tài liệu này trace trên v5.10.241, không phải v5.4. Khác biệt so với v5.4 được ghi chú ở §39 Book vs Modern Kernel. Signal là gì?

Dưới góc nhìn kernel, một signal không phải là một lời gọi hàm bất đồng bộ được kernel "bắn" thẳng vào handler của process đích. Nó là một bit được bật trong một bitmask (sigset_t) cộng với (tuỳ loại) một struct sigqueue chứa siginfo nằm trong một hàng đợi (struct sigpending). Việc "chạy handler" chỉ xảy ra sau đó, tại một thời điểm kernel biết chắc process sắp quay lại userspace (EL0) — không phải tại thời điểm signal được tạo ra.

Generation ≠ Delivery — khái niệm trung tâm

GENERATION (tạo signal)

Chạy trong ngữ cảnh của sender (hoặc kernel report lỗi). Chỉ làm 3 việc:

  1. Alloc sigqueue, gắn vào pending hoặc shared_pending
  2. Bật bit trong pending->signal (sigset_t)
  3. Đặt TIF_SIGPENDING trên thread đích + đánh thức nó

Symbol: __send_signal() — kernel/signal.c:1077

DELIVERY (giao signal)

Chạy trong ngữ cảnh của chính process nhận, chỉ tại điểm nó sắp rời kernel để về EL0 (ret_to_user). Kernel kiểm TIF_SIGPENDING, gọi do_signal() → get_signal() chọn 1 signal → dựng signal frame trên user stack → chuyển pt_regs.pc sang handler.

Symbol: do_notify_resume() — arch/arm64/kernel/signal.c:917

Hệ quả quan trọng Giữa lúc generate và lúc deliver, process nhận có thể đã chạy hàng nghìn lệnh khác (nếu nó đang RUNNING trên CPU khác) hoặc đang ngủ (nếu nó bị đánh thức bởi chính signal đó). kill() trả về ngay sau bước generation — không đợi handler chạy xong, thậm chí không đợi handler bắt đầu chạy.

complete_signal() — chọn thread để đánh thức

kernel/signal.ccomplete_signal() · line 996
static void complete_signal(int sig, struct task_struct *p, enum pid_type type)
{
	struct signal_struct *signal = p->signal;
	struct task_struct *t;

	if (wants_signal(sig, p))
		t = p;                                   /* main thread ưu tiên nhận trước */
	else if ((type == PIDTYPE_PID) || thread_group_empty(p))
		return;                                   /* chỉ 1 thread, tự dequeue lúc chạy lại */
	else {
		t = signal->curr_target;                 /* round-robin qua các thread */
		while (!wants_signal(sig, t)) {
			t = next_thread(t);
			if (t == signal->curr_target)
				return;                      /* không ai nhận, để trong queue chờ */
		}
		signal->curr_target = t;
	}

	if (sig_fatal(p, sig) && !(signal->flags & SIGNAL_GROUP_EXIT) &&
	    !sigismember(&t->real_blocked, sig) && (sig == SIGKILL || !p->ptrace)) {
		if (!sig_kernel_coredump(sig)) {
			signal->flags = SIGNAL_GROUP_EXIT;   /* fatal → hạ cả nhóm thread ngay */
			signal->group_exit_code = sig;
			t = p;
			do {
				sigaddset(&t->pending.signal, SIGKILL);
				signal_wake_up(t, 1);
			} while_each_thread(p, t);
			return;
		}
	}
	signal_wake_up(t, sig == SIGKILL);      /* ← đặt TIF_SIGPENDING + wake_up_state() */
}

wants_signal() (line 979) trả false nếu thread đang bị block signal đó, đang PF_EXITING, hoặc đang stopped/traced — nghĩa là kernel chọn một thread cụ thể để "giao việc dequeue", chứ không chạy handler ngay tại đây.

Nhầm lẫn thường gặp complete_signal()/signal_wake_up() KHÔNG chạy signal handler. Chúng chỉ set cờ TIF_SIGPENDING và gọi wake_up_state() để đưa task về runnable. Handler chỉ chạy khi chính task đó tự trở về userspace và đi qua do_notify_resume() — xem §20.

Common Misconceptions

❌ WRONG: Signal generation = signal delivery
✅ CORRECT: Generation chỉ bật bit pending + đánh thức; delivery là bước riêng chạy trong ngữ cảnh process nhận, tại return-to-user.
Why: kill() trả về ngay sau __send_signal(), không chờ handler chạy. Xem §01, §04.
Source: kernel/signal.c:1077 (__send_signal), arch/arm64/kernel/signal.c:846 (do_signal)
❌ WRONG: Signal bị block nghĩa là signal biến mất
✅ CORRECT: Bit vẫn được set trong pending->signal; nó chỉ không được next_signal() chọn ra cho tới khi unblock.
Why: __send_signal() không hề kiểm tra t->blocked trước khi sigaddset().
Source: kernel/signal.c:1171, next_signal() line 214
❌ WRONG: kill() luôn thực thi handler ngay lập tức
✅ CORRECT: kill() chỉ đặt hàng (queue); handler chạy sau đó, trong ngữ cảnh của process nhận, khi nó tự quay lại userspace.
Why: Không có cơ chế nào trong kernel "nhảy" trực tiếp vào code của process khác từ ngữ cảnh sender.
Source: complete_signal()/signal_wake_up() chỉ gọi wake_up_state(), kernel/signal.c:1068
❌ WRONG: Signal handler chạy ở kernel mode (EL1)
✅ CORRECT: Handler chạy hoàn toàn ở EL0 (userspace); kernel chỉ sửa pt_regs rồi eret.
Why: setup_return() chỉ ghi giá trị vào struct pt_regs nằm trên kernel stack; CPU mới là thứ thật sự chuyển exception level khi eret chạy.
Source: arch/arm64/kernel/signal.c:729 (setup_return)
❌ WRONG: sigreturn chỉ đơn giản "return" như một lời gọi hàm bình thường
✅ CORRECT: rt_sigreturn là một syscall đặc biệt ghi đè TOÀN BỘ pt_regs (kể cả pc, sp, pstate) bằng dữ liệu đọc từ user stack — không có "return address" theo nghĩa thông thường.
Why: Handler được "gọi" bằng cách giả lập lời gọi hàm (sửa pc/sp/x0), nên nó không thể return kiểu bình thường về nơi đã gọi nó — vì kernel chưa từng thực sự CALL nó bằng instruction BL/BLR.
Source: arch/arm64/kernel/signal.c:486 (restore_sigframe), 530 (rt_sigreturn)
❌ WRONG: Mọi signal đều được xếp hàng (queue) riêng biệt từng instance
✅ CORRECT: Chỉ realtime signal (≥SIGRTMIN) mới queue nhiều instance; standard signal chỉ giữ 1 bit, các lần gửi trùng lặp trong lúc pending bị gộp lại.
Why: legacy_queue() chặn alloc thêm sigqueue cho standard signal đã pending.
Source: kernel/signal.c:1072 (legacy_queue), xem §33

42Self Test

Click vào câu hỏi để xem đáp án.

1. Signal generation khác signal delivery như thế nào?
Generation = chạy trong ngữ cảnh sender, chỉ set bit pending + đánh thức (__send_signal()). Delivery = chạy trong ngữ cảnh process nhận, tại return-to-user, build frame + nhảy vào handler (do_signal()). Hai việc có thể cách nhau tuỳ ý về thời gian.
2. Signal pending được lưu ở đâu?
2 nơi: task_struct.pending (riêng từng thread) và task_struct.signal->shared_pending (chung cả thread group). Mỗi nơi là 1 struct sigpending gồm bitmask signal + list sigqueue.
3. shared_pending khác pending như thế nào?
pending nhận signal thread-directed (tgkill, fault đồng bộ) — chỉ chính thread đó dequeue được. shared_pending nhận signal process-directed (kill, raise) — bất kỳ thread nào trong group thoả wants_signal() cũng có thể được chọn để dequeue. dequeue_signal() luôn thử pending riêng TRƯỚC.
4. signal_struct và sighand_struct khác nhau thế nào?
signal_struct: state + shared_pending, share theo CLONE_THREAD. sighand_struct: bảng action[64] + siglock, share theo CLONE_SIGHAND. Về lý thuyết tách rời được, thực tế luôn đi cùng nhau khi tạo pthread.
5. Signal mask nằm ở đâu?
task_struct.blocked (sigset_t) — riêng từng thread, không share. Còn có real_blocked và saved_sigmask dùng tạm cho sigsuspend()/syscall kiểu ppoll.
6. kill() gửi signal đến process hay thread?
Đến process (thread group) — dùng PIDTYPE_TGID, đẩy vào shared_pending, kernel tự chọn 1 thread phù hợp để nhận qua complete_signal().
7. tgkill() khác kill() thế nào?
tgkill(tgid,pid,sig) gửi tới ĐÚNG 1 thread cụ thể (PIDTYPE_PID, vào t->pending riêng), có kiểm tra tgid để tránh race PID bị tái sử dụng. kill() gửi tới cả process, kernel tự chọn thread.
8. Khi signal bị block chuyện gì xảy ra?
Bit vẫn được set trong pending->signal bình thường (generation không quan tâm blocked). Nó chỉ không được next_signal()/dequeue_signal() chọn ra cho tới khi bị unblock.
9. Khi signal được unblock chuyện gì xảy ra?
__set_current_blocked() gọi recalc_sigpending() ngay lập tức; nếu có signal vừa unblock đang pending, TIF_SIGPENDING được set lại → lần return-to-user tiếp theo sẽ deliver nó, không cần signal mới nào được gửi.
10. do_signal() được gọi khi nào?
Trong do_notify_resume(), khi thread_flags & (_TIF_SIGPENDING | _TIF_NOTIFY_SIGNAL), đúng vào điểm task chuẩn bị eret về EL0 (sau syscall hoặc sau interrupt/exception).
11. get_signal() làm gì?
Vòng lặp: dequeue 1 signal → nếu SIG_IGN thì bỏ qua lặp tiếp → nếu SIG_DFL thì thực thi default action (có thể không return, vd terminate) → nếu có handler thật thì điền ksig và trả true. Trả false nếu hàng đợi rỗng.
12. handle_signal() làm gì?
Gọi setup_rt_frame() để dựng signal frame trên user stack, rồi kiểm tra valid_user_regs(), cuối cùng gọi signal_setup_done() để cập nhật blocked mask (thêm sa_mask + chính signal đó trừ SA_NODEFER).
13. Signal frame nằm ở đâu?
Trên USER STACK (dưới regs->sp hiện tại), hoặc trên alternate signal stack nếu handler dùng SA_ONSTACK + sigaltstack(). Vị trí chính xác tính bởi get_sigframe().
14. ARM64 thay đổi register thế nào khi gọi signal handler?
setup_return(): pc=địa chỉ handler, sp=địa chỉ signal frame, x0=số hiệu signal, x1/x2=siginfo*/ucontext* (nếu SA_SIGINFO), x30=địa chỉ trampoline (vDSO hoặc sa_restorer) để khi handler ret sẽ tự rơi vào đường sigreturn.
15. sigreturn khôi phục gì?
Toàn bộ pt_regs (x0-x30, sp, pc, pstate — đã lọc qua valid_user_regs()), signal mask (uc_sigmask → set_current_blocked()), FPSIMD/SVE state, và alternate stack settings (restore_altstack()).
16. Tại sao signal có thể interrupt syscall?
Khi 1 syscall đang ngủ (TASK_INTERRUPTIBLE) chờ điều kiện (dữ liệu, lock, timeout), một signal khác đến sẽ đánh thức nó qua wake_up_state(). Vòng lặp chờ bên trong syscall kiểm signal_pending() và thoát sớm, trả một trong các mã -ERESTART* thay vì tiếp tục chờ.
17. -ERESTARTSYS nghĩa là gì?
Mã lỗi nội bộ kernel (giá trị 512, không phải errno POSIX thật) nghĩa là "syscall bị ngắt bởi signal, restart NẾU handler có SA_RESTART, ngược lại trả -EINTR cho user". Được xử lý và chuyển đổi hoàn toàn trong do_signal(), userspace không bao giờ thấy giá trị 512.
18. SA_RESTART ảnh hưởng thế nào?
Chỉ có hiệu lực khi mã lỗi là -ERESTARTSYS: nếu set, kernel lùi pc về lệnh svc để chạy lại syscall sau khi handler xong; nếu không set, kernel đổi thành -EINTR và tiếp tục sau svc. Với -ERESTARTNOINTR luôn restart bất kể cờ này; với -ERESTARTNOHAND, có handler chạy thì luôn EINTR bất kể cờ này.
19. Standard signal và realtime signal khác nhau thế nào?
Standard (<SIGRTMIN): chỉ giữ 1 bit pending, gửi trùng nhiều lần bị gộp (legacy_queue()). Realtime (SIGRTMIN..SIGRTMAX): mỗi lần gửi tạo 1 sigqueue riêng, xếp hàng FIFO, giữ nguyên siginfo từng lần, dequeue tuần tự.
20. Nếu read() đang sleep và signal đến, kernel thực hiện flow nào?
(1) __send_signal() đặt bit + complete_signal() đánh thức task; (2) vòng chờ trong sys_read() thấy signal_pending(), trả -ERESTARTSYS; (3) ret_to_user → do_notify_resume() → do_signal() lùi pc về lệnh svc; (4) get_signal() chọn signal, nếu có handler → handle_signal() dựng frame, huỷ quyết định restart nếu không có SA_RESTART; (5) handler chạy ở EL0; (6) rt_sigreturn khôi phục pt_regs với pc đã được đặt đúng (restart_addr hoặc continue_addr); (7) syscall chạy lại từ đầu HOẶC ứng dụng nhận -EINTR — xem sơ đồ đầy đủ ở §38.
