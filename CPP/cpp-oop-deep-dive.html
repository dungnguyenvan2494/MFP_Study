01

OOP Fundamentals

OOP giải quyết vấn đề gì, và tại sao C++ "không đơn giản chỉ là ngôn ngữ OOP".

Các paradigm lập trình

Procedural programming: chương trình là chuỗi lệnh thao túng dữ liệu toàn cục hoặc truyền qua tham số — dữ liệu và hàm tách rời hoàn toàn (C, Pascal). Structured programming thêm kỷ luật control-flow (if/while/for thay vì goto), giúp code dễ đọc hơn nhưng chưa giải quyết vấn đề tổ chức dữ liệu lớn.

Object-Oriented Programming gộp dữ liệu + hành vi thao túng dữ liệu đó vào một đơn vị (object), và giấu chi tiết implementation sau một interface ổn định. Generic programming (templates) tách hành vi khỏi kiểu dữ liệu cụ thể, sinh code tại compile-time. Data-oriented programming đi ngược lại OOP cổ điển: tổ chức theo layout dữ liệu tối ưu cache (SoA — struct of arrays) thay vì theo "đối tượng nghiệp vụ". Functional programming nhấn mạnh hàm thuần (pure function), immutability, composition thay vì state + mutation.

OOP giải quyết vấn đề gì?

Khi hệ thống lớn dần, "dữ liệu nằm ở đâu, ai được sửa nó, sửa thế nào cho an toàn" trở thành vấn đề chính — không phải thuật toán. OOP xuất hiện (Simula, Smalltalk, rồi C++ những năm 1980) để: (1) nhóm state với các thao tác hợp lệ trên state đó, giữ invariant; (2) cho phép thay thế implementation mà không phá vỡ code gọi nó (abstraction/interface); (3) cho phép viết code dùng chung cho nhiều kiểu dữ liệu khác nhau miễn chúng tuân theo cùng interface (polymorphism); (4) mô hình hoá quan hệ "là một" (is-a) giữa các khái niệm nghiệp vụ (inheritance).

Ưu điểm / nhược điểm

  • Ưu điểm: đóng gói giảm coupling; polymorphism cho phép mở rộng không sửa code cũ (Open/Closed); mô hình hoá domain trực quan; dễ chia module theo interface.
  • Nhược điểm: virtual call có chi phí indirection (khó inline, ảnh hưởng branch predictor); deep hierarchy dễ trở thành "God Object" hoặc fragile base class; lạm dụng inheritance tạo coupling ẩn giữa base/derived; object header (vptr) tốn thêm bộ nhớ mỗi object.

Khi nào OOP không phù hợp?

Khi bài toán là biến đổi dữ liệu hàng loạt hiệu năng cao (game engine ECS, xử lý tín hiệu, HFT) — lúc đó data-oriented design (SoA, cache-friendly, không virtual dispatch) thắng rõ rệt. Khi logic là thuần hàm số học không có state phức tạp — generic/functional style gọn hơn. Khi hệ thống nhỏ, một struct + free function đã đủ — OOP hoá sẽ chỉ thêm boilerplate.

Core concept C++ không phải "ngôn ngữ OOP thuần". C++ là multi-paradigm language: bạn có thể viết procedural (C-style), OOP (class/virtual), generic (template), functional (lambda + <algorithm>), và data-oriented — cùng lúc, trong cùng một codebase, chọn công cụ theo bài toán chứ không ép mọi thứ thành class.

Interview: OOP giải quyết vấn đề gì mà procedural không giải quyết được?
Procedural không ràng buộc được ai được sửa dữ liệu và sửa như thế nào — invariant dễ vỡ khi codebase lớn. OOP gắn dữ liệu với hành vi hợp lệ trên nó (encapsulation) và cho phép thay thế implementation qua interface ổn định (abstraction + polymorphism) mà không phải sửa code gọi nó.
Interview: Vì sao nói C++ là "zero-overhead abstraction"?
Triết lý Bjarne Stroustrup: "what you don't use, you don't pay for" — nếu bạn không dùng virtual function, object không có vptr, không có chi phí indirection; nếu bạn không dùng exception, không trả chi phí runtime cho unwinding ở nhánh không throw (với model zero-cost exception hiện đại). So với Java (luôn có vtable + GC dù bạn cần hay không), C++ để lập trình viên tự trả chi phí cho đúng phần mình dùng.
02

Class & Object

Class là bản thiết kế (type); Object là instance sống trong bộ nhớ tại runtime.

Class

class và struct trong C++ hoàn toàn giống nhau về mặt layout và semantics — khác duy nhất một điều: access specifier mặc định. struct mặc định public, class mặc định private. Đây thuần tuý là default, không phải rule của compiler; bạn có thể viết struct với toàn bộ member private và nó tương đương 100% một class.

C++
class A {
public:
    int x;      // truy cập được từ mọi nơi
private:
    int y;      // chỉ A và friend của A truy cập được
protected:
    int z;      // A, friend, và class kế thừa A truy cập được
};

Compiler hiểu declaration này như thế nào?

Compiler không sinh code cho access specifier — public/private/protected chỉ là compile-time check, hoàn toàn biến mất sau khi compile xong (không tồn tại ở machine code, không có runtime enforcement). Compiler build một symbol table cho class: danh sách member variable (kèm offset), member function (kèm mangled name), static member, nested type. Với mỗi lần truy cập a.y, compiler kiểm tra ngữ cảnh gọi có nằm trong "phạm vi được phép" hay không (member function của A, hoặc friend) — nếu vi phạm, đây là compile error, không phải runtime error. Vì vậy reinterpret_cast/con trỏ thô hoàn toàn có thể "vượt rào" private ở machine level (undefined behavior về mặt ngôn ngữ, nhưng vẫn chạy được vì private không tồn tại lúc runtime).

Member variable, member function, static member

  • Member variable (non-static): mỗi object có bản sao riêng, nằm trong vùng nhớ của object đó.
  • Member function (non-static): chỉ tồn tại một bản duy nhất trong code segment; nhận thêm tham số ẩn this (xem chương 16).
  • Static member: thuộc về class, không thuộc về object nào — chỉ một bản duy nhất tồn tại (xem chương 16).
  • Nested class: class định nghĩa bên trong class khác, chủ yếu để scope hoá tên (namespace hoá), không tự động có quan hệ đặc biệt gì với object của outer class.
  • Friend: khai báo một hàm/class khác được quyền truy cập private/protected — phá vỡ encapsulation có kiểm soát (xem chương 16).
  • Type alias / member type (using value_type = T;): công cụ để generic code (template) truy vấn kiểu liên quan tới class, nền tảng cho STL iterator traits.

Object

Object là một vùng nhớ đã được cấp phát và có kiểu — nó là instance cụ thể tồn tại tại runtime, có địa chỉ, có lifetime, có state. Class chỉ là type — không tồn tại trong bộ nhớ runtime (ngoại trừ vtable/RTTI metadata mà compiler sinh ra, xem chương 13).

C++
A a;      // automatic object — sống trên stack, lifetime gắn với scope
A* p = new A;   // dynamic object — sống trên heap, lifetime thủ công (tới khi delete)
A& r = a;       // KHÔNG phải object mới — chỉ là một tên khác (alias) trỏ tới object 'a'

A a; tạo một object mới, gọi constructor ngay. A* p = new A; cấp phát vùng nhớ trên free store rồi gọi constructor tại đó, trả về địa chỉ — bạn chịu trách nhiệm gọi delete p; để chạy destructor + giải phóng bộ nhớ. A& r = a; không cấp phát gì cả — reference chỉ là một alias ở compile-time (thường compiler hiện thực reference bằng con trỏ ẩn phía dưới, nhưng về ngôn ngữ, reference không có "địa chỉ riêng" khác với object nó tham chiếu: &r == &a).

Subobject

Một object có thể chứa các subobject bên trong nó: base-class subobject (phần bộ nhớ dành cho base class khi kế thừa) và member subobject (mỗi member variable kiểu class cũng là một object con, có địa chỉ nằm trong object cha). Khái niệm này là nền tảng bắt buộc phải hiểu trước khi đọc chương Memory Layout và Inheritance — địa chỉ của một subobject không nhất thiết trùng địa chỉ object cha (xem "pointer adjustment" ở chương Multiple Inheritance).

Best practice Luôn phân biệt rõ 3 khái niệm khi debug: type (class, biết lúc compile-time), object (vùng nhớ cụ thể, biết lúc runtime), và value (nội dung bytes hiện tại của object đó). Rất nhiều bug (dangling reference, use-after-free, object slicing) xuất phát từ nhầm lẫn "tôi có một object" với "tôi có một reference/pointer còn hợp lệ tới object đó".
03

Object Memory Model

sizeof, alignment, padding, member ordering, empty base optimization — object thực sự trông như thế nào trong RAM.

Vì sao cần alignment?

CPU đọc/ghi bộ nhớ hiệu quả nhất khi dữ liệu nằm ở địa chỉ chia hết cho kích thước của nó (một int 4 byte nên nằm ở địa chỉ chia hết cho 4; một double 8 byte nên nằm ở địa chỉ chia hết cho 8). Trên một số kiến trúc, truy cập lệch alignment (misaligned access) gây fault cứng (SIGBUS) — trên x86 thì chỉ chậm hơn. Vì vậy compiler tự động chèn padding (byte đệm vô nghĩa) giữa các member để mọi member đều đúng alignment, và ở cuối struct để array of struct cũng giữ alignment cho phần tử tiếp theo.

Ví dụ layout thực tế

C++
class A {
    char   a;   // 1 byte
    int    b;   // 4 byte, cần alignment 4
    double c;   // 8 byte, cần alignment 8
};
// sizeof(A) trên hầu hết compiler 64-bit: 16 (không phải 1+4+8=13)
MEMORY LAYOUT (common implementation, GCC/Clang x86-64)
offset  0        1  2  3  4        8                 16
        +--------+--+--+--+--------+-----------------+
        |   a    |  pad  |    b    |        c        |
        +--------+--+--+--+--------+-----------------+
        1 byte   3 byte  4 byte     8 byte
        pad(a)   pad     pad(b)     (double alignment=8)

sizeof(A) = 16   alignof(A) = 8   (padding chiếm 3+... byte "chết")

Nếu bạn đổi thứ tự khai báo thành double c; int b; char a; (khai từ lớn xuống nhỏ), compiler chỉ cần 1 byte padding cuối cùng để tổng size chia hết cho alignof lớn nhất → sizeof giảm còn 16 vẫn (double 8 + int 4 + char 1 + pad 3 = 16 trong ví dụ cụ thể này, nhưng với struct nhiều field nhỏ, sắp xếp từ lớn tới nhỏ luôn tối ưu hoặc bằng cách sắp bất kỳ). Đây là kỹ thuật thực tế gọi là struct packing / member reordering để giảm memory footprint khi có hàng triệu object.

Core concept — Standard vs Implementation C++ Standard không quy định compiler phải sắp xếp member theo đúng thứ tự khai báo giữa các access-specifier section khác nhau (ví dụ nó không bắt buộc field public phải đứng trước field private trong bộ nhớ) — nhưng nó bắt buộc các member cùng một access-specifier section (giữa hai public:/private: liên tiếp) phải giữ đúng thứ tự khai báo tương đối với nhau. Việc chèn bao nhiêu padding, alignment cụ thể của từng kiểu — đó là ABI-specific (Itanium ABI với GCC/Clang, hoặc MSVC ABI).

Empty class & Empty Base Optimization (EBO)

Một class không có non-static data member (class Empty {};) vẫn có sizeof(Empty) == 1, không phải 0 — vì Standard yêu cầu hai object khác nhau phải có địa chỉ khác nhau (nếu size = 0, một array Empty arr[10] sẽ có tất cả phần tử trùng địa chỉ, vi phạm nguyên tắc identity của object). Nhưng khi một class rỗng được dùng làm base class (không phải member), Empty Base Optimization cho phép compiler không cấp thêm byte nào cho nó — vì base subobject không cần định danh độc lập như một object đứng riêng, miễn nó không trùng địa chỉ với subobject/member liền kề cùng kiểu.

C++
struct Empty {};
struct WithMember   { Empty e; int x; };   // sizeof thường = 8 (Empty chiếm 1 byte + pad)
struct WithEBO : Empty { int x; };          // sizeof thường = 4 (Empty base "miễn phí")

EBO là lý do std::unique_ptr<T, EmptyDeleter> có cùng kích thước với con trỏ thô khi deleter không có state — thư viện chuẩn lưu deleter như một base class (hoặc dùng [[no_unique_address]] từ C++20) thay vì member, để tận dụng EBO.

Address của object và của member

&a cho ra địa chỉ byte đầu tiên của object (đúng theo Standard với standard-layout type; với non-standard-layout — ví dụ có base class không rỗng — địa chỉ object không nhất thiết trùng địa chỉ base subobject đầu tiên, sẽ nói kỹ ở chương Multiple/Virtual Inheritance). &a.b là &a + offsetof(A, b) — offsetof chỉ được Standard đảm bảo hợp lệ với standard-layout type (không có virtual function, không có nhiều access-specifier khác nhau xen kẽ theo một số điều kiện, tất cả non-static member cùng access control...).

Interview: Vì sao sizeof(EmptyClass) là 1 chứ không phải 0?
Vì C++ yêu cầu mọi object độc lập phải có địa chỉ duy nhất (identity). Nếu size = 0, một mảng các object rỗng sẽ khiến tất cả phần tử "chồng" lên cùng một địa chỉ, vi phạm con trỏ số học (&arr[i] != &arr[i+1] phải luôn đúng).
Interview: Tại sao nên sắp xếp member từ kiểu lớn (alignment cao) tới kiểu nhỏ?
Để giảm padding chèn giữa các member — mỗi member chỉ cần padding tối thiểu do member liền kề trước nó gây ra thay vì padding lặp lại nhiều lần do xen kẽ kiểu lớn/nhỏ. Với struct có hàng triệu instance (ví dụ trong game engine hay embedded), việc này giảm đáng kể memory footprint và tăng cache locality.
04

Encapsulation & Abstraction

Giấu dữ liệu để giữ invariant (encapsulation) và giấu cách làm để chỉ lộ "cái gì" (abstraction) — hai khái niệm gần nhau nhưng không phải một.

Encapsulation — giữ invariant

Invariant là một điều kiện luôn phải đúng trong suốt vòng đời object (ví dụ: số dư tài khoản không bao giờ âm). Encapsulation nghĩa là chặn mọi đường sửa dữ liệu ngoại trừ qua các hàm mà chính class kiểm soát — nhờ đó lớp bảo đảm invariant luôn giữ đúng, bất kể ai gọi nó.

C++ — có encapsulation
class BankAccount {
public:
    void withdraw(double amount) {
        if (amount > balance_) throw std::runtime_error("insufficient funds");
        balance_ -= amount;                 // invariant: balance_ >= 0 luôn đúng
    }
    double balance() const { return balance_; }
private:
    double balance_ = 0.0;
};
C++ — không có encapsulation
struct BankAccount { double balance; };   // ai cũng có thể: acc.balance = -999999;

Khác biệt không nằm ở "tốc độ" hay "cú pháp" — nó nằm ở khả năng chứng minh tính đúng đắn của chương trình. Với class BankAccount ở trên, bạn chỉ cần audit các member function của nó để biết balance có thể ra sao; với struct trần, balance có thể bị sửa từ bất kỳ đâu trong toàn bộ codebase — invariant không thể đảm bảo cục bộ.

Const correctness như một phần của encapsulation

const mở rộng encapsulation sang chiều "khả năng thay đổi": hàm balance() const tự cam kết (và được compiler ép buộc) không sửa state — người gọi có thể tin tưởng gọi nó trên một object const BankAccount&. Getter/setter nếu chỉ trả về/set trực tiếp field mà không kiểm tra gì thì chỉ là "boilerplate hoá" quyền truy cập public, không thực sự tạo ra encapsulation về mặt invariant.

Abstraction — API boundary

Abstraction trả lời câu hỏi: người dùng class cần biết gì, không cần biết gì?

C++
class Device {
public:
    void start();   // Cần biết: gọi hàm này để khởi động thiết bị
private:
    void initClock();
    void configureRegisters();
    uint32_t reg_base_;
};

Người dùng Device cần biết: "gọi start() thì thiết bị chạy". Họ không cần biết: thứ tự init clock/register bên trong, địa chỉ thanh ghi cụ thể, hay start() có gọi thêm hàm private nào. Đây chính là interface vs implementation — interface là hợp đồng ổn định, implementation có thể đổi hoàn toàn (đổi chip, đổi thuật toán) mà không phá code gọi nó.

Phân biệt Encapsulation vs Abstraction Encapsulation là cơ chế (access specifier) — trả lời "ai được truy cập gì". Abstraction là thiết kế (interface design) — trả lời "người dùng cần thấy những gì để dùng đúng, và nên giấu gì để họ không phụ thuộc nhầm vào chi tiết implementation". Một class có thể có encapsulation tốt (mọi field private) nhưng abstraction tệ (interface public lộ quá nhiều chi tiết implementation, ví dụ trả về con trỏ nội bộ).

Liên hệ thực tế: PImpl & module boundary

Kỹ thuật PImpl (Pointer to Implementation) đẩy abstraction lên mức cực đoan: header chỉ khai báo interface + một con trỏ tới struct implementation ẩn hoàn toàn trong file .cpp — người dùng include header còn không nhìn thấy tên các private member, giúp giảm thời gian compile lại khi implementation đổi, và ổn định ABI giữa các version thư viện. Chi tiết đầy đủ ở chương 19.

C++
class A {
public:
    A(int x) : x_(x) {}     // parameterized, dùng member-initializer-list
private:
    int x_;
};

A a{10};   // brace-init (list-initialization), gọi A::A(int)

Compiler xử lý A a{10}; ra sao?

Compiler overload-resolve constructor phù hợp nhất với {10} (ở đây chỉ có một constructor nhận int nên khớp trực tiếp). Sau đó nó cấp phát vùng nhớ cho a trên stack (kích thước đã biết tại compile-time), rồi phát sinh lệnh gọi A::A(A* this, int x) — constructor về bản chất là một hàm thường nhận thêm this ẩn, không có "return value" theo nghĩa thông thường (nó khởi tạo vùng nhớ đã cấp sẵn, không trả về object mới). Member-initializer-list (: x_(x)) khác hoàn toàn gán trong constructor body — initializer list khởi tạo trực tiếp (direct-initialization) member ngay khi nó được tạo; nếu bạn gán trong body (x_ = x;), member đã được default-construct trước đó rồi mới bị gán đè — tốn thêm một lần khởi tạo thừa, và với const member hay reference member thì bắt buộc phải dùng initializer list (không thể gán sau khi đã tạo).

Lỗi thường gặp Member trong initializer list được khởi tạo theo thứ tự khai báo trong class, không phải thứ tự bạn viết trong initializer list. Viết A(int x) : y_(x_), x_(x) {} khi x_ khai báo sau y_ sẽ khiến y_ được khởi tạo từ x_ chưa được khởi tạo — undefined behavior, dù đọc code tưởng như "đúng thứ tự". GCC/Clang với -Wreorder sẽ cảnh báo lỗi này.

Default member initializer & explicit

C++
class Config {
    int retries_ = 3;        // default member initializer — dùng nếu constructor không set
    explicit Config(int r) : retries_(r) {}   // explicit chặn: Config c = 5;  (lỗi compile)
};
Config c1(5);       // OK — direct-init
// Config c2 = 5;   // lỗi vì explicit — chặn implicit conversion int -> Config

explicit tồn tại vì converting constructor một tham số rất dễ gây implicit conversion không mong muốn (ví dụ std::vector<int> v(10); so với vô tình truyền nhầm literal ở nơi cần vector) — nguyên tắc: constructor một tham số nên explicit trừ khi bạn cố ý muốn cho phép implicit conversion (như std::string s = "hello";).

Constructor Order — thứ tự khởi tạo chính xác

Thứ tự bắt buộc theo Standard 
1. Virtual base class     (theo thứ tự xuất hiện trong DAG kế thừa, chỉ một lần)
2. Direct base class      (theo thứ tự khai báo kế thừa, trái sang phải)
3. Non-static data member (theo thứ tự khai báo trong class, KHÔNG theo initializer-list)
4. Constructor body        (thân hàm constructor chạy sau cùng)
C++ — multilevel
struct Base   { Base()   { std::puts("Base");   } };
struct Mid    : Base    { Mid()    { std::puts("Mid");    } };
struct Member { Member() { std::puts("Member"); } };
struct Derived: Mid {
    Member m;
    Derived() { std::puts("Derived"); }
};
Derived d;
// Output: Base -> Mid -> Member -> Derived
DIAGRAM — thứ tự chạy constructor
new Derived()
   │
   ├─▶ Base::Base()      (base của Mid, chạy trước tiên)
   ├─▶ Mid::Mid()        (direct base của Derived)
   ├─▶ Member::Member()  (data member 'm', theo thứ tự khai báo)
   └─▶ Derived::Derived() body   (thân hàm chạy sau cùng)

Constructor Inheritance (using Base::Base;)

C++11+
struct Base { Base(int x) {} };
struct Derived : Base {
    using Base::Base;   // "kế thừa" constructor của Base — sinh Derived(int) tương đương
};
Derived d(5);   // hợp lệ nhờ using-declaration

Đây chỉ là cú pháp sinh thêm constructor forwarding tự động, không có nghĩa là Derived "dùng chung" constructor với Base ở mức object — Derived vẫn khởi tạo đầy đủ theo thứ tự chuẩn ở trên (member của Derived vẫn được default-init nếu không có initializer riêng).

Interview: Vì sao virtual base luôn được khởi tạo trước direct base, kể cả khi nó nằm "sâu" trong hierarchy?
Vì virtual base chỉ tồn tại đúng một bản duy nhất trong toàn bộ object dù nhiều class kế thừa nó (giải quyết diamond problem — xem chương 10). Nếu để mỗi lớp trung gian tự khởi tạo virtual base, nó sẽ bị khởi tạo lặp lại nhiều lần. Standard giải quyết bằng cách: chỉ constructor của most-derived class (object thực sự được tạo ra) mới chịu trách nhiệm gọi constructor của virtual base, và nó luôn chạy trước mọi direct base khác.

Destructor

Thứ tự huỷ (ngược hoàn toàn với constructor), và lý do virtual destructor gần như luôn bắt buộc khi có polymorphism.

Thứ tự destructor — ngược lại constructor

Thứ tự huỷ 
1. Constructor body kết thúc → chạy destructor body trước
2. Non-static data member    (thứ tự NGƯỢC khai báo)
3. Direct base class          (thứ tự NGƯỢC khai báo kế thừa)
4. Virtual base class          (huỷ sau cùng, chỉ một lần)

Dùng lại ví dụ ở chương 05: huỷ Derived d; sẽ in ra Derived -> Member -> Mid -> Base — đúng thứ tự ngược lại constructor. Nguyên tắc này đảm bảo: khi huỷ một phần, các phần phụ thuộc vào nó (được xây dựng sau) đã được dọn trước.

Virtual Destructor — vì sao gần như bắt buộc

C++ — KHÔNG có virtual destructor (nguy hiểm)
struct Base   { ~Base()   { std::puts("~Base");   } };   // non-virtual
struct Derived: Base { int* buf = new int[100]; ~Derived(){ delete[] buf; std::puts("~Derived"); } };

Base* p = new Derived;
delete p;   // UNDEFINED BEHAVIOR: chỉ gọi ~Base(), KHÔNG gọi ~Derived() -> rò rỉ 'buf'!
C++ — có virtual destructor (an toàn)
struct Base   { virtual ~Base() { std::puts("~Base"); } };
struct Derived: Base { int* buf = new int[100]; ~Derived() override { delete[] buf; std::puts("~Derived"); } };

Base* p = new Derived;
delete p;   // đúng: gọi ~Derived() trước (qua vtable), rồi tự động gọi ~Base()
// Output: ~Derived -> ~Base
Undefined Behavior delete một object qua con trỏ base không có virtual destructor khi object thực sự là kiểu derived là undefined behavior theo Standard ([expr.delete]). Trên thực tế (common implementation), compiler chỉ phát sinh lệnh gọi trực tiếp Base::~Base() (vì không có gì để tra vtable) — phần Derived::~Derived() (và mọi resource nó lẽ ra phải giải phóng) bị bỏ qua hoàn toàn → memory leak, hoặc tệ hơn nếu Derived override thêm hành vi giải phóng handle/lock.
Best practice Quy tắc kinh điển: nếu một class có ít nhất một virtual function, nó nên có virtual destructor (kể cả khi thân hàm rỗng: virtual ~Base() = default;). Ngược lại, nếu class không định dùng làm polymorphic base (không có virtual function nào, không định delete qua con trỏ base) — không cần virtual destructor, vì nó thêm vptr vào object (tốn 8 byte trên 64-bit) và một tầng indirection không cần thiết. Đây chính là runtime cost bạn "trả tiền" khi dùng polymorphism (xem chương 25).

Pure Virtual Destructor

C++
struct AbstractBase {
    virtual ~AbstractBase() = 0;   // pure virtual, nhưng VẪN PHẢI có định nghĩa!
};
AbstractBase::~AbstractBase() {}   // bắt buộc định nghĩa ở ngoài, vì derived luôn gọi nó

struct Derived : AbstractBase {};  // Derived giờ instantiate được (AbstractBase vẫn abstract)

Kỹ thuật này dùng để ép một class trở thành abstract (không thể new AbstractBase) mà không cần thêm pure virtual function nghiệp vụ nào — nhưng khác các pure virtual function khác, destructor luôn được gọi trong chuỗi huỷ đối tượng derived (base destructor luôn chạy), nên nếu không định nghĩa thân hàm, linker sẽ báo lỗi "undefined reference".

Destruction of members & bases — exception trong destructor

Nếu destructor của một member ném exception trong lúc một exception khác đang unwind (ví dụ constructor throw giữa chừng khiến các member đã khởi tạo bị huỷ), chương trình gọi std::terminate() ngay lập tức — đây là lý do destructor mặc định là noexcept kể từ C++11 (trừ khi bạn tự khai báo khác) và nguyên tắc bất di bất dịch: không bao giờ để exception thoát ra khỏi destructor.

Interview: Điều gì xảy ra khi Base* p = new Derived; delete p; mà ~Base() không virtual?
Undefined behavior theo Standard; trên thực tế, compiler chỉ sinh lệnh gọi trực tiếp Base::~Base() vì lời gọi được resolve tĩnh theo kiểu con trỏ (Base*), không tra vtable. Kết quả: phần override và các member riêng của Derived không được huỷ đúng cách — rò rỉ tài nguyên hoặc state không nhất quán.

Copy / Move Semantics & Rule of 0 / 3 / 5

Shallow vs deep copy, std::move thực sự làm gì, và khi nào bạn cần tự viết 5 hàm đặc biệt (hoặc không viết hàm nào cả).

Shallow copy vs Deep copy

Compiler tự sinh copy constructor mặc định thực hiện memberwise copy — copy từng byte/member một cách "nông" (shallow): nếu member là con trỏ, chỉ địa chỉ được copy, không copy dữ liệu nó trỏ tới.

C++ — Shallow copy (nguy hiểm)
class Buffer {
    char* data;
public:
    Buffer(size_t n) : data(new char[n]) {}
    ~Buffer() { delete[] data; }
    // KHÔNG tự viết copy constructor -> compiler sinh default (shallow copy)
};
Buffer a(10);
Buffer b = a;      // b.data == a.data (cùng trỏ một vùng nhớ!)
// khi a và b cùng bị huỷ -> delete[] cùng một con trỏ HAI LẦN -> double free (UB)
C++ — Deep copy (đúng)
class Buffer {
    char* data; size_t size_;
public:
    Buffer(size_t n) : data(new char[n]), size_(n) {}
    Buffer(const Buffer& other) : data(new char[other.size_]), size_(other.size_) {
        std::memcpy(data, other.data, size_);   // copy NỘI DUNG, cấp phát vùng nhớ riêng
    }
    Buffer& operator=(const Buffer& other) {
        if (this == &other) return *this;          // self-assignment check
        char* newData = new char[other.size_];      // copy-then-swap: an toàn cả khi new throw
        std::memcpy(newData, other.data, other.size_);
        delete[] data;
        data = newData; size_ = other.size_;
        return *this;
    }
    ~Buffer() { delete[] data; }
};
Self-assignment a = a; tưởng vô hại nhưng nếu copy-assignment không kiểm tra this == &other và giải phóng data trước khi copy nội dung nguồn, bạn sẽ delete chính vùng nhớ mình đang cần đọc để copy — dùng lại dữ liệu đã free (UB). Kỹ thuật copy-and-swap (cấp phát bản sao mới trước, swap, rồi để bản cũ tự huỷ) giải quyết vấn đề này tự nhiên mà không cần check tường minh.

Copy Elision

Từ C++17, một số trường hợp trả về object theo giá trị (return T{...}; hoặc T t = T(...);) được Standard bắt buộc bỏ qua copy/move constructor hoàn toàn (mandatory copy elision, không chỉ là optimization/RVO tuỳ compiler như trước C++17) — object được xây dựng trực tiếp tại nơi nó sẽ được dùng, không có bản sao trung gian nào cả, kể cả khi copy constructor có side-effect (ví dụ std::puts) thì side-effect đó cũng không xảy ra.

Move Semantics

Vấn đề move semantics giải quyết: khi trả về hoặc truyền một object tạm thời (rvalue) — dữ liệu nó chứa sắp bị huỷ ngay sau đó — copy sâu (deep copy) là lãng phí. Thay vì copy nội dung, ta có thể "cướp" (steal) con trỏ nội bộ của object nguồn, để lại nguồn ở trạng thái rỗng hợp lệ.

C++11
Buffer(Buffer&& other) noexcept : data(other.data), size_(other.size_) {
    other.data = nullptr;   // nguồn không còn sở hữu gì -> destructor của nó an toàn (delete nullptr no-op)
    other.size_ = 0;
}
Buffer& operator=(Buffer&& other) noexcept {
    if (this != &other) {
        delete[] data;               // giải phóng tài nguyên hiện tại
        data = other.data; size_ = other.size_;
        other.data = nullptr; other.size_ = 0;
    }
    return *this;
}

A b = std::move(a); — std::move không di chuyển gì cả, nó chỉ là một static_cast<A&&>(a), tức "ép kiểu" lvalue a thành rvalue reference để overload resolution chọn move constructor thay vì copy constructor. Việc "di chuyển" thực sự (steal con trỏ) là do bạn viết trong thân move constructor — compiler và runtime không tự làm điều đó, std::move chỉ là tín hiệu ("tôi cho phép cướp tài nguyên của biến này").

Moved-from state Sau A b = std::move(a);, a ở trạng thái "hợp lệ nhưng không xác định" (valid but unspecified state) — bạn được phép gán giá trị mới hoặc huỷ nó, nhưng không được giả định giá trị cũ còn nguyên. Đọc a sau khi move (ngoài gán mới/huỷ) là bug logic, dù thường không phải UB cứng ở mức ngôn ngữ (trừ khi move constructor bạn viết để lại state thực sự invalid).

noexcept trên move constructor cực kỳ quan trọng: std::vector khi realloc sẽ ưu tiên move phần tử cũ sang vùng nhớ mới chỉ khi move constructor là noexcept — nếu không, để đảm bảo strong exception guarantee (nếu giữa chừng lỗi thì vector cũ vẫn nguyên vẹn), nó buộc phải copy (chậm hơn) thay vì move.

Rule of 0 / 3 / 5

RuleÝ nghĩaKhi áp dụng
Rule of 0Không tự viết bất kỳ hàm nào trong 5 hàm đặc biệt (destructor, copy ctor, copy assign, move ctor, move assign)Class chỉ chứa member đã tự quản lý tài nguyên đúng (RAII: std::string, std::vector, std::unique_ptr...) — để compiler tự sinh, mọi thứ đúng "miễn phí"

C++ — vì sao class này VI PHẠM Rule of 3
class Buffer {
    char* data;
public:
    Buffer(size_t n) : data(new char[n]) {}
    ~Buffer() { delete[] data; }
    // THIẾU copy constructor & copy assignment!
    // compiler tự sinh bản shallow-copy -> double free khi 2 object cùng huỷ 'data'
};

Class này cần destructor (giải phóng data) → theo Rule of 3, nó phải tự viết cả copy constructor và copy assignment (deep copy), nếu không compiler-generated version sẽ shallow-copy con trỏ và gây double-free khi cả hai object bị huỷ. Nếu class không quản lý tài nguyên thô trực tiếp (dùng std::vector<char> thay char*), nó rơi về Rule of 0 — không cần viết gì cả, vì std::vector đã tự lo đủ 5 hàm đúng cách rồi.

Best practice Trong code hiện đại, Rule of 3/5 nên hiếm khi xuất hiện trực tiếp trong business logic — nó nên bị "chôn" vào một lớp RAII nhỏ, chuyên trách (như Buffer ở trên, hoặc dùng thẳng std::unique_ptr/std::vector), còn phần lớn class nghiệp vụ nên tuân theo Rule of 0. Nếu bạn thấy mình viết nhiều class business logic phải tự tay viết cả 5 hàm, đó thường là dấu hiệu thiết kế nên tách riêng resource-owner ra khỏi logic.
Interview: std::move(a) có thực sự "di chuyển" dữ liệu của a ngay lập tức không?
Không. std::move chỉ là một cast — nó biến a (lvalue) thành rvalue reference để trigger overload resolution chọn move constructor/move assignment thay vì bản copy. Việc "cướp" tài nguyên (con trỏ, handle) là do logic bạn viết bên trong move constructor quyết định; nếu class không có move constructor, std::move(a) vẫn fallback về copy bình thường.

IS-A vs HAS-A

IS-A — inheritance
class Animal { public: virtual void speak(); };
class Dog : public Animal { public: void speak() override; };
// "Dog LÀ MỘT Animal" -> Dog* có thể dùng ở bất kỳ đâu cần Animal*
HAS-A — composition
class Engine { public: void start(); };
class Car { Engine engine; public: void start() { engine.start(); } };
// "Car CÓ MỘT Engine" -> Car không phải là Engine, chỉ SỞ HỮU nó
Prefer composition over inheritance — vì sao? Inheritance tạo coupling rất chặt: Derived phụ thuộc vào chi tiết implementation của Base (không chỉ interface) — đổi Base có thể phá Derived theo cách không rõ ràng ("fragile base class problem"). Inheritance cũng chỉ cho một trục quan hệ tĩnh (cố định lúc compile-time). Composition thì lỏng hơn: Car chỉ phụ thuộc interface của Engine, có thể đổi loại engine tại runtime (dependency injection), dễ test (mock Engine), và không kế thừa nhầm các hành vi không mong muốn. Quy tắc thực dụng: chỉ dùng inheritance khi thực sự có quan hệ is-a và bạn cần polymorphism (gọi qua con trỏ/reference base) — mọi trường hợp "muốn tái sử dụng code" thuần tuý nên ưu tiên composition trước.

Điểm mấu chốt: địa chỉ subobject B bên trong C khác địa chỉ chính object C (nó nằm sau phần A). Đây gọi là pointer adjustment — khi bạn viết B* pb = &c;, compiler tự động cộng thêm offset (ở đây là +16) vào con trỏ, hoàn toàn ngầm định, để pb trỏ đúng vào phần B bên trong C.

C++ — pointer adjustment ngầm định
C c;

// pa và pb là HAI giá trị con trỏ KHÁC NHAU, dù cùng trỏ vào object 'c'
std::cout << (void*)pa << " vs " << (void*)pb;   // in ra 2 địa chỉ khác nhau

Virtual dispatch với multiple inheritance — thunk

Khi gọi virtual function qua pb->fb(), vtable của phần B cần trỏ đúng vào hàm — nhưng nếu C override fb(), hàm C::fb nhận this là con trỏ tới toàn bộ C (offset 0), trong khi lời gọi đến từ pb (offset 16). Compiler giải quyết bằng thunk: một đoạn mã máy cực nhỏ chèn vào vtable, tự động trừ lại offset trước khi nhảy vào hàm thật, đảm bảo this bên trong hàm luôn đúng.

Ambiguity

C++ — lỗi ambiguity
struct A { void foo(); };
struct B { void foo(); };
struct C : public A, public B {};
C c;
// c.foo();          // LỖI COMPILE: ambiguous, A::foo hay B::foo?
c.A::foo();           // OK — chỉ rõ dùng phiên bản của A

Compiler không tự đoán bạn muốn gọi hàm nào khi hai base độc lập có cùng tên hàm — bạn phải chỉ rõ bằng scope resolution (c.A::foo()) hoặc thêm một hàm foo() ở C để "che" (hide) cả hai, tự quyết định logic gọi bản nào.

Thứ tự constructor / destructor với multiple inheritance

Constructor chạy theo thứ tự khai báo kế thừa (trái → phải trong class C : public A, public B → A trước, B sau), destructor chạy ngược lại (B trước, A sau) — nhất quán với nguyên tắc ở chương 05-06, chỉ mở rộng từ "base đơn" sang "danh sách base theo thứ tự khai báo".

Diamond inheritance sinh ra hai bản sao base trùng lặp — virtual inheritance là cách C++ giải quyết.

Compiler implementation & overhead

Vì offset của virtual base không cố định tại compile-time của B/C riêng lẻ (nó phụ thuộc vào object cuối cùng nào kế thừa B, C — có thể D, có thể E khác kế thừa B,C theo cách khác), compiler không thể hard-code offset như multiple inheritance thường. Common implementation (Itanium ABI): mỗi base ảo có một entry trong vtable (hoặc một bảng riêng gọi là virtual base table) lưu offset tới virtual base đó — offset này được tra tại runtime, không phải compile-time. Đây là lý do virtual inheritance có overhead thực sự: mỗi object cần thêm con trỏ/offset table, mỗi lần truy cập virtual base là một indirection qua bảng đó — chậm hơn truy cập base thường (chỉ cộng offset cố định).

Constructor với virtual base

Như đã nói ở chương 05: chỉ constructor của most-derived class mới thực sự gọi constructor của virtual base — các lớp trung gian (B, C) dù có khai báo gọi A(...) trong initializer list, lời gọi đó bị bỏ qua nếu chúng không phải most-derived. Đây là điểm gây bug kinh điển: người viết B tưởng constructor của mình luôn khởi tạo A theo cách mình muốn, nhưng nếu D (kế thừa B, C) không tự gọi A(...) trong initializer list của D, A sẽ được khởi tạo bằng default constructor, không phải theo ý B.

Best practice Virtual inheritance nên là ngoại lệ hiếm gặp, không phải công cụ mặc định. Hầu hết framework hiện đại tránh diamond inheritance hoàn toàn bằng cách dùng interface (pure abstract, không có data member — xem chương 19) làm base thay vì class có state, vì nhiều interface không data member kế thừa cùng lúc không gây diamond-with-state.

Polymorphism

Compile-time (static) vs Runtime (dynamic) polymorphism — cùng mục tiêu "một interface, nhiều hành vi", khác cơ chế và chi phí hoàn toàn.

Compile-time Polymorphism

Hành vi được chọn tại compile-time, dựa trên kiểu tĩnh — không cần indirection lúc runtime.

  • Function overloading: nhiều hàm cùng tên, khác signature — compiler chọn dựa trên kiểu argument.
  • Operator overloading: định nghĩa lại ý nghĩa toán tử cho kiểu do người dùng định nghĩa.
  • Templates: sinh code riêng cho từng kiểu cụ thể tại compile-time (monomorphization).
  • CRTP (Curiously Recurring Template Pattern): mô phỏng "virtual" nhưng resolve tại compile-time — xem chương 23.

Virtual Function

virtual, override, final, pure virtual, abstract class — và tại sao luôn nên viết override.

Các từ khoá

C++
struct Base {
    virtual void foo();          // có thể override, có implementation
    virtual void bar() = 0;      // PURE virtual — bắt buộc override, Base thành abstract
    virtual void baz() final;    // không class con nào được override tiếp
};
struct Derived : Base {
    void foo() override;         // 'override' là compile-time check, không đổi runtime behavior
    void bar() override;         // bắt buộc, nếu không Derived vẫn abstract
};

override — tại sao luôn nên dùng

C++ — bug kinh điển KHÔNG dùng override
struct Base { virtual void process(int x); };
struct Derived : Base {
    void process(int x) const;   // KHÁC signature (thêm const) -> đây KHÔNG PHẢI override!
    // Compiler âm thầm coi đây là một hàm MỚI, che (hide) Base::process, không override nó
};
Base* p = new Derived;
p->process(5);   // gọi Base::process, KHÔNG gọi hàm bạn tưởng đã override trong Derived!
C++ — thêm 'override' bắt lỗi ngay
struct Derived : Base {
    void process(int x) const override;   // LỖI COMPILE: không hàm virtual nào của Base khớp
};                                          // -> buộc bạn phát hiện và sửa signature ngay lập tức

Đây là lý do tuyệt đối nên dùng override cho mọi hàm định override: nó biến một bug runtime âm thầm (hàm bị "che" thay vì override, hành vi sai nhưng compile OK) thành compile error tường minh.

Pure Virtual Function & Abstract Class

Class có ít nhất một pure virtual function chưa được override là abstract class — không thể new trực tiếp (compile error), nhưng vẫn có thể có constructor/destructor riêng (được gọi khi derived class được tạo), có thể có member variable, có thể có non-pure virtual function khác. Một class chỉ toàn pure virtual function, không data member, không implementation — thường gọi là interface class (chi tiết ở chương 19).

Interview: virtual void foo() = 0; có bắt buộc không được có thân hàm không?
Không — pure virtual function VẪN được phép có định nghĩa (thân hàm), chỉ là nó bắt buộc derived class phải override nếu muốn instantiate. Derived có thể gọi thân hàm base qua Base::foo() tường minh bên trong override của nó — kỹ thuật này dùng khi muốn ép override nhưng vẫn cung cấp hành vi mặc định dùng chung.

VTable / VPtr — Deep Dive

Đây là phần bắt buộc phải hiểu sâu nhất trong toàn bộ tài liệu.

Standard guarantee vs Common implementation C++ Standard không hề nhắc tới từ "vtable" hay "vptr" ở bất kỳ đâu. Standard chỉ định nghĩa hành vi quan sát được: gọi virtual function qua con trỏ/reference base phải dispatch tới override phù hợp nhất với kiểu thực của object. vtable/vptr là kỹ thuật implementation phổ biến nhất (GCC, Clang, MSVC đều dùng, dù chi tiết ABI khác nhau) — nhưng về lý thuyết, một compiler khác hoàn toàn có thể hiện thực virtual dispatch bằng cơ chế khác (ví dụ tra bảng theo kiểu khác, hoặc pattern-matching runtime type tag) miễn hành vi quan sát được đúng như Standard yêu cầu.

vtable là gì? vptr là gì?

  • vtable (virtual table): một bảng tĩnh (thường đặt trong read-only data segment), một bảng cho mỗi class có virtual function (không phải mỗi object) — chứa con trỏ tới implementation thực tế của từng virtual function.
  • vptr (virtual pointer): một con trỏ ẩn nằm bên trong mỗi object (thường ở đầu object, offset 0), trỏ tới vtable của kiểu thực object đó. vptr được compiler tự động khởi tạo trong constructor — bắt đầu từ constructor của lớp thấp nhất trong hierarchy (Base), rồi mỗi lớp con re-set lại vptr thành vtable của chính nó khi constructor của nó chạy (đây là lý do gọi virtual function trong constructor/destructor không dispatch tới override của derived — xem box cảnh báo bên dưới).
C++
class Base {
public:
    virtual void foo();
    virtual void bar();
};
class Derived : public Base {
public:
    void foo() override;   // override foo, KHÔNG override bar
};

                                        | slot 0: &Base::foo    |
                                        | slot 1: &Base::bar    |
                                        +-----------------------+

Mỗi object có một vtable riêng không? Class có bao nhiêu vtable?

Không. Mỗi object chỉ có một vptr (8 byte trên 64-bit) — không có bản sao vtable riêng. Mọi object cùng kiểu Derived chia sẻ chung một vtable duy nhất (một bảng static, được compiler sinh một lần khi biên dịch class Derived, đặt trong binary). Với multiple inheritance (chương 09), một class có thể có nhiều hơn một vtable — mỗi base polymorphic độc lập cần một vtable riêng (vì mỗi base part có "góc nhìn" offset khác nhau vào object, cần thunk riêng — xem lại diagram ở chương 09).

Với virtual inheritance, vtable còn lưu thêm thông tin offset tới virtual base (virtual base table offset — vbtable/vtt tuỳ ABI), cộng thêm RTTI pointer (xem chương 15) — Itanium ABI thường đặt typeinfo pointer ngay trước bảng các hàm ảo trong cùng vtable object.

    void init() override { std::puts("Derived::init"); }
};
Derived d;   // In ra "Base::init", KHÔNG PHẢI "Derived::init"!
Lý do: khi Base::Base() đang chạy, vptr của object vẫn đang trỏ tới vtable của Base (vì Derived::Derived() chưa kịp chạy để "nâng cấp" vptr) — object chưa hoàn thành trở thành một Derived thực sự, dù bộ nhớ cho phần Derived đã được cấp phát. Virtual dispatch trong constructor/destructor luôn resolve theo kiểu đang được xây dựng/huỷ tại thời điểm đó, không bao giờ "nhìn thấy trước" phần derived. Đây không phải bug compiler — đó là hành vi được Standard định nghĩa rõ ràng, và là một nguồn lỗi runtime rất phổ biến với lập trình viên không hiểu cơ chế vptr.

Virtual Dispatch

Từ CPU register tới lệnh gọi gián tiếp — so sánh với non-virtual call.

DIAGRAM — các bước thực thi p->foo()
CPU register (chứa địa chỉ 'p')
   │
   ▼ load object tại địa chỉ p (không cần đọc toàn bộ, chỉ cần offset 0)
load vptr = *(p + 0)              // đọc 8 byte đầu object -> địa chỉ vtable
   │
   ▼
load vtable entry = *(vptr + slot_offset)   // slot_offset cố định tại compile-time (biết 'foo' là slot thứ mấy)
   │
   ▼
indirect call qua function pointer vừa load được (CALL [reg])

Ba bước "load object → load vptr → load vtable slot → indirect call" là runtime cost thực sự của virtual dispatch: hai lần dereference bộ nhớ thêm (so với gọi hàm thường chỉ một CALL địa_chỉ_cố_định), và quan trọng hơn — CPU branch predictor khó dự đoán đích của indirect call nếu kiểu object thay đổi liên tục qua các lần gọi (ví dụ lặp qua vector<Base*> chứa nhiều kiểu derived khác nhau xen kẽ) → có thể gây pipeline stall.

RTTI (Run-Time Type Information)

dynamic_cast, typeid, std::type_info — compiler/runtime thực sự làm gì khi hỏi "object này thực chất là kiểu gì?".

dynamic_cast

C++
Base* p = new Derived;
Derived* d = dynamic_cast<Derived*>(p);   // p thực sự là Derived -> d != nullptr
Other*   o = dynamic_cast<Other*>(p);      // p KHÔNG phải Other -> o == nullptr (con trỏ)
Derived& rd = dynamic_cast<Derived&>(*p);  // với reference: ném std::bad_cast nếu sai kiểu

dynamic_cast chỉ hoạt động trên polymorphic type (class có ít nhất một virtual function) — vì nó cần vptr để tìm ra RTTI metadata. Tại runtime, nó: (1) đọc vptr của object, (2) từ vtable lần ra std::type_info gắn với kiểu thực, (3) so sánh/duyệt cây kế thừa được mã hoá trong type_info để xem đích cast có phải base/derived hợp lệ của kiểu thực không, (4) nếu hợp lệ, tính toán offset cần điều chỉnh con trỏ (giống pointer adjustment ở chương 09) và trả về; nếu không hợp lệ, trả nullptr (với con trỏ) hoặc ném std::bad_cast (với reference).

Performance dynamic_cast không phải phép toán O(1) đơn giản — nó có thể phải duyệt cây kế thừa (đặc biệt với multiple/virtual inheritance phức tạp), tốn hơn hẳn static_cast (chỉ cộng offset cố định, không kiểm tra gì). Dùng dynamic_cast dày đặc trong hot path (vòng lặp hiệu năng cao) là dấu hiệu thiết kế nên xem lại (thường nên thay bằng virtual function đúng nghĩa thay vì "hỏi kiểu rồi rẽ nhánh" — vi phạm tinh thần polymorphism).

typeid & std::type_info / std::type_index

C++
Base* p = new Derived;
if (typeid(*p) == typeid(Derived)) { /* ... */ }   // so sánh kiểu THỰC (vì *p polymorphic)
std::cout << typeid(*p).name();                     // tên kiểu (mangled, tuỳ compiler)

std::type_index idx(typeid(Derived));               // wrap type_info để dùng làm key trong map/set
std::unordered_map<std::type_index, Handler> table;

Lưu ý quan trọng: typeid(*p) (dereference con trỏ, polymorphic type) trả về kiểu thực tại runtime (đọc qua vptr, giống dynamic_cast) — nhưng typeid(p) (không dereference) chỉ trả về kiểu tĩnh của con trỏ (Base*), được resolve tại compile-time, không cần vtable.

Standard guarantee vs Common implementation

Phân loại Standard chỉ đảm bảo: dynamic_cast và typeid phải cho kết quả đúng theo ngữ nghĩa (thành công/thất bại, đúng kiểu). Standard không quy định RTTI được lưu trữ dưới dạng nào. Common implementation (Itanium ABI): mỗi class polymorphic có một object std::type_info tĩnh, con trỏ tới nó được nhúng ngay trước bảng hàm ảo trong cùng vtable. Một số compiler cho phép tắt RTTI hoàn toàn (-fno-rtti) để giảm binary size trên hệ nhúng — khi đó dynamic_cast/typeid trên polymorphic type không dùng được (lỗi compile hoặc linker tuỳ cách dùng), đây là lựa chọn phổ biến trong embedded C++ (xem chương 28).

this / Static Member / Friend

Ba cơ chế nhỏ nhưng nền tảng cho toàn bộ hệ thống OOP của C++.

this — thực chất là gì?

Mô hình conceptually gần đúng
class A {
public:
    void foo(int x);
};
// conceptually tương đương (không phải cú pháp hợp lệ, chỉ để hình dung):
void A_foo(A* this, int x);

A a; a.foo(5);
// compiler biến thành: A_foo(&a, 5);   -- 'this' là tham số ẩn ĐẦU TIÊN

this là một con trỏ hằng (A* const trong hàm không-const, const A* const trong hàm const) được compiler tự động truyền vào mọi non-static member function như tham số ẩn đầu tiên — đây là cách thực tế mà một member function "biết" nó đang thao tác trên object nào. this không tồn tại trong static member function (vì static function không gắn với object cụ thể), và trong lambda, [this] hoặc [*this] capture quyết định lambda giữ con trỏ hay bản sao object bao quanh nó.

this trong multiple inheritance Như đã nói ở chương 09, giá trị this bên trong một hàm có thể khác địa chỉ object nhìn từ bên ngoài, tuỳ base part nào đang được gọi — compiler tự chèn phép cộng/trừ offset (pointer adjustment/thunk) để đảm bảo this bên trong hàm luôn trỏ đúng vào phần dữ liệu nó cần thao tác.

Static Data Member & Static Member Function

C++
class Counter {
public:
    Counter() { ++count_; }
    static int count() { return count_; }   // không có 'this', không truy cập non-static member
private:
    static inline int count_ = 0;            // C++17: inline static -> định nghĩa ngay trong class, một bản duy nhất
};

Static data member không nằm trong object nào cả — nó nằm ở static storage (giống biến global, nhưng có tên được scope hoá trong class và tuân theo access control). Trước C++17, phải định nghĩa static member bên ngoài class (int Counter::count_ = 0; trong file .cpp) để tránh multiple-definition khi header được include nhiều nơi; C++17 inline giải quyết việc này gọn hơn. Static member function không nhận this, nên không thể truy cập non-static member trực tiếp — nó về bản chất chỉ là một hàm free function được "scope hoá" vào tên class.

Static Initialization Order Fiasco Thứ tự khởi tạo các static object ở các translation unit (file .cpp) khác nhau là không xác định theo Standard. Nếu static object ở file A phụ thuộc static object ở file B (khởi tạo trong constructor của A dùng giá trị của B), và B chưa kịp khởi tạo trước A — bug rất khó phát hiện. Giải pháp kinh điển: "Construct On First Use" — bọc static object trong một hàm trả về reference tới một function-local static (được khởi tạo lười, tại lần gọi đầu tiên, thread-safe từ C++11).

Friend

C++
class Matrix {
    friend Matrix operator*(const Matrix&, const Matrix&);   // friend function
    friend class MatrixBuilder;                                // friend class — toàn bộ class được truy cập private
private:
    double data_[16];
};

friend phá vỡ encapsulation một cách có kiểm soát và tường minh — chỉ class/hàm được khai báo tường minh mới có quyền, và quyền này không được kế thừa (friend của Base không phải friend của Derived) và không đối xứng (A khai báo B là friend không có nghĩa B cũng cho A truy cập private của nó). Use-case hợp lý: operator overloading cần truy cập private của cả hai bên (như operator* ở trên, thường không thể là member function nếu cần symmetric implicit conversion ở cả 2 vế), hoặc một class "builder"/"factory" cần dựng object ở trạng thái nội bộ đặc biệt.

Khi nào friend hợp lý Friend hợp lý khi hai thực thể về mặt logic là một phần của cùng một khái niệm (ví dụ Matrix và hàm operator* của nó, hay một class và test-fixture của chính nó) chứ không phải cách để "lách" thiết kế tồi khi hai class không liên quan cần truy cập lẫn nhau. Nếu bạn thấy dùng friend giữa hai class không liên quan về nghiệp vụ — đó là dấu hiệu nên tách lại interface public thay vì mở rộng quyền truy cập.

Object Lifetime & Placement New

Lifetime bắt đầu/kết thúc khi nào — và cách tạo object thủ công trên vùng nhớ có sẵn.

Lifetime bắt đầu/kết thúc khi nào

Theo Standard, lifetime của object bắt đầu khi: (1) storage với alignment/size đúng đã được cấp phát, VÀ (2) constructor của nó đã chạy xong (không throw). Lifetime kết thúc khi: destructor bắt đầu chạy (với kiểu có destructor không tầm thường), hoặc storage nó chiếm bị tái sử dụng/giải phóng. Quan trọng: "có vùng nhớ đúng kích thước" không có nghĩa "có object hợp lệ" — truy cập member/gọi virtual function trên vùng nhớ chưa chạy constructor (hoặc đã chạy destructor) là undefined behavior, dù về mặt bytes vùng nhớ đó "trông giống" object cũ.

4 loại storage duration (đã giới thiệu ở chương 02, nhắc lại đầy đủ)

  • Automatic: gắn với scope khối lệnh — object trên stack, tự huỷ khi ra khỏi {}.
  • Static: tồn tại suốt chương trình — global, namespace-scope, hoặc static bên trong hàm/class.
  • Thread: mỗi thread có bản riêng — thread_local.
  • Dynamic: cấp phát/giải phóng thủ công qua new/delete (hoặc malloc/placement new, xem dưới).

Placement New

C++
alignas(A) unsigned char buf[sizeof(A)];   // raw storage, CHƯA có object nào ở đây
A* p = new (buf) A(42);                     // placement new: chỉ GỌI CONSTRUCTOR tại địa chỉ 'buf'
                                              // KHÔNG cấp phát bộ nhớ mới (buf đã có sẵn)
p->~A();                                     // gọi destructor TƯỜNG MINH -- vì không dùng 'delete'
                                              // ('delete p' ở đây SẼ SAI vì buf không phải do 'new' cấp phát)

Placement new tách rời hai việc mà new thông thường gộp làm một: cấp phát bộ nhớ và khởi tạo object (chạy constructor). Nó nhận một con trỏ tới vùng nhớ đã có sẵn (từ malloc, một buffer stack, memory pool tự viết, hay memory-mapped hardware register trong embedded) và chỉ chạy constructor tại đó. Vì không có "cấp phát" tương ứng, bạn không bao giờ gọi delete trên con trỏ này — phải gọi destructor tường minh (p->~A();), rồi tự giải phóng vùng nhớ gốc theo cách nó được cấp phát ban đầu (nếu có).

C++17/20 — công cụ chuẩn hoá
#include <memory>
std::construct_at(p, 42);   // C++20: tương đương placement-new nhưng constexpr-friendly, an toàn kiểu hơn
std::destroy_at(p);          // C++17: gọi destructor tường minh, thay cho p->~A() viết tay

Liên hệ embedded systems

Placement new cực kỳ quan trọng trong embedded: khi không có heap allocator (hoặc cấm dùng dynamic allocation vì lý do real-time/an toàn), object vẫn cần được khởi tạo đúng cách (constructor chạy) tại một địa chỉ cố định — ví dụ một memory pool tĩnh cấp phát trước, hoặc thậm chí trực tiếp tại địa chỉ thanh ghi hardware đã memory-map. Placement new cho phép dùng đầy đủ ngữ nghĩa C++ (constructor, RAII, virtual dispatch) mà không cần malloc/free-store.

Const Correctness, Operator Overloading & Conversion

Ba công cụ để interface của class diễn đạt đúng ý định và an toàn kiểu.

Const object — phân biệt 3 cách viết dễ nhầm

C++
const A a;        // object 'a' là const -> không gọi được non-const member function trên nó
A* const p = &a2;  // 'p' là const con trỏ (không đổi được p trỏ đi đâu khác), NHƯNG *p vẫn sửa được
const A* p2 = &a;  // p2 trỏ tới const A -> KHÔNG sửa được *p2, nhưng p2 tự do đổi trỏ chỗ khác

Đọc kiểu con trỏ phức tạp theo quy tắc "từ phải sang trái, bắt đầu từ tên biến": const A* p2 đọc là "p2 là con trỏ tới (A mà là const)"; A* const p đọc là "p là (const con trỏ) tới A".

Member function const

C++
class Vector3 {
public:
    double length() const { return std::sqrt(x_*x_ + y_*y_ + z_*z_); }   // KHÔNG sửa state -> const
    void normalize();   // CÓ sửa state -> không const
private:
    double x_, y_, z_;
};
void printLen(const Vector3& v) { std::cout << v.length(); }   // chỉ gọi được length(), không gọi normalize()

Về compiler-level, hàm const nhận this với kiểu const A* const thay vì A* const — compiler dùng chính cơ chế overload resolution/type-check thông thường để cấm gọi hàm non-const trên object const, hoàn toàn ở compile-time, không có runtime cost nào. const-correctness là công cụ giao tiếp ý định cực mạnh: một hàm nhận const Vector3& cam kết với người gọi "tôi sẽ không sửa object của bạn" — cam kết được compiler enforce.

Conversion — vì sao A a = 10; compile được

C++
class A { public: A(int) {} };   // converting constructor, KHÔNG explicit
A a = 10;   // hợp lệ: compiler tìm đường "int -> A" qua constructor 1-tham số không explicit

Đây gọi là user-defined implicit conversion. Compiler chỉ cho phép tối đa một user-defined conversion trong chuỗi implicit conversion cho một biểu thức (không cho phép bắc cầu hai converting constructor liên tiếp) — đây là giới hạn an toàn để tránh implicit conversion chain khó kiểm soát. Conversion operator (operator T() const;) làm điều ngược lại: cho phép object của bạn tự implicit-convert sang kiểu khác — cực kỳ dễ gây bug khó lường (ví dụ hai kiểu tự động convert qua lại lẫn nhau dẫn tới ambiguous overload resolution ở những nơi không ngờ tới), nên C++11 thêm explicit operator T() const; để chỉ cho phép conversion tường minh (như static_cast<T>) — mẫu kinh điển là explicit operator bool() const; trên smart pointer, cho phép if (ptr) nhưng chặn int x = ptr;.

Access Control, Abstract Interface & PImpl

protected dễ hiểu nhầm nhất trong access control; interface pattern & PImpl là hai công cụ abstraction thực chiến.

protected — trường hợp dễ nhầm

C++ — hiểu nhầm phổ biến
struct Base { protected: int x; };
struct A : Base {
    void foo(Base& b) { b.x = 5; }     // LỖI COMPILE!
    void bar(A& other) { other.x = 5; } // OK
};

Đây là điểm gây nhầm lẫn kinh điển: protected không có nghĩa "mọi class kế thừa Base đều được truy cập x trên MỌI object Base" — nó chỉ cho phép A truy cập phần x nằm bên trong chính subobject Base của một object cùng kiểu A trở xuống (hoặc kiểu A chính xác). b ở trên có kiểu tĩnh là Base& (không đảm bảo đó là một A) nên A không được phép đụng vào phần private/protected của một Base "trần trụi", chỉ được đụng vào phần protected khi nó chắc chắn nằm trong một object cùng hoặc-là-con của chính A.

Interface trong C++

C++
class IDevice {
public:
    virtual void open()  = 0;
    virtual void close() = 0;
    virtual ~IDevice() = default;   // virtual destructor BẮT BUỘC (xem chương 06)
};
class UartDevice : public IDevice {
public:
    void open()  override { /* ... */ }
    void close() override { /* ... */ }
};

C++ không có từ khoá interface riêng như Java — quy ước là một class chỉ chứa pure virtual function (và virtual destructor), không data member, không implementation. Đây là công cụ chủ lực cho Dependency Inversion (module cấp cao phụ thuộc abstraction, không phụ thuộc chi tiết cụ thể) và Dependency Injection (truyền implementation cụ thể vào từ bên ngoài, thường qua constructor nhận con trỏ/reference interface) — nền tảng để test bằng mock (thay UartDevice thật bằng một MockDevice implement cùng IDevice khi unit test).

PImpl (Pointer to Implementation)

Widget.h — header PUBLIC, không lộ chi tiết
class Widget {
public:
    Widget();
    ~Widget();                       // phải khai báo (không = default) trong header
    void doWork();
private:
    class Impl;                      // forward declaration, chưa cần định nghĩa đầy đủ ở đây
    std::unique_ptr<Impl> pimpl_;    // con trỏ tới implementation ẩn hoàn toàn
};
Widget.cpp — implementation THẬT nằm ở đây
class Widget::Impl {
public:
    void doWorkImpl() { /* toàn bộ chi tiết, thư viện phụ thuộc... nằm ở đây */ }
    HeavyInternalType data_;   // người dùng Widget.h KHÔNG BAO GIỜ thấy kiểu này

Widget::Widget() : pimpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;    // ĐỊNH NGHĨA Ở ĐÂY, nơi Impl đã đầy đủ (complete type)

Vì sao destructor không thể = default ngay trong header std::unique_ptr<Impl> cần Impl là complete type (định nghĩa đầy đủ, không chỉ forward-declare) tại nơi destructor của nó được sinh, vì unique_ptr's destructor cần biết sizeof(Impl) để gọi đúng delete. Nếu bạn viết ~Widget() = default; ngay trong header (nơi Impl mới chỉ forward-declare), compiler sẽ báo lỗi "incomplete type". Giải pháp chuẩn: chỉ khai báo destructor trong header, định nghĩa (kể cả bằng = default;) trong .cpp — nơi Impl đã có định nghĩa đầy đủ.

PImpl đánh đổi: thêm một tầng indirection + một lần cấp phát heap mỗi object, để đổi lấy: (1) đổi implementation không cần recompile code dùng header (giảm thời gian build cho codebase lớn — "compile firewall"), (2) ABI ổn định giữa các version thư viện (thêm/bớt private member không đổi sizeof(Widget) nhìn từ bên ngoài, quan trọng khi phân phối shared library nhị phân).

RAII & Smart Pointer

Nguyên lý quản lý tài nguyên quan trọng bậc nhất trong C++ hiện đại — và các smart pointer hiện thực hoá nó.

RAII — Resource Acquisition Is Initialization

Ý tưởng cốt lõi: gắn vòng đời tài nguyên (memory, file handle, mutex lock, socket, GPU handle...) với vòng đời của một object — tài nguyên được lấy trong constructor, giải phóng trong destructor. Vì C++ đảm bảo destructor của object tự động (stack) luôn chạy khi ra khỏi scope — kể cả khi thoát qua exception (stack unwinding) — tài nguyên không bao giờ bị "quên giải phóng" miễn nó được bọc trong một RAII object đúng cách.

C++ — RAII với mutex
void criticalSection(std::mutex& m) {
    std::lock_guard<std::mutex> lock(m);   // constructor: m.lock()
    doWork();                               // nếu doWork() throw...
}   // ...lock_guard's destructor VẪN chạy khi unwind -> m.unlock() LUÔN được gọi, không deadlock

Đây chính là lý do RAII được coi là kết hợp tự nhiên với exception: không cần try/finally (C++ không có finally) — destructor đóng vai trò "finally" tự động cho mọi resource.

Chỉ chuyển sang shared_ptr khi thực sự có nhiều chủ sở hữu đồng thời và không biết trước ai huỷ trước. Tránh shared_ptr "mặc định vì tiện" — đó là dấu hiệu chưa nghĩ rõ ai thực sự sở hữu object, và mang theo overhead runtime không cần thiết (atomic increment/decrement mỗi lần copy, ảnh hưởng cache và performance đa luồng).

CRTP & Type Erasure

Hai kỹ thuật đối lập: CRTP loại bỏ virtual dispatch bằng template; type erasure giấu kiểu cụ thể đằng sau một interface thống nhất.

CRTP — Curiously Recurring Template Pattern

C++
template <typename Derived>
class Shape {
public:
    double area() const {
        return static_cast<const Derived*>(this)->areaImpl();   // "virtual" NHƯNG resolve tại COMPILE-TIME
    }
};
class Circle : public Shape<Circle> {   // Derived tự truyền chính nó làm template argument -- "curiously recurring"
public:
    double areaImpl() const { return 3.14159 * r_ * r_; }
private:
    double r_ = 1.0;
};

CRTP mô phỏng polymorphism (base gọi được hàm của derived) nhưng static_cast ở đây được resolve hoàn toàn tại compile-time — không có vptr, không có vtable, không có indirect call. Shape<Circle>::area() có thể được inline thẳng vào Circle::areaImpl(). Đánh đổi: mất khả năng heterogeneous container — bạn không thể có std::vector<Shape*> chứa cả Circle và Square, vì Shape<Circle> và Shape<Square> là hai kiểu hoàn toàn khác nhau (mỗi instantiation của template sinh ra một kiểu riêng).

CRTP giải quyết vấn đề gì? Khi bạn cần "chia sẻ code chung ở base, nhưng gọi lại hàm cụ thể của derived" (giống virtual) mà biết chắc kiểu cụ thể ngay tại compile-time (không cần heterogeneous container) — CRTP cho performance tương đương hand-written code (zero-overhead), trong khi virtual function luôn trả giá indirection dù bạn có cần polymorphism runtime hay không.

Type Erasure

Type erasure là kỹ thuật ngược lại: giấu hoàn toàn kiểu cụ thể đằng sau một interface thống nhất, nhưng không cần các kiểu đó cùng kế thừa một base chung tường minh (không cần "is-a" quan hệ tĩnh) — điển hình nhất chính là std::function.

C++ — cách std::function hoạt động (rút gọn concept)
// Bên trong std::function<void()> (đơn giản hoá để minh hoạ nguyên lý):
struct ICallable { virtual void call() = 0; virtual ~ICallable() = default; };
template <typename F>
struct CallableImpl : ICallable {   // wrapper TỰ ĐỘNG SINH cho MỌI kiểu F có thể gọi được
    F f;
    CallableImpl(F f) : f(std::move(f)) {}
    void call() override { f(); }
};
class MyFunction {
    std::unique_ptr<ICallable> impl_;   // KHÔNG BIẾT kiểu F cụ thể ở đây -- đã bị "xoá kiểu"
public:
    template <typename F>
    MyFunction(F f) : impl_(std::make_unique<CallableImpl<F>>(std::move(f))) {}
    void operator()() { impl_->call(); }
};
MyFunction f1 = []() { std::puts("lambda"); };   // hai kiểu HOÀN TOÀN KHÁC nhau (lambda vs function pointer)...
MyFunction f2 = &someFreeFunction;                 // ...nhưng cùng lưu được trong MyFunction!

Type erasure kết hợp template (compile-time) để sinh một wrapper polymorphic cho từng kiểu cụ thể, với virtual dispatch (runtime) để interface bên ngoài (MyFunction) không cần biết/không cần template hoá theo kiểu bên trong. Đây là cách C++ đạt được sự linh hoạt gần giống duck-typing của ngôn ngữ động, trong khi vẫn giữ static type-checking ở lớp ngoài.

Performance, Object Slicing & Undefined Behavior

Chi phí thực sự của OOP trong C++, và các cạm bẫy UB kinh điển.

Object Slicing

C++ — bug kinh điển
struct Base    { int x; virtual void foo(); };
struct Derived : Base { int y; void foo() override; };

void process(Base b) { b.foo(); }   // NHẬN THEO GIÁ TRỊ -- đây chính là nguồn gốc bug!
Derived d;
process(d);   // 'd' bị COPY vào 'b' kiểu Base -- phần 'y' và vptr của Derived bị "CẮT" (slice) mất!
              // b.foo() bên trong process() luôn gọi Base::foo(), KHÔNG BAO GIỜ Derived::foo()
DIAGRAM — object slicing
Derived d:                          Base b (sau khi copy 'd' vào 'b' theo giá trị):
+------------------+                +------------------+
| vptr (Derived)   |   copy chỉ     | vptr (Base)      |  <- vptr được set LẠI thành Base's vtable
| int x            |  ─────────▶    | int x            |     bởi Base's copy constructor!
+------------------+  phần Base     +------------------+
| int y            |  <- MẤT hoàn toàn, không có chỗ chứa trong 'b'
+------------------+

"Slicing" xảy ra vì process(Base b) nhận tham số theo giá trị — compiler chỉ cấp đủ bộ nhớ cho một Base, copy constructor của Base (được gọi ngầm khi truyền tham số) chỉ biết copy đúng phần Base, và quan trọng: nó tự set vptr của b trỏ về vtable của Base, không phải vtable của Derived — object b giờ "quên hoàn toàn" nó từng là Derived. Đây không phải undefined behavior (hành vi được định nghĩa rõ, chỉ là không như ý), nhưng gần như luôn là bug logic.

Best practice Luôn nhận polymorphic object qua con trỏ hoặc reference (void process(Base& b) hoặc const Base&), không bao giờ theo giá trị, nếu bạn định dùng virtual dispatch trên nó. Một quy tắc kinh nghiệm: nếu class có virtual function, cân nhắc xoá copy constructor/assignment (hoặc để chúng protected) để chặn slicing ngay từ compile-time.

Đây là lý do các hệ thống hiệu năng cực cao (game engine, HFT) thường tránh polymorphism runtime trong hot path, chuyển sang CRTP/template hoặc data-oriented design.

Undefined Behavior — tổng hợp các trường hợp OOP kinh điển

  • delete qua base pointer không có virtual destructor khi object thực là derived (chương 06).
  • Gọi virtual function trên object đã bị huỷ (dangling), hoặc trong constructor mong đợi hành vi của derived (chương 13).
  • Truy cập member sau std::move giả định giá trị cũ còn nguyên (chương 07) — không phải UB cứng nhưng gần biên giới nếu class tự viết move constructor để lại state thực sự invalid.
  • Dùng offsetof/ép kiểu byte-level trên non-standard-layout type (có virtual function, nhiều access-section...) — Standard không đảm bảo layout, dù common implementation thường "vẫn chạy đúng" một cách tình cờ.
  • Exception thoát khỏi destructor trong lúc đang unwind một exception khác → std::terminate() ngay lập tức (chương 06).
  • static_cast xuống (downcast) sai kiểu thực (không kiểm tra bằng dynamic_cast) rồi truy cập member không tồn tại — không có runtime check nào cứu bạn, khác hẳn dynamic_cast.

ABI & Compiler Internals

Name mangling, calling convention, và tại sao "trộn compiler" trong C++ nguy hiểm hơn hẳn C.

Name Mangling

C++ cho phép overload (nhiều hàm cùng tên khác tham số), namespace, template — nhưng linker chỉ hiểu một tên duy nhất cho mỗi symbol. Compiler giải quyết bằng name mangling: mã hoá namespace, tên class, tên hàm, kiểu tham số thành một chuỗi định danh duy nhất.

Ví dụ mangling (Itanium ABI — GCC/Clang)
int foo(int);        // mangled: _Z3fooi
int foo(double);      // mangled: _Z3food     -- khác 'i' vs 'd' -> hai symbol RIÊNG BIỆT
namespace ns { void bar(); }   // mangled: _ZN2ns3barEv

Đây là lý do C và C++ không link trực tiếp với nhau nếu không có extern "C": hàm C không mangled (tên symbol y hệt tên hàm), còn C++ mangled theo quy tắc riêng của từng compiler — extern "C" ép compiler dùng convention không-mangled kiểu C cho hàm đó, cho phép C++ gọi thư viện C (và ngược lại) an toàn.

Tại sao ABI của các compiler khác nhau

Standard C++ chỉ định nghĩa ngôn ngữ (cú pháp + ngữ nghĩa quan sát được), không định nghĩa ABI (cách mangling, layout object, calling convention, cách truyền tham số, cách unwind exception). Mỗi trình biên dịch/nền tảng tự chọn một ABI: GCC và Clang trên Linux/macOS cùng tuân theo Itanium C++ ABI (một đặc tả công khai, mục đích ban đầu là để nhiều compiler tương thích nhau trên kiến trúc Itanium, sau đó trở thành chuẩn thực tế cho Unix-like) — nên object file từ GCC và Clang (cùng version tương thích) thường link được với nhau. MSVC dùng ABI hoàn toàn riêng, không công khai đầy đủ, không tương thích Itanium — object file MSVC không link trực tiếp được với GCC/MinGW nếu khác ABI.

Hệ quả thực tế Không bao giờ trộn lẫn thư viện C++ đã biên dịch sẵn (.lib/.a/.so) từ các compiler khác nhau (hoặc cùng compiler nhưng version chênh lệch đáng kể, đặc biệt qua các cột mốc ABI-breaking) trong cùng một binary nếu chúng trao đổi std::string, std::vector, object polymorphic, hay bất kỳ kiểu C++ nào qua ranh giới đó — layout nội bộ (kể cả của thư viện chuẩn) có thể khác nhau giữa các ABI, dẫn tới đọc sai bytes, crash, hoặc lỗi im lặng cực khó debug. Đây là lý do các thư viện C++ phân phối dạng binary thường ghi rõ "compiled with GCC x.y, libstdc++ ABI version z".

OOP + Concurrency & Testing

Object và đa luồng; thiết kế OOP để dễ test.

OOP + Concurrency

  • vtable là read-only, chia sẻ an toàn giữa các thread (nó tĩnh, không đổi sau khi biên dịch) — bản thân virtual dispatch không có race condition. Vấn đề race condition luôn nằm ở state (data member) của object, không phải cơ chế OOP.
  • Constructor chạy trên object chưa "public" (chưa được publish cho thread khác thấy) thường an toàn tự nhiên — nhưng nếu bạn "leak this" ra ngoài trong constructor (ví dụ đăng ký callback với this trước khi object khởi tạo xong), thread khác có thể thấy object ở trạng thái nửa vời — cực kỳ nguy hiểm kết hợp với vấn đề vptr chưa hoàn chỉnh (chương 13).
  • Function-local static (Meyer's Singleton) được Standard đảm bảo khởi tạo thread-safe từ C++11 — compiler tự chèn double-checked locking ở machine code, không cần bạn tự viết.
  • shared_ptr's control block dùng atomic cho ref count — an toàn copy/destroy shared_ptr từ nhiều thread, nhưng truy cập object nó trỏ tới vẫn cần đồng bộ hoá riêng nếu nhiều thread cùng sửa.

OOP + Testing

Interface (chương 19) + Dependency Injection (chương 21) là nền tảng để unit test code OOP: thay vì class OrderService { Database db_; } (phụ thuộc cứng một implementation cụ thể), viết class OrderService { IDatabase& db_; } nhận qua constructor — test có thể truyền một MockDatabase : IDatabase giả lập kết quả mà không cần database thật. Virtual function chính là cơ chế C++ dùng để "mock" — mock framework (Google Mock...) thường tự sinh class implement interface, ghi lại lời gọi, và cho phép assert số lần gọi/tham số truyền vào.

Best practice Để dễ test, thiết kế class sao cho mọi dependency "khó test" (I/O, thời gian hệ thống, network) đều đi qua một interface có thể inject — không new cứng bên trong constructor. Đây chính là ứng dụng trực tiếp của Dependency Inversion Principle (chương 21).

Embedded C++ & Linux / System Programming

OOP vẫn hữu ích trên MCU giới hạn tài nguyên, nhưng phải chọn lọc cơ chế cẩn thận.

Những gì thường TRÁNH trong embedded

  • Exception (-fno-exceptions): bảng unwind chiếm flash, và thời gian throw không xác định (không phù hợp real-time) — thường thay bằng error code hoặc std::expected (C++23)/kiểu tương tự tự viết.
  • RTTI (-fno-rtti): dynamic_cast/typeid cần metadata tĩnh cho mỗi class polymorphic — tắt để giảm binary size khi flash rất hạn chế.
  • Dynamic allocation (new/malloc tuỳ ý): fragmentation trên hệ không có MMU/virtual memory là rủi ro nghiêm trọng — thường dùng static allocation, memory pool cố định kích thước, hoặc placement new (chương 17) trên buffer tĩnh.

Những gì VẪN dùng tốt

  • Virtual function cho HAL (Hardware Abstraction Layer): một interface IGpio với các implementation cụ thể theo chip — code nghiệp vụ viết một lần, chạy trên nhiều board bằng cách đổi implementation, chi phí một vptr/object và một indirect call là chấp nhận được trên hầu hết MCU hiện đại (Cortex-M trở lên).
  • RAII cực kỳ có giá trị: quản lý bật/tắt clock peripheral, lock ISR, giữ/nhả DMA channel — đảm bảo dọn dẹp đúng thứ tự kể cả khi có early-return.
  • Templates/CRTP khi cần chọn hành vi theo chip tại compile-time mà không trả phí runtime — phổ biến trong các HAL hiện đại (ví dụ nhiều thư viện Cortex-M dùng CRTP để định nghĩa register map theo kiểu, kiểm tra ở compile-time thay vì runtime).
  • Placement new để khởi tạo object đúng ngay tại địa chỉ memory-mapped register hoặc trong static buffer đã cấp phát trước.

Linux / System Programming

Trên Linux user-space, OOP C++ thường bọc quanh các resource kiểu POSIX (file descriptor, socket, mutex pthread, mmap) bằng RAII wrapper (mở trong constructor, close()/munmap() trong destructor) — cùng nguyên lý với smart pointer nhưng cho tài nguyên hệ điều hành thay vì bộ nhớ thuần. Virtual interface cũng phổ biến để trừu tượng hoá transport layer (TCP vs Unix domain socket vs serial) đằng sau một ITransport chung.

C vs C++ OOP

C không có OOP native — nhưng kỹ sư C vẫn mô phỏng được các ý tưởng cốt lõi bằng tay, giúp hiểu rõ hơn C++ làm gì "miễn phí" cho bạn.

C — mô phỏng "class" & "virtual function" thủ công
// "vtable" tự viết bằng tay
typedef struct { void (*speak)(void* self); } AnimalVTable;
typedef struct { const AnimalVTable* vtable; } Animal;   // "vptr" chính là con trỏ này

typedef struct { Animal base; const char* name; } Dog;
void dog_speak(void* self) { printf("%s: Woof!\n", ((Dog*)self)->name); }
static const AnimalVTable dog_vtable = { .speak = dog_speak };

void animal_speak(Animal* a) { a->vtable->speak(a); }   // "virtual call" thủ công qua con trỏ hàm

Đoạn code C ở trên chính xác là những gì compiler C++ tự động sinh ra phía sau khi bạn viết virtual void speak(); — struct AnimalVTable tương đương vtable, con trỏ vtable trong Animal tương đương vptr, và animal_speak() tương đương cơ chế virtual dispatch ở chương 14. Hiểu được bài tập "viết OOP bằng tay trong C" này là cách chắc chắn nhất để nội tâm hoá rằng vtable/vptr không phải "phép màu ngôn ngữ" — nó chỉ là pattern con trỏ hàm được compiler tự động hoá và tối ưu.

Interview Questions — tổng hợp

30 câu hỏi cốt lõi (đúng theo mục tiêu cuối tài liệu gốc), trả lời ngắn gọn kèm link về chương chi tiết.

1. Class và object khác nhau thế nào?
Class là type (bản thiết kế, biết lúc compile-time); object là instance cụ thể tồn tại trong bộ nhớ tại runtime, có địa chỉ và lifetime riêng. Xem chương 02.
2. Object nằm trong memory như thế nào?
Là một vùng bytes liên tục: member theo thứ tự khai báo (trong cùng access-section), có padding chèn giữa để đảm bảo alignment, cộng vptr nếu class polymorphic. Xem chương 03.
3. sizeof(class) được quyết định ra sao?
Tổng kích thước member + padding cần thiết để mọi member đúng alignment + padding cuối để size chia hết cho alignment lớn nhất (để array hoạt động đúng) + vptr nếu có virtual function. Xem chương 03.
4. this thực chất là gì?
Tham số ẩn đầu tiên compiler tự truyền vào mọi non-static member function, trỏ tới object đang được thao tác. Xem chương 16.
5. Constructor hoạt động thế nào?
Khởi tạo virtual base → direct base → data member (theo thứ tự khai báo) → chạy thân hàm. Xem chương 05.
6. Destructor hoạt động thế nào?
Ngược hoàn toàn constructor: thân hàm → data member (ngược khai báo) → direct base (ngược khai báo) → virtual base. Xem chương 06.
7. Tại sao phải có virtual destructor?
Để delete qua con trỏ base gọi đúng chuỗi destructor của kiểu thực; thiếu nó là undefined behavior, thường gây rò rỉ tài nguyên của phần derived. Xem chương 06.
8. Virtual function hoạt động thế nào?
Compiler không resolve tĩnh — object có vptr trỏ tới vtable của kiểu thực, lời gọi tra đúng slot trong vtable rồi gọi gián tiếp. Xem chương 12-14.
9. vtable/vptr là gì?
vtable: bảng con trỏ hàm tĩnh, một bảng/class. vptr: con trỏ trong mỗi object trỏ tới vtable đúng kiểu thực của nó. Đây là common implementation, không phải yêu cầu của Standard. Xem chương 13.
10. Virtual dispatch hoạt động ra sao?
Load vptr từ object → load entry tương ứng trong vtable → indirect call qua con trỏ hàm đó. Xem chương 14.
11. Multiple inheritance làm object layout thay đổi thế nào?
Object chứa nhiều base subobject nối tiếp nhau; địa chỉ của base thứ hai trở đi khác địa chỉ object gốc (cần pointer adjustment); nếu có polymorphic base, có thể có nhiều vtable/thunk. Xem chương 09.
12. Diamond inheritance giải quyết thế nào?
Dùng virtual inheritance để đảm bảo chỉ một bản base chung duy nhất; offset tới virtual base được tra tại runtime thay vì cố định. Xem chương 10.
13. RTTI hoạt động thế nào?
Metadata type_info tĩnh gắn với mỗi class polymorphic (thường nhúng kèm vtable); dynamic_cast/typeid đọc qua vptr để tra kiểu thực tại runtime. Xem chương 15.
14. dynamic_cast làm gì?
Kiểm tra tại runtime xem cast có hợp lệ theo kiểu thực của object không, trả nullptr (con trỏ) hoặc ném bad_cast (reference) nếu không hợp lệ — khác static_cast không kiểm tra gì. Xem chương 15.
15. Object slicing là gì?
Khi copy một object derived vào biến kiểu base theo giá trị, phần derived (và vptr đúng) bị "cắt" mất, object kết quả trở thành đúng nghĩa một Base. Xem chương 25.
16. Copy và move khác nhau thế nào?
Copy nhân bản dữ liệu (deep copy nếu viết đúng); move "cướp" tài nguyên từ nguồn (rvalue) và để nguồn ở trạng thái rỗng hợp lệ, tránh copy thừa. Xem chương 07.
17. Rule of 0/3/5 là gì?
Rule of 0: không viết hàm đặc biệt nào nếu member đã tự quản lý tài nguyên. Rule of 3: viết đủ destructor+copy ctor+copy assign nếu quản lý tài nguyên thô. Rule of 5: thêm move ctor+move assign. Xem chương 07.
18. RAII là gì?
Gắn vòng đời tài nguyên với vòng đời object — lấy trong constructor, giải phóng trong destructor, đảm bảo dọn dẹp kể cả khi có exception. Xem chương 20.
19. Composition và inheritance khác nhau thế nào?
Inheritance là is-a, coupling chặt (kể cả implementation); composition là has-a, chỉ phụ thuộc interface của thành phần, linh hoạt hơn và dễ đổi tại runtime. Xem chương 08, 22.
20. Khi nào dùng virtual?
Khi cần chọn hành vi theo kiểu thực tại runtime, đặc biệt khi cần heterogeneous container (một danh sách chứa nhiều kiểu con khác nhau qua con trỏ base chung). Xem chương 11-12.
21. Khi nào dùng template?
Khi kiểu cụ thể biết được tại compile-time và bạn muốn zero-overhead, hoặc cần viết code generic hoạt động với nhiều kiểu không cần chung base class. Xem chương 24.
22. CRTP giải quyết vấn đề gì?
Cho phép base "gọi lại" hàm cụ thể của derived (như virtual) nhưng resolve hoàn toàn tại compile-time, không cần vtable — đổi lại mất khả năng heterogeneous container. Xem chương 23.
23. Type erasure hoạt động ra sao?
Kết hợp template (sinh wrapper polymorphic cho từng kiểu cụ thể tại compile-time) với virtual dispatch (interface ngoài không cần biết kiểu bên trong) — ví dụ điển hình là std::function. Xem chương 23.
24. OOP có overhead gì?
vptr thêm vào mỗi object polymorphic, indirect call khó inline/khó branch-predict, có thể ảnh hưởng cache locality khi object rải rác trên heap. Xem chương 25.
25. Compiler biến OOP code thành machine code thế nào?
Tính layout/offset member, sinh vtable tĩnh, mangling tên symbol, sinh IR rồi assembly theo ABI đích, virtual call trở thành load+load+indirect-call. Xem chương 26.
26. ABI ảnh hưởng OOP ra sao?
ABI quyết định layout vtable, vị trí vptr, cách mangling, calling convention — khác nhau giữa GCC/Clang (Itanium ABI) và MSVC, nên object file biên dịch bởi ABI khác nhau không nên trộn lẫn khi trao đổi kiểu C++. Xem chương 26.
27. OOP được áp dụng thế nào trong embedded?
Dùng chọn lọc: virtual cho HAL interface, RAII cho quản lý peripheral, tránh exception/RTTI/dynamic allocation tuỳ ràng buộc tài nguyên/real-time. Xem chương 28.
28. Làm thế nào để thiết kế một hệ thống C++ OOP lớn mà không biến thành "God Object"?
Áp dụng Single Responsibility nghiêm ngặt, ưu tiên composition, chia interface nhỏ theo Interface Segregation, và dùng dependency injection thay vì để một class ôm quá nhiều trách nhiệm/dependency. Xem chương 21.
29. Khi nào OOP là lựa chọn sai?
Khi bài toán là xử lý dữ liệu hàng loạt hiệu năng cực cao (data-oriented design thắng rõ), khi logic thuần hàm không có state phức tạp (functional/generic gọn hơn), hoặc khi hệ thống quá nhỏ để cần trừu tượng hoá. Xem chương 01.
30. Làm sao review một thiết kế OOP ở mức Senior?
Kiểm tra: mỗi class có đúng một trách nhiệm không (SRP); interface có tối thiểu, không rò rỉ chi tiết implementation không (abstraction); có vi phạm Liskov ở đâu không; ownership của mọi con trỏ/resource có rõ ràng không (RAII, unique_ptr mặc định); có chỗ nào lẽ ra nên composition nhưng lại dùng inheritance không; virtual có đang được dùng đúng chỗ cần polymorphism runtime, hay chỉ vì thói quen.

Practice Roadmap — 12 cấp độ

Mỗi bài kèm yêu cầu, cạm bẫy ẩn và gợi ý — solution để bạn tự làm trước khi xem chương liên quan.

Level 1 — Class / Object cơ bản

Yêu cầu: Viết class Point2D (x, y kiểu double) với constructor, hàm distanceTo(const Point2D&) const.

Cạm bẫy ẩn: Quên const trên hàm không sửa state — sẽ không gọi được trên object const Point2D&. Gợi ý: xem chương 18 về const correctness.

Level 2 — Constructor / Destructor

Yêu cầu: Viết class quản lý một mảng động (IntArray) với constructor nhận size, destructor giải phóng.

Cạm bẫy ẩn: Không viết copy constructor → double free khi copy object. Gợi ý: chương 07, Rule of 3.

Level 3 — Copy / Move

Yêu cầu: Thêm move constructor + move assignment cho IntArray ở Level 2, viết noexcept đúng chỗ.

Cạm bẫy ẩn: Quên set con trỏ nguồn về nullptr sau move → double free khi cả hai object bị huỷ. Gợi ý: chương 07.

Level 4 — Inheritance

Yêu cầu: Shape base với area(), Circle/Rectangle kế thừa.

Cạm bẫy ẩn: Viết hàm printArea(Shape s) nhận theo giá trị → object slicing. Gợi ý: chương 25.

Level 5 — Polymorphism

Yêu cầu: std::vector<std::unique_ptr<Shape>> chứa nhiều kiểu, lặp gọi area() qua con trỏ base.

Cạm bẫy ẩn: Quên virtual destructor trên Shape → rò rỉ khi unique_ptr huỷ qua kiểu base. Gợi ý: chương 06.

Level 6 — RTTI

Yêu cầu: Viết hàm nhận Shape*, dùng dynamic_cast để xử lý riêng nếu là Circle.

Cạm bẫy ẩn: Lạm dụng dynamic_cast thay vì thêm virtual function đúng nghĩa — vi phạm tinh thần polymorphism. Gợi ý: chương 15, cân nhắc lại thiết kế virtual.

Level 7 — RAII

Yêu cầu: Viết FileGuard RAII wrapper cho FILE* (fopen/fclose).

Cạm bẫy ẩn: Không xoá copy constructor/assignment → hai FileGuard cùng đóng một FILE* (double close). Gợi ý: chương 20, cân nhắc unique_ptr với custom deleter thay vì tự viết.

Level 8 — Design Pattern

Yêu cầu: Implement Observer pattern: Subject thông báo nhiều IObserver khi state đổi.

Cạm bẫy ẩn: Giữ IObserver* thô sau khi observer đã bị huỷ → dangling pointer khi notify. Gợi ý: chương 20-21, cân nhắc weak_ptr.

Level 9 — Memory Layout

Yêu cầu: Dùng offsetof/in sizeof để xác nhận padding thực tế của một struct tự thiết kế, thử sắp lại member để giảm size.

Cạm bẫy ẩn: Dùng offsetof trên non-standard-layout type (có virtual function) — undefined behavior. Gợi ý: chương 03.

Level 10 — Compiler Internals

Yêu cầu: Dùng nm -C/objdump -d -C để tìm vtable của một class, xác nhận số lượng entry khớp số virtual function.

Cạm bẫy ẩn: Quên rằng gọi qua kiểu tĩnh chính xác (không qua con trỏ base) có thể bị devirtualize, không thấy indirect call như mong đợi. Gợi ý: chương 30.

Level 11 — Embedded OOP

Yêu cầu: Thiết kế interface IGpio (set/clear/read pin) với một implementation giả lập bằng mảng trong RAM (mô phỏng register), dùng placement new để khởi tạo tại một buffer tĩnh.

Cạm bẫy ẩn: Dùng new/delete thông thường thay vì static allocation — không phù hợp ràng buộc embedded thực tế. Gợi ý: chương 17, 28.

Level 12 — System Architecture

Yêu cầu: Thiết kế lại toàn bộ Level 1-11 thành một mini framework thống nhất (xem Final Project ở chương 35), review chính thiết kế của bạn theo SOLID.

A(const A&);                // copy constructor
