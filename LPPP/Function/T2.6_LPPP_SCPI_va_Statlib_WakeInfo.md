## 0 · `LPPP_SCPI.c` = 11 wrapper mỏng

File 193 dòng, mỗi hàm chỉ chuyển tiếp sang `LPPP_Statlib` / `LPPP_WakeInfo` / GPIO. Không có
logic riêng. Được `process_scpi_cmd` (case `0x81`–`0x8A`) gọi trực tiếp:

| SCPI | `app_scpi.c` gọi | `LPPP_SCPI.c` làm |
|---|---|---|
| `0x81` | `SCPIGetProtocolVersion()` (`:924`) | `return PROTOCOL_VERSION` = `(1<<8)|0` = `0x0100` |
| `0x82` | `SCPIAPOff()` (`:929`) | `scpi_ap_ctl(0)` → `LPPP_GPIO_Write(AP_PWR_EN, 0)` |
| `0x83` | `SCPISetAPStatus(payload)` (`:934`) | `LPPP_SetStatus(ap_sd, status)` |
| `0x84` | `SCPIGetAPStatus()` (`:939`) | `LPPP_GetStatus(ap_sd)` |
| `0x85` | `SCPISetPowerStatus(payload)` (`:943`) | `LPPP_SetStatus(pwr_sd, status)` ★ cửa hậu |
| `0x86` | `SCPIGetPowerStatus()` (`:948`) | `LPPP_GetStatus(pwr_sd)` |
| `0x87` | `SCPIGetWakeInfo()` (`:953`) | `LPPP_GetWakeInfo()` — **đọc + xoá** |
| `0x8A` | `SCPIGetPmuEvent()` (`:971`) | ★ **side effect** + bit `MC_WDT` |

`SCPIAPOn()` cũng có trong file (`scpi_ap_ctl(1)`) nhưng **không case nào gọi** — case `0x82`
luôn gọi `SCPIAPOff()`. ⇒ tham số `on` mà Linux gửi trong `KM_SCPI_CMD_AP_CTL (0x82)` (T2.5 §4)
**bị bỏ qua ở R4** — lệnh `0x82` luôn hạ `AP_PWR_EN` (cắt nguồn AP). Linux chỉ gửi khi thật sự
muốn tắt (`ap_ctl(0)` — lệnh cuối trước khi AP biến mất).

### `SCPIGetPmuEvent()` (`LPPP_SCPI.c:180-193`) — hai việc trong một hàm "Get"
```c
uint8_t SCPIGetPmuEvent(void) {
    LPPP_GPIO_HandleMainSW(false);              // ★ SIDE EFFECT: gỡ VĨNH VIỄN ISR nút nguồn chính
    uint8_t event = 0;
    if (LPPP_get_McWDT_status())                // MC (Machine Control M3) watchdog đã nổ?
        event |= KM_SCPI_PMU_MC_WDT;            // = 0x01
    return event;
}
```
Đúng như `AppMhuTest.md §E.7`: tên `Get*` nhưng còn **bàn giao quyền xử lý nút nguồn từ LPPP
sang AP** — trước khi Linux boot xong, LPPP tự xử lý nút nguồn (kéo `HRESET_REQN`); Linux gọi
`0x8A` một lần → LPPP nhả ra. Không có lệnh hoàn tác.

## 1 · `LPPP_SCPI_Protocol.h` — hằng số giao thức KM (đối chiếu Linux `km_scpi.h`)

| Nhóm | LPPP `LPPP_SCPI_Protocol.h` | Linux `km_scpi.h` (T2.5) | Ghi chú |
|---|---|---|---|
| version | `PROTOCOL_VERSION = SET_PROTOCOL_VER(1,0)` = `0x0100` | `get_protocol_version` rx u16 | `(major<<8)\|minor` |
| cmd `0x82` | `KM_SCPI_CMD_AP_OFF` | `KM_SCPI_CMD_AP_CTL` (+ `_OFF=0/_ON=1`) | **tên khác** — R4 chỉ hiểu "OFF" |
| cmd `0x8B` | `KM_SCPI_CMD_WDT_REBOOT` | `KM_SCPI_CMD_SET_WDT_CA72` | AR1072285 |
| cmd `0x8C` | `KM_SCPI_CMD_WDT_REBOOTEXT` | `KM_SCPI_CMD_SET_WDT_CA72_EXT` | OP_BTS-14005 |
| AP status | `KM_SCPI_AP_NOT_BOOT=0`, `KM_SCPI_AP_WARP_BOOT=1` (`=SNAP_SHOT_FIN`) | idem | — |
| pwr status | `KM_SCPI_PWR_PWR_OFF=0 / NORMAL=1 / SLEEP1=2 / SLEEP2=3 / ERP=4` | idem (`KM_SCPI_PWR_*`) | ★ khớp `pwr_status_t` |
| AP event `0x88` | `WAKEUP_NORMAL=0 / GO_TO_S1=1 / GO_TO_S2=2 / GO_TO_ERP=3` (+ `INVAL=-1`) | `KM_SCPI_GENEV_*` (0..3) | payload 2/3 vô tác dụng (AppMhuTest.md §E.1) |
| WDT sub-cmd | `KM_SCPI_WD_CA72_START=0 / END=1 / REFRESH=2 / START_SHORT=3` | `KM_SCPI_WDT_CA72_START/END/REFRESH` (không có SHORT) | R4 có thêm SHORT (10s) |
| wake info | `KM_SCPI_WAKEUP_PACKET_ARRIVED=1`, `KM_SCPI_SNMPII_PACKET_ARRIVED=1` | idem | ⚠ **di sản** — thực tế `0x87` trả bitmask 4-bit (§2) |
| PMU event | `KM_SCPI_PMU_MC_WDT=0x01` | `PMU_EVENT_MC_WDT` | Machine Control M3 watchdog |

**Bất nhất `wake info`:** Protocol.h định nghĩa `*_PACKET_ARRIVED = 1` (kiểu giá trị 0/1), nhưng
`SCPIGetWakeInfo` trả thẳng `guc_wake_info` — một **bitmask 4-bit** (§2). Hằng số 1-giá-trị là
tàn dư từ thiết kế cũ; Linux (`km_scpi_get_wake_info`) đọc từng bit.

## 2 · `LPPP_WakeInfo.c` (52 dòng) — cờ nguyên nhân đánh thức

```c
uint8_t guc_wake_info = 0;                              // toàn cục

void    LPPP_SetWakeInfo(uint8_t info) { guc_wake_info |= info; }   // TÍCH LUỸ bằng |=
uint8_t LPPP_GetWakeInfo(void) {
    uint8_t info = guc_wake_info;
    guc_wake_info = 0;                                  // ★ ĐỌC PHÁ HUỶ
    return info;
}
```

**Bit** (`LPPP_WakeInfo.h`):
| Bit | Hằng | Nguồn |
|---|---|---|
| `1<<0` | `LPPP_WAKE_INFO_PROXY` | gói proxy khớp (không phải SNMP/WoL) |
| `1<<1` | `LPPP_WAKE_INFO_SNMP2` | gói SNMPv2 |
| `1<<2` | `LPPP_WAKE_INFO_USB` | hoạt động USB device |
| `1<<3` | `LPPP_WAKE_INFO_WOL` | Wake-on-LAN (magic packet) |

**4 nơi gọi `LPPP_SetWakeInfo`** (grep xác nhận):
| File:line | Bit | Context |
|---|---|---|
| `Application/snmp_proxy/snmp_proxy.c:832` | `SNMP2` | gói SNMP cần đánh thức host (T5.4) |
| `Sys/system/sys_system_api.c:194` | `PROXY` | proxy chung — gói cần host xử lý (T5.6) |
| `Sys/timer/sys_timer_irq.c:272` | `WOL` | phát hiện WoL trong ISR timer link-state (T9.4) |
| `Sys/wake_USBD/lpp_usbd.c:69` | `USB` | `lpp_usbd_isr` (T9.2) |

**Luồng:** nguồn wake set bit → `wake_system()` → đánh thức A72 → Linux gọi SCPI `0x87`
(`PMU_IOCSGETWAKEINFO`) → `SCPIGetWakeInfo` trả bitmask **rồi xoá**. Gọi lần 2 → `0`.
Đây là nguồn dữ liệu cho `dev_attr` wake-reason phía Linux (`BspGetWakeInfo`).

`0x87` **không** liên quan `LPPP_GPIO_HandleMainSW` — chỉ `0x8A` mới có side effect nút nguồn.

## 3 · `LPPP_Statlib.c` (196 dòng) — thư viện status descriptor

### Cấu trúc
```c
typedef uint8_t desc_t;   // ← bitmap 8 descriptor tối đa
static struct status_info {
    desc_t            desc_bitmap;                   // bit i = descriptor i đang mở
    stat_t            status[sizeof(desc_t)*8];      // = status[8], mỗi descriptor 1 giá trị int
    SemaphoreHandle_t mutex_handle;                  // 1 mutex CHUNG cho cả 8
} _status_info;
```

### 5 hàm (mọi hàm lấy mutex, timeout **10ms**)
| Hàm | Việc | Lỗi |
|---|---|---|
| `LPPP_InitStatus()` | `desc_bitmap = 0`; tạo mutex | mutex NULL → `SYS_ERROR` |
| `LPPP_OpenStatus()` | tìm bit `0` đầu tiên trong `desc_bitmap`, set nó, trả index `0..7` | không lấy được mutex / hết bit → `-1` |
| `LPPP_GetStatus(sd)` | `check_sd_range` + mutex + `return status[sd]` | range sai / timeout → `-1` |
| `LPPP_SetStatus(sd, s)` | `check_sd_range` + mutex + `status[sd] = s` | range sai / timeout → `SYS_ERROR`; OK → `SYS_OK` (=0) |
| `LPPP_CloseStatus(sd)` | mutex + `desc_bitmap &= ~(1<<sd)` | range sai → return im |

`check_sd_range(desc_t sd)`: `if (sd < 0 || 7 < sd) ret = -1`. `sd` là `uint8_t` nên `sd < 0`
luôn false; nhưng caller truyền `stat_desc_t sd` (kiểu `int`) → ép ngầm `int→uint8`: `-1` (từ
`Open` fail) thành `255` → bị `255 > 7` bắt. Hoạt động, nhưng luộm thuộm.

### Ai mở descriptor nào (`PowerControlEventManager.md §2` — `LPPP_KM_Init`)
```c
LPPP_InitStatus();
ap_sd  = LPPP_OpenStatus();   // → descriptor 0
pwr_sd = LPPP_OpenStatus();   // → descriptor 1
LPPP_SetStatus(pwr_sd, PWR_STATUS_POWEROFF);   // = KM_SCPI_PWR_PWR_OFF = 0
LPPP_SetStatus(ap_sd,  AP_STATUS_NO_BOOT);     // = KM_SCPI_AP_NOT_BOOT = 0
```
`ap_sd` và `pwr_sd` là biến **extern** (`LPPP_Task.c`), dùng khắp KM. Chỉ 2 descriptor được mở
trong toàn firmware.

### Non-atomicity — điểm mấu chốt (khớp `PowerControlEventManager.md §5`)
```c
// event_handler():
e_lppstat = LPPP_GetStatus(pwr_sd);                         // ← mutex take/give
e_lppstat = fpLPPP_ScenarioFunc[e_lppstat][e_Evt](...);     // ← KHÔNG khoá ở đây
LPPP_SetStatus(pwr_sd, e_lppstat);                          // ← mutex take/give (khác lần)
```
`Get` và `Set` mỗi cái tự lấy/nhả mutex → **khoảng giữa (chạy scenario) KHÔNG được bảo vệ**.
An toàn **chỉ vì** mọi event serialize qua đúng 1 consumer (`PwEvtMgr`). Thêm consumer thứ 2
hoặc gọi `event_handler` từ context khác (`LPPP_KM_Init` gọi trực tiếp ở prio 3) → lost-update.
Trên thực tế không có race vì chênh lệch priority (`init_thread` prio 3 chạy xong trước `PwEvtMgr` prio 0).

### Bẫy giá trị trả về (khớp `AppMhuTest.md §H`)
`LPPP_SetStatus` trả `SYS_OK = 0` khi **thành công**. `TestMsgSend`/`TestMsgSendIsr` (CLI debug)
gán vào `bool b_ret` → `0` thành `false` → coi là lỗi → return sớm. Bug ở **caller**, không phải
Statlib. `SCPISetAPStatus`/`SCPISetPowerStatus` bỏ qua giá trị trả về nên không dính.

## 4 · Ba lệnh KM chạm state machine (tổng hợp T2.5 §6 + AppMhuTest.md §F)

```
0x85 SCPISetPowerStatus(p) → LPPP_SetStatus(pwr_sd, p)   ★ ép thẳng pwr_sd, BỎ QUA ma trận
                                                            (cửa hậu — CA72 đồng bộ lại sau resume)
0x83 SCPISetAPStatus(s)    → LPPP_SetStatus(ap_sd, s)    ★ giải giáp TR2b:
                                                            s=WARP_BOOT → flicker không reset A72
0x88 (ap_event) payload 0/1 → send_km_queue → PwMHUEv → PwEvtMgr (WAKEUP_NORMAL / GO_TO_S1)
```
`0x87`/`0x8A` chỉ **đọc** (0x8A kèm side effect nút nguồn). `0x81/0x82/0x84/0x86` vô hại với SM.

## 5 · Tóm tắt (theo format skill)

**1. Tồn tại để làm gì:** `LPPP_SCPI.c` là 11 wrapper mỏng nối `process_scpi_cmd` case
`0x81`–`0x8A` với 3 kho trạng thái: `LPPP_Statlib` (2 descriptor `ap_sd`=0, `pwr_sd`=1, mỗi cái
1 `int` bảo vệ bằng 1 mutex chung, timeout 10ms), `LPPP_WakeInfo` (`guc_wake_info` bitmask 4-bit,
`Set` tích luỹ `|=`, `Get` đọc-phá-huỷ), và GPIO (`SCPIAPOff` → `AP_PWR_EN=0`). `0x8A GetPmuEvent`
có side effect ẩn: gỡ vĩnh viễn ISR nút nguồn chính (bàn giao cho AP).

**2. Lifecycle `ap_sd` / `pwr_sd`:**
```
LPPP_KM_Init [init_thread prio 3]:
  LPPP_InitStatus()                → tạo mutex
  ap_sd  = LPPP_OpenStatus()       → desc 0, bitmap |= 1
  pwr_sd = LPPP_OpenStatus()       → desc 1, bitmap |= 2
  LPPP_SetStatus(pwr_sd, POWEROFF=0)
  LPPP_SetStatus(ap_sd, NO_BOOT=0)
  event_handler(PWR_SW_ON)         → TR0 → LPPP_SetStatus(pwr_sd, NORMAL=1)
── runtime ──
  PwEvtMgr:  Get(pwr_sd) → scenario → Set(pwr_sd)     [KHÔNG atomic giữa Get và Set]
  SCPI 0x85: Set(pwr_sd, p)  ← cửa hậu, bỏ qua scenario
  SCPI 0x83: Set(ap_sd, s)   ← TR5/6 đặt NO_BOOT, SCPI 0x83 đặt WARP_BOOT
  SCPI 0x84/0x86: Get(ap_sd)/Get(pwr_sd)
  LPPP_CloseStatus — chỉ ở `out:` dead code của PwEvtMgr (không bao giờ chạy)
```

**3. File đã tham chiếu:**
- `ApplicationKM/LPPP_SCPI.c` (toàn bộ 193 dòng)
- `ApplicationKM/LPPP_SCPI_Protocol.h` (toàn bộ 77 dòng)
- `ApplicationKM/LPPP_WakeInfo.c/.h` (toàn bộ)
- `ApplicationKM/LPPP_Statlib.c/.h` (toàn bộ 196 dòng)
- `ApplicationMrvl/Test/app_scpi.c:924-971` (caller)
- callers `LPPP_SetWakeInfo`: `snmp_proxy.c:832`, `sys_system_api.c:194`, `sys_timer_irq.c:272`, `lpp_usbd.c:69`

**4. Đã xác nhận / phát hiện:**
- ✅ `SCPIAPOn()` tồn tại nhưng **không được gọi** — `0x82` luôn `SCPIAPOff()`; tham số `on` của
  Linux bị bỏ qua ở R4.
- ✅ `LPPP_WakeInfo`: 4 bit (PROXY/SNMP2/USB/WOL), 4 nơi set, đọc-phá-huỷ. Hằng
  `KM_SCPI_*_PACKET_ARRIVED` trong Protocol.h là di sản (không dùng đúng ngữ nghĩa).
- ✅ `LPPP_Statlib`: chỉ **2 descriptor** (`ap_sd`=0, `pwr_sd`=1) trong toàn firmware; 1 mutex
  chung; `Get`/`Set` không atomic với nhau → an toàn nhờ single consumer + chênh priority.
- ✅ `LPPP_SetStatus` trả `SYS_OK=0` khi thành công (bẫy `bool` ở `TestMsgSend`).
- ✅ Hằng số pwr/ap/event khớp 1:1 giữa `LPPP_SCPI_Protocol.h` (R4) và `km_scpi.h` (Linux).
