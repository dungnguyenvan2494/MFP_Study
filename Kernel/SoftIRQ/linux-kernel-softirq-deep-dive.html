01SoftIRQ là gì & Vì sao Linux cần nó

Concept → Why → Kernel Design. SOURCE: KERNEL SOURCE

Vấn đề mà SoftIRQ giải quyết

Khi một thiết bị phần cứng phát tín hiệu ngắt (IRQ), CPU nhảy vào hard IRQ handler — chạy trong interrupt context, với hard IRQ hiện tại bị mask trên CPU đó (tuỳ kiến trúc). Nếu handler này làm toàn bộ công việc thực sự (parse packet, chạy timer callback, xử lý RCU callback...) ngay tại đó, hệ quả là:

RỦI RO 1Ngắt khác bị trễ/miss vì CPU đang bận trong ISR quá lâu.
RỦI RO 2Interrupt context không được sleep → không thể gọi bất cứ API có thể block (mutex_lock, kmalloc GFP_KERNEL...).
RỦI RO 3Latency toàn hệ thống tăng vì mọi tác vụ khác phải chờ ISR xong.
GIẢI PHÁPDeferred (bottom-half) processing: ISR chỉ làm tối thiểu (ack hardware, lưu dữ liệu), phần còn lại defer ra ngoài, chạy sau với ít ràng buộc hơn.

SoftIRQ là một trong các cơ chế "bottom half" đó trong Linux — cùng với Tasklet (dựng trên SoftIRQ) và Workqueue (chạy trong process context, có thể sleep). Định nghĩa theo comment gốc trong kernel/softirq.c dòng 33-49:

kernel/softirq.c — dòng 33-49 (comment gốc của tác giả)
   - No shared variables, all the data are CPU local.
   - If a softirq needs serialization, let it serialize itself
     by its own spinlocks.
   - Even if softirq is serialized, only local cpu is marked for
     execution. Hence, we get something sort of weak cpu binding.
     Though it is still not clear, will it result in better locality
     or will not.

   Examples:
   - NET RX softirq. It is multithreaded and does not require
     any global serialization.
   - NET TX softirq. It kicks software netdevice queues, hence
     it is logically serialized per device, but this serialization
     is invisible to common code.
   - Tasklets: serialized wrt itself.

Điểm mấu chốt: SoftIRQ được thiết kế per-CPU, không share state toàn cục — mỗi CPU có bitmap pending riêng, tự quyết định chạy vector nào, không cần lock toàn cục để biết "ai đang pending". Đây là lý do hiệu năng SoftIRQ tốt hơn nhiều so với việc dùng một global queue.

    preempt_count bit layout (thực tế trong source)

    include/linux/preempt.h — dòng 32-54
    #define PREEMPT_BITS	8
#define SOFTIRQ_BITS	8
#define HARDIRQ_BITS	4
#define NMI_BITS	4

#define SOFTIRQ_SHIFT	(PREEMPT_SHIFT + PREEMPT_BITS)
#define HARDIRQ_SHIFT	(SOFTIRQ_SHIFT + SOFTIRQ_BITS)
#define NMI_SHIFT	(HARDIRQ_SHIFT + HARDIRQ_BITS)

#define PREEMPT_MASK	(__IRQ_MASK(PREEMPT_BITS) << PREEMPT_SHIFT)
#define SOFTIRQ_MASK	(__IRQ_MASK(SOFTIRQ_BITS) << SOFTIRQ_SHIFT)
#define HARDIRQ_MASK	(__IRQ_MASK(HARDIRQ_BITS) << HARDIRQ_SHIFT)
#define NMI_MASK	(__IRQ_MASK(NMI_BITS)     << NMI_SHIFT)

#define HARDIRQ_OFFSET	(1UL << HARDIRQ_SHIFT)

    NMI
    4 bit
    HARDIRQ
    4 bit
    SOFTIRQ
    8 bit — đếm được cả "disabled" (x2 offset) và "đang serving" (x1 offset)
    PREEMPT

    Chi tiết quan trọng ít người để ý: SOFTIRQ dùng SOFTIRQ_OFFSET khi đang thực sự chạy một softirq handler (trong __do_softirq()), nhưng dùng SOFTIRQ_DISABLE_OFFSET = 2×SOFTIRQ_OFFSET khi chỉ disable bottom-half bằng local_bh_disable(). Nhờ vậy in_serving_softirq() (chỉ true khi cộng đúng 1×offset, tức đang thật sự trong handler) khác với in_softirq()/softirq_count() (true cả hai trường hợp).

    Macro phát hiện context

    include/linux/preempt.h — dòng 80-104
    #define hardirq_count()	(preempt_count() & HARDIRQ_MASK)
#define softirq_count()	(preempt_count() & SOFTIRQ_MASK)
#define irq_count()	(preempt_count() & (HARDIRQ_MASK | SOFTIRQ_MASK | NMI_MASK))

/*
 * in_irq()       - We're in (hard) IRQ context
 * in_softirq()   - We have BH disabled, or are processing softirqs
 * in_interrupt() - We're in NMI,IRQ,SoftIRQ context or have BH disabled
 * in_serving_softirq() - We're in softirq context
 * in_nmi()       - We're in NMI context
 * in_task()	  - We're in task context
 *
 * Note: due to the BH disabled confusion: in_softirq(),in_interrupt() really
 *       should not be used in new code.
 */
#define in_irq()		(hardirq_count())
#define in_softirq()		(softirq_count())
#define in_interrupt()		(irq_count())
#define in_serving_softirq()	(softirq_count() & SOFTIRQ_OFFSET)
#define in_nmi()		(preempt_count() & NMI_MASK)
#define in_task()		(!(preempt_count() & \
				   (NMI_MASK | HARDIRQ_MASK | SOFTIRQ_OFFSET)))
    Cảnh báo trong chính source: comment ghi rõ in_softirq() và in_interrupt() "really should not be used in new code" — vì chúng cũng trả true khi chỉ đơn giản đang local_bh_disable(), không hề chạy trong softirq handler thật. Muốn biết "đang thực thi trong một softirq handler hay không" phải dùng in_serving_softirq().

    #define MAX_SOFTIRQ_TIME  msecs_to_jiffies(2)
#define MAX_SOFTIRQ_RESTART 10

asmlinkage __visible void __softirq_entry __do_softirq(void)
{
	unsigned long end = jiffies + MAX_SOFTIRQ_TIME;
	unsigned long old_flags = current->flags;
	int max_restart = MAX_SOFTIRQ_RESTART;
	struct softirq_action *h;
	bool in_hardirq;
	__u32 pending;
	int softirq_bit;

	/*
	 * Mask out PF_MEMALLOC as the current task context is borrowed for the
	 * softirq. A softirq handled, such as network RX, might set PF_MEMALLOC
	 * again if the socket is related to swapping.
	 */
	current->flags &= ~PF_MEMALLOC;

	pending = local_softirq_pending();
	account_irq_enter_time(current);

	__local_bh_disable_ip(_RET_IP_, SOFTIRQ_OFFSET);
	in_hardirq = lockdep_softirq_start();

restart:
	/* Reset the pending bitmask before enabling irqs */
	set_softirq_pending(0);

	local_irq_enable();

	h = softirq_vec;

	while ((softirq_bit = ffs(pending))) {
		unsigned int vec_nr;
		int prev_count;

		h += softirq_bit - 1;
		vec_nr = h - softirq_vec;
		prev_count = preempt_count();

		kstat_incr_softirqs_this_cpu(vec_nr);

		trace_softirq_entry(vec_nr);
		h->action(h);
		trace_softirq_exit(vec_nr);
		if (unlikely(prev_count != preempt_count())) {
			pr_err("huh, entered softirq %u %s %p with preempt_count %08x, exited with %08x?\n",
			       vec_nr, softirq_to_name[vec_nr], h->action,
			       prev_count, preempt_count());
			preempt_count_set(prev_count);
		}
		h++;
		pending >>= softirq_bit;
	}

	if (__this_cpu_read(ksoftirqd) == current)
		rcu_softirq_qs();
	local_irq_disable();

	pending = local_softirq_pending();
	if (pending) {
		if (time_before(jiffies, end) && !need_resched() &&
		    --max_restart)
			goto restart;

		wakeup_softirqd();
	}

	lockdep_softirq_end(in_hardirq);
	account_irq_exit_time(current);
	__local_bh_enable(SOFTIRQ_OFFSET);
	WARN_ON_ONCE(in_interrupt());
	current_restore_flags(old_flags, PF_MEMALLOC);
}

static void tasklet_action_common(struct softirq_action *a,
				  struct tasklet_head *tl_head,
				  unsigned int softirq_nr)
{
	struct tasklet_struct *list;

	local_irq_disable();
	list = tl_head->head;
	tl_head->head = NULL;
	tl_head->tail = &tl_head->head;
	local_irq_enable();

	while (list) {
		struct tasklet_struct *t = list;
		list = list->next;

		if (tasklet_trylock(t)) {
			if (!atomic_read(&t->count)) {
				if (!test_and_clear_bit(TASKLET_STATE_SCHED, &t->state))
					BUG();
				if (t->use_callback)
					t->callback(t);
				else
					t->func(t->data);
				tasklet_unlock(t);
				continue;
			}
			tasklet_unlock(t);
		}
		/* bận (count>0) hoặc trylock thất bại → đẩy lại vào cuối list */
		local_irq_disable();
		t->next = NULL;
		*tl_head->tail = t;
		tl_head->tail = &t->next;
		__raise_softirq_irqoff(softirq_nr);
		local_irq_enable();
	}
}

		usecs_to_jiffies(READ_ONCE(netdev_budget_usecs));

	list_splice_tail(&repoll, &list);

    SoftIRQ Starvation

    Dựa trên cơ chế chống-starvation đã đọc ở §08 (2ms / need_resched / 10 restart) và budget NAPI ở §12 (netdev_budget), starvation xảy ra khi:

    Workload liên tục tự raise lại chính vector đang chạy (network flood, RCU callback flood, timer dồn cục)
    ↓ __do_softirq() liên tục hit giới hạn restart → wakeup_softirqd() lặp lại
    ksoftirqd/N gần như luôn runnable, chiếm phần lớn CPU time của CPU đó
    ↓
    User task & kernel task khác trên CÙNG CPU bị trễ đáng kể (scheduler vẫn phải cho ksoftirqd chạy theo priority của nó)
    Cụ thể trên board này: vì patch CONFIG_KM_BIZHUB (§09) đặt ksoftirqd ở SCHED_RR priority 256, một khi rơi vào tình trạng starvation, ksoftirqd sẽ giữ CPU trước cả mọi task SCHED_OTHER và mọi RT task priority <256 — mức độ ảnh hưởng tới hệ thống cao hơn hẳn so với mainline (nơi ksoftirqd chỉ là SCHED_OTHER, dễ bị các task khác chen vào hơn).

    SoftIRQ ↔ RCU Stall — quan hệ CÓ ĐIỀU KIỆN, không phải nhân-quả tuyệt đối

    Nói đúng theo yêu cầu của prompt nghiên cứu: SoftIRQ không phải là Grace Period, và starvation SoftIRQ không "gây" RCU stall một cách tất định — nó tạo ra một con đường hợp lý để RCU chậm tiến triển trên CPU bị ảnh hưởng, cần xác nhận bằng /proc/softirqs (bit RCU tăng chậm) + dmesg RCU stall warning thật khi debug case cụ thể (xem §16).

    Scenario 1 — Network Flood

    SymptomCPU softirq (NET_RX) cao, throughput không tăng thêm, latency ping/SSH tăng. Expected flowNIC IRQ → napi_schedule → NET_RX_SOFTIRQ → net_rx_action → napi_poll trong budget. What happensPacket tới nhanh hơn tốc độ napi_poll() xử lý → budget <= 0 hoặc time_after_eq(jiffies,time_limit) → net_rx_action() tự __raise_softirq_irqoff(NET_RX_SOFTIRQ) lại (§12) → __do_softirq() restart loop chạm giới hạn (§08) → wakeup_softirqd(). What to inspect/proc/softirqs cột NET_RX tăng rất nhanh; sd->time_squeeze (không có API /proc chuẩn trong bản này để đọc trực tiếp — cần ftrace/kprobe nếu muốn theo dõi runtime) tăng mỗi lần budget hết. How to verifyftrace softirq_raise dồn dập cho NET_RX, perf top thấy net_rx_action/driver poll function chiếm phần lớn CPU.

    Scenario 2 — RCU Callback Flood

    SymptomRCU_SOFTIRQ tăng nhanh trong /proc/softirqs, có thể kèm cảnh báo RCU trong dmesg. Expected flowcall_rcu() liên tục (vd giải phóng object với tốc độ cao) → grace period hoàn thành → invoke_rcu_core() → RCU_SOFTIRQ → rcu_core() dispatch callback. What happensCallback backlog lớn khiến rcu_core() tốn nhiều CPU time trong mỗi lượt dispatch — vì RCU_SOFTIRQ là bit cuối trong enum (§04), nếu các vector khác cũng bận, RCU có thể bị dispatch muộn trong cùng lượt __do_softirq(). What to inspectCột RCU trong /proc/softirqs; liên hệ §15 (RCU Stall connection) để đánh giá nguy cơ. How to verifyftrace softirq_entry/softirq_exit cho vec RCU đo thời gian mỗi lượt rcu_core() chạy; dmesg tìm "rcu_sched detected stalls" nếu tình trạng kéo dài.

    Scenario 3 — Timer Flood

    SymptomTIMER_SOFTIRQ tăng cao, nhiều timer expire cùng lúc (vd nhiều driver dùng timer polling ngắn). Expected flowTick → update_process_times() → run_local_timers() → (nếu next_expiry đã tới) raise_softirq(TIMER_SOFTIRQ) → run_timer_softirq() chạy callback thật. What happensNếu rất nhiều timer cùng expire trong 1 tick, toàn bộ callback đó chạy dồn trong 1 lần run_timer_softirq() — không có "budget" riêng cho timer như NAPI (§12), nên timer callback chậm/nhiều có thể kéo dài đúng 1 lượt softirq này, chịu chung giới hạn 2ms/10-restart của __do_softirq(). What to inspectCột TIMER trong /proc/softirqs; danh sách timer đang active trên hệ thống nếu có debugfs tương ứng. How to verifyftrace function_graph quanh run_timer_softirq() đo tổng thời gian 1 lượt.

    Scenario 4 — Tasklet Flood

    SymptomTASKLET_SOFTIRQ cao, một tasklet cụ thể tự schedule lại chính nó liên tục. Expected flowtasklet_schedule() → TASKLET_SOFTIRQ → tasklet_action_common() chạy callback → callback tự gọi tasklet_schedule() lại. What happensVì tasklet_action_common() (§10) xử lý hết list hiện tại trong 1 lượt (không có budget riêng), nếu callback liên tục tự re-schedule, TASKLET_SOFTIRQ pending bit liên tục được set lại → góp phần trigger giới hạn restart của __do_softirq(). What to inspectCột TASKLET trong /proc/softirqs; xác định driver/module nào đang dùng tasklet đó (không có API kernel chuẩn để liệt kê owner của từng tasklet instance — cần biết trước từ driver code). How to verifyftrace + kprobe trên hàm callback cụ thể nếu biết địa chỉ/tên hàm.

    Scenario 5 — SoftIRQ CPU Hog tổng quát

    Symptomtop cho thấy %si (softirq) rất cao trên 1 hoặc nhiều CPU, %us/%sy thấp bất thường. Expected flowBất kỳ scenario 1-4 kéo dài, hoặc kết hợp nhiều vector cùng lúc. What happensCPU liên tục ở trong __do_softirq() (trực tiếp hoặc qua ksoftirqd), user/kernel task khác trên CPU đó bị trễ — nếu patch CONFIG_KM_BIZHUB có hiệu lực, ksoftirqd SCHED_RR priority 256 làm tình trạng "chiếm CPU trước RT task khác" rõ rệt hơn (§09, §15). What to inspectToàn bộ /proc/softirqs theo cột CPU để xác định vector nào và CPU nào bị ảnh hưởng. How to verifyperf record -a -g + perf report xem call graph tổng thể, xác nhận đúng hàm đã liệt kê trong §05 Function Index.

    Common Mistakes khi đọc/nói về SoftIRQ

    Sai: "SoftIRQ chạy sau interrupt."
    Đúng: SoftIRQ chạy sau interrupt CỦA CHÍNH CPU ĐÓ, được dispatch bởi invoke_softirq() gọi từ irq_exit() (kernel/softirq.c), có thể chạy trực tiếp trên stack hiện tại HOẶC bị defer sang ksoftirqd/N — tuỳ 3 điều kiện restart ở §08.
    Sai: "ksoftirqd xử lý SoftIRQ" (nói như thể luôn luôn đúng).
    Đúng: Phần lớn SoftIRQ chạy trực tiếp trong hard-IRQ-return path, KHÔNG qua ksoftirqd. ksoftirqd chỉ vào cuộc khi __do_softirq() chạm giới hạn 2ms/10-restart, hoặc khi force_irqthreads được bật, hoặc khi code raise softirq từ ngoài interrupt context (§09).
    Sai: "preempt_count chỉ đếm số lần preempt_disable()."
    Đúng: Cùng một biến preempt_count được chia thành 4 field (NMI/HARDIRQ/SOFTIRQ/PREEMPT — §03), và field SOFTIRQ tự nó có 2 ý nghĩa (đang serving vs chỉ đang disabled) tuỳ offset 1× hay 2×.

      SoftIRQ là gì?›
      Short: Cơ chế "bottom half" chạy trong atomic context, defer công việc từ hard IRQ.

      Tại sao cần SoftIRQ?›
      Short: Tránh giữ CPU quá lâu trong hard IRQ, giảm latency ngắt khác, cho phép công việc "nặng hơn ISR" nhưng vẫn không cần sleep.
      Deep: §01 — 3 rủi ro của việc làm hết việc trong ISR (miss ngắt, không sleep được, latency toàn hệ thống).

      Common trap: Nghĩ SoftIRQ "nhanh hơn" ISR — thực ra nó chỉ ít ràng buộc hơn về thời điểm chạy, không nhanh hơn về bản chất.
      SoftIRQ khác Hard IRQ thế nào?›
      Short: Hard IRQ là phản hồi trực tiếp phần cứng, không thể bị defer thêm; SoftIRQ là cơ chế defer, có thể bị trì hoãn tới tận ksoftirqd.
      Deep: Bảng so sánh context §01.

      Glossary

      SoftIRQ
      Cơ chế bottom-half atomic, 10 vector cố định, dispatch qua softirq_vec[] trong kernel/softirq.c.
      Hard IRQ
      Interrupt handler chạy trực tiếp khi phần cứng phát ngắt, atomic context nghiêm ngặt nhất.
      ksoftirqd/N
      Kernel thread per-CPU (N = chỉ số CPU), chạy softirq bị defer, dùng framework smp_hotplug_thread.
      Tasklet
      Cơ chế bottom-half dựng trên TASKLET_SOFTIRQ/HI_SOFTIRQ, tự serialize với chính nó qua TASKLET_STATE_RUN.
      NAPI
      New API — cơ chế poll-based cho network RX, dùng NET_RX_SOFTIRQ để lên lịch, có budget chống livelock.
      RCU_SOFTIRQ
      Vector cuối trong enum, dispatch callback RCU thật sự (rcu_core()), không phải nơi grace period hoàn thành.
      preempt_count
      Biến bitfield 4 phần (NMI/HARDIRQ/SOFTIRQ/PREEMPT) biểu diễn execution context hiện tại.
      local_bh_disable()
      Chặn SoftIRQ chạy trên CPU hiện tại bằng cách cộng SOFTIRQ_DISABLE_OFFSET vào preempt_count.
      irq_stat.__softirq_pending
      Bitmap 32-bit per-CPU lưu vector nào đang chờ xử lý trên CPU đó.
      invoke_softirq()
      Hàm quyết định chạy __do_softirq() trực tiếp hay wakeup_softirqd(), gọi từ irq_exit().
      netdev_budget
      Số work unit tối đa net_rx_action() xử lý trong 1 lượt softirq, mặc định 300.
      MAX_SOFTIRQ_RESTART
      Giới hạn 10 lần restart loop trong __do_softirq(), cơ chế chống starvation không phụ thuộc jiffies.
      CONFIG_KM_BIZHUB
      Patch vendor riêng của repo này, đặt ksoftirqd chạy SCHED_RR priority 256 — không có trong mainline.
