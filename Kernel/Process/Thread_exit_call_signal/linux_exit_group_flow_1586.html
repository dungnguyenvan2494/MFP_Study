    1.Executive Summary

    Overview

    Tài liệu này trace luồng một thread trong process đa luồng gọi exit()/_exit()/SYS_exit/SYS_exit_group cho tới khi parent thu hồi zombie, dựa trên source thật của repository Kernel/Src (arm64, Linux 5.10.y có vendor patch KM). Mọi khẳng định quan trọng có nhãn Confirmed from source (đọc trực tiếp trong source, kèm file:line), Confirmed by experiment (chạy chương trình kiểm chứng), Inference (suy luận từ source), VERSION-DEPENDENT (khác theo phiên bản) hoặc Chưa xác nhận.

    USERSPACE Userspace (glibc)

    1. exit(status)
    2. chạy atexit / on_exit handler
    3. flush & đóng stdio (_IO_cleanup)
    4. libc _exit(status)
    5. svc #0, x8 = 94 (__NR_exit_group)

    glibc reference Confirmed by experiment

    KERNEL Kernel (thread gọi)

    1. el0_svc → invoke_syscall
    2. __arm64_sys_exit_group → do_group_exit((code&0xff)<<8)
    3. lock sighand->siglock
    4. group_exit_code = code; flags = SIGNAL_GROUP_EXIT
    5. zap_other_threads(current)
    6. unlock; do_exit(code) – không chờ thread khác

    Confirmed from source kernel/exit.c:985

    SIGNAL Các thread còn lại

    1. bit SIGKILL vào t->pending (riêng từng thread)
    2. TIF_SIGPENDING + wake_up_state / kick_process (IPI)
    3. tự chạy tới ret_to_user → do_notify_resume
    4. do_signal → get_signal: signal_group_exit() = true
    5. goto fatal → do_group_exit(SIGKILL)
    6. do_exit(group_exit_code)

    Confirmed from source kernel/signal.c:2616

    SCHEDULER Kết thúc & parent

    1. mỗi thread: exit_mm/files/fs… (giảm refcount)
    2. exit_notify: non-leader tự reap, leader thành EXIT_ZOMBIE
    3. khi group rỗng + leader zombie → do_notify_parent → SIGCHLD
    4. parent wait4 → wait_task_zombie → release_task(leader)
    5. status = signal->group_exit_code

    Confirmed from source kernel/exit.c:1176

    Warning

    SIGKILL pending không có nghĩa task biến mất ngay lập tức. Task đang ở TASK_UNINTERRUPTIBLE có thể chưa thoát cho tới khi operation trong kernel hoàn thành. signal_wake_up_state() chỉ đánh thức task nếu p->state chứa TASK_INTERRUPTIBLE hoặc TASK_WAKEKILL (kernel/signal.c:776); task D-state thuần sẽ ngủ tiếp.

    Vendor patch trong repo này

    Kernel trong repo có patch CONFIG_THREADDRV ngay trong đường fatal của get_signal() (kernel/signal.c:2777–2864): nếu thread chết có comm bắt đầu bằng mfp000_hwQt/lui000, hoặc sau khi cờ static mfp000_hwQt_flg đã bật, thread sẽ down(&sem_mfp000_hwQt) (semaphore toàn cục, ngủ D-state), printk, có thể ghi SPI-flash và show_state() trước khi gọi do_group_exit(). Các thread bị zap đi qua đúng đường này nên bị tuần tự hóa. Xem mục Vendor patch.

    2.Mental Model cho người mới

    Overview
    Giải thích đơn giản
    • Process giống một công ty: có tài sản chung (bộ nhớ mm_struct, bảng file files_struct, thư mục làm việc fs_struct, bảng xử lý signal sighand_struct, hồ sơ chung signal_struct).
    • Thread là nhân viên; mỗi nhân viên có hồ sơ riêng task_struct, hộp thư riêng t->pending, stack riêng.
    • SYS_exit = một nhân viên tự nghỉ. Công ty vẫn hoạt động.
    • SYS_exit_group = lệnh đóng cửa cả công ty. Người ra lệnh ghi “công ty đang giải thể” vào hồ sơ chung (SIGNAL_GROUP_EXIT) cùng lý do (group_exit_code).
    • zap_other_threads() = bỏ một tờ “phải rời đi ngay” vào hộp thư riêng của từng nhân viên khác và gõ cửa (wakeup / IPI). Người ra lệnh không làm thủ tục nghỉ việc thay họ.
    • SIGKILL pending = thông báo bắt buộc đã được ghi nhận. Nhân viên đang “làm việc không thể bỏ dở” (D-state) chỉ đọc hộp thư khi xong việc.
    • Scheduler = người quyết định khi nào từng nhân viên được chạy để tự làm thủ tục.
    • do_exit() = thủ tục bàn giao của từng người: trả chìa khoá (giảm refcount), người cuối cùng thì khoá cửa (giải phóng tài nguyên chung).
    • waitpid() = công ty mẹ thu hồi hồ sơ cuối cùng (zombie của leader) và đọc lý do giải thể.

    Analogy chỉ giúp hình dung, không thay thế hành vi kỹ thuật trong source.

    • exit() có phải syscall? Không — exit() chạy hoàn toàn trong userspace cho tới khi gọi _exit(). glibc reference

    • atexit handler chạy ở đâu? Trong calling thread (Test 1: handler in tid của Thread A), trong khi các thread khác vẫn đang chạy song song. Confirmed by experiment

    28.Vì sao exit() trong process đa luồng có thể nguy hiểm

    UserspaceRace conditionExperiment
    glibc reference

    Toàn bộ mục này là hành vi glibc/userspace, không thuộc kernel. Thực nghiệm chạy trên glibc 2.39 (container), chưa chạy trên board.

    • atexit handler chạy trong calling thread trong khi các thread khác vẫn chạy (kernel chưa được gọi) → handler giải phóng/destroy object mà thread khác đang dùng ⇒ use-after-free, crash trong lúc thoát.
    • C++ static/global destructor (đăng ký qua __cxa_atexit) cũng chạy ở đó → thread khác dùng object đã hủy.
    • stdio lock: _IO_cleanup() flush mọi stream; nếu một thread khác đang giữ lock của stream (đang printf dài hoặc bị dừng giữa chừng) thì flush chờ hoặc bỏ qua tùy implementation.
    • malloc lock: handler gọi free/malloc khi thread khác đang giữ arena lock → chờ.
    • pthread cancellation: exit() không cancel thread khác; chỉ exit_group trong kernel mới dừng chúng.
    • Gọi exit() từ signal handler: exit() không async-signal-safe.
    • exit() sau fork() trong child của MT process: child chỉ có 1 thread (bản sao thread gọi fork) nhưng mọi mutex ở trạng thái lúc fork — mutex do thread khác giữ sẽ không bao giờ được unlock.

    37.Câu hỏi thường gặp (20 câu bắt buộc)

    Overview
    1. exit() có trực tiếp là syscall không?

    Không. exit() là hàm glibc: atexit → stdio cleanup → _exit() → syscall exit_group.

    glibc reference

    2. _exit() của glibc gọi SYS_exit hay SYS_exit_group?

    SYS_exit_group (NPTL). Kiểm chứng: strace và disassemble trên glibc 2.39. glibc trên board cần kiểm tra lại.

    Confirmed by experiment VERSION-DEPENDENT

    3. SYS_exit kết thúc một thread hay toàn process?

    Một thread (calling thread). Process chỉ kết thúc khi thread cuối cùng exit. kernel/exit.c:975.

    Confirmed from source Confirmed by experiment

    4. SYS_exit_group kết thúc thread khác thế nào?

    do_group_exit đặt SIGNAL_GROUP_EXIT + group_exit_code dưới siglock rồi zap_other_threads đặt SIGKILL vào t->pending và đánh thức; mỗi thread tự đi get_signal → do_group_exit → do_exit.

    Confirmed from source

    5. zap_other_threads() có thực sự gọi send_sig(SIGKILL) không?

    Không. sigaddset trực tiếp + signal_wake_up(t, 1). kernel/signal.c:1368–1369.

    Confirmed from source

    6. SIGKILL được đặt ở pending queue nào?

    t->pending (per-thread) của từng thread khác; shared_pending không đổi.

    Confirmed from source

    7. Thread bị zap có chạy signal handler không?

    Không. get_signal nhảy tới fatal trước khi tra sighand->action; SIGKILL cũng không thể có handler.

    Confirmed from source

    8. Thread nào gọi do_exit() cho target thread?

    Chính target thread, từ get_signal() (kernel/signal.c:2865) → do_group_exit → do_exit (kernel/exit.c:1008).

    Confirmed from source

    9. Calling thread có chờ các thread khác exit không?

    Không. do_group_exit gọi do_exit ngay sau khi unlock. (Khác với de_thread của execve, vốn chờ notify_count.)

    Confirmed from source

    10. Thread ở TASK_UNINTERRUPTIBLE có chết ngay không?

    Không. Nó không được wake; chết sau khi điều kiện chờ hoàn tất và nó tới get_signal.

    Confirmed from source

    11. Parent nhận exit status nào?

    wait_task_zombie: SIGNAL_GROUP_EXIT ? signal->group_exit_code : leader->exit_code (kernel/exit.c:1176).

    Confirmed from source

    12. Thread leader có bắt buộc exit cuối cùng không?

    Không. Leader có thể thoát trước, thành zombie; delay_group_leader ngăn reap tới khi group rỗng.

    Confirmed from source Confirmed by experiment

    13. Thread cuối cùng được xác định như thế nào?

    group_dead = atomic_dec_and_test(&signal->live) trong do_exit; và thread_group_empty(leader) trong exit_notify/release_task cho việc notify parent. Không có quick_threads trong 5.10.

    Confirmed from source

    14. Resource shared được giải phóng bằng reference count nào?

    mm_users (mmput), files->count, fs->users, nsproxy kref, sighand->count, signal->sigcnt, task usage/rcu_users.

    Confirmed from source

    15. kill -9 và zap_other_threads() khác nhau thế nào?

    kill -9: syscall, permission/LSM/audit, __send_signal, shared_pending, complete_signal, trace signal_generate, exit code 9 (killed). zap: nội bộ, không check, chỉ t->pending, exit code = group_exit_code (exited).

    Confirmed from source Confirmed by experiment

    16. Vì sao signal pending không có nghĩa task đã exit?

    Pending chỉ là bit; task phải được chạy, tới điểm kiểm tra (ret_to_user/get_signal), rồi tự chạy do_exit. D-state, freezer, ptrace, spinlock, patch THREADDRV đều có thể trì hoãn.

    Confirmed from source

    17. Vì sao gọi exit() sau fork trong process đa luồng có thể deadlock?

    Child chỉ có 1 thread nhưng mutex do thread khác giữ lúc fork vẫn ở trạng thái locked; atexit/stdio cần mutex đó → chờ mãi (Test 10).

    Confirmed by experiment glibc reference

    18. Vì sao child sau fork thường dùng _exit()?

    _exit chỉ là syscall exit_group, không chạy atexit/flush (tránh deadlock và tránh flush hai lần buffer stdio đã copy từ parent).

    glibc reference Confirmed by experiment

    19. Zombie đại diện cho thread hay process?

    Process (leader). Thread non-leader autoreap trong exit_notify; ngoại lệ thread bị ptrace.

    Confirmed from source

    20. Khi nào release_task() được gọi?

    (1) exit_notify khi autoreap; (2) wait_task_zombie khi parent reap; (3) release_task đệ quy cho leader khi thread cuối thấy leader zombie và parent ignore SIGCHLD; (4) de_thread release leader cũ; (5) reparent_leader khi reaper ignore SIGCHLD.

    Confirmed from source

    39.Kết luận

    Overview
    1. exit() → glibc cleanup → _exit() → SYS_exit_group. SYS_exit là thứ hoàn toàn khác: chỉ một thread. glibc reference Confirmed by experiment Confirmed from source
    2. do_group_exit() chốt một exit code duy nhất cho group dưới siglock; ai đến sau dùng lại code đó. Confirmed from source Confirmed by experiment
    3. zap_other_threads() không gửi signal theo nghĩa API: nó set bit SIGKILL trong t->pending, set TIF_SIGPENDING, đánh thức task ở trạng thái có INTERRUPTIBLE/WAKEKILL và IPI task đang chạy CPU khác. Confirmed from source
    4. Mỗi thread tự phát hiện trong get_signal() (signal_group_exit()), tự gọi do_group_exit() → do_exit(group_exit_code). Không ai chết “thay” ai. Confirmed from source
    5. D-state, freezer, ptrace, vòng lặp kernel không kiểm tra signal và patch THREADDRV có thể làm khoảng “pending → exit” kéo dài, thậm chí vô hạn. Confirmed from source Inference
    6. Resource shared được thả bằng refcount; signal_struct/sighand sống tới release/reap. Parent được báo đúng một lần khi group rỗng và leader zombie; status = group_exit_code. Confirmed from source
