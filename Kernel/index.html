0.1Executive Summary — năm câu hỏi lớn

❶ Vì sao
Đề xuất nâng kernel có từ 2018 (vá lỗ hổng, theo kịp Chromium/Node.js — [2SCD]) nhưng chỉ thành dự án năm 2023 khi chính phủ Mỹ đưa IPv6 Single-Stack vào điều kiện đấu thầu; chứng nhận IPv6 Ready Logo Phase 2/USGv6 bản mới đòi kernel ≥ v5 ([SCH] 全体 D5–D9). Ứng viên thu hẹp còn 5.10 và 6.1 theo thời gian hỗ trợ; chọn 5.10 (LTS, CIP tới 2031), bản mới nhất khi bắt đầu: 5.10.205 (chốt 2024-01-05).
❷ Phạm vi
Không chỉ kernel: Buildroot 2016.02 → 2023.11, gcc 5.2.1 → 11.4.0 (binutils 2.40, glibc 2.21 → 2.38), host gcc 13.2, RFS (6.378 mục), initramfs (409 mục, 32 .ko), toàn bộ firmware KM3/Subset build lại; Qt 5.3.0 và Xorg giữ version (chỉ build lại).
❸ Chiến lược
Không lấy kernel mới từ Marvell, không apply patch. Lấy upstream 5.10.205 sạch, trích "delta" Marvell (diff -rq 4.4.8 upstream vs Marvell: ~1.300 khác biệt → 746 mục đánh giá theo Level 0–3 → 252 cần merge) và delta KM, rồi merge + redesign thủ công. Chạy song song một "track" build 5.10.205 bằng toolchain cũ (cần a.patch) để tách lỗi source khỏi lỗi compiler; RFS và FW build song song với kernel.
❹ Diễn tiến
12/2023 dựng toolchain (3 lần: lỗi config → gcc 7.3.1 → gcc 11 vì gói mpd); 12/25–1/29 merge Marvell; 1/30–2/5 sửa 363 lỗi build (TC2016); 2/6 build OK bằng TC2023; merge KM + 76 lỗi link; 2/16–3/4 RFS & initramfs; 3–5/2024 debug boot 95 vấn đề; 11/2024 CT spec; 12/2024 rebase SparrowH + IT; 2/2025 FVT (9.302 TC), 3/2025 SVT và merge vào stream model.
❺ Kết quả (tại 2025-03-28)
Kernel 5.10.205 + MV + KM boot được, MFP chạy, đã qua CT (kernel 3.840 TC/195 NG), FVT đang chạy (58 bug: 28 đã sửa, 2 SSB), SVT 19 %, merge model đợt 1 từ 3/25, dự báo bug = 0 ngày 2025-06-04, GM model 5/2026. Chưa phải bản phát hành. Kế hoạch trễ ~6 tháng.

0.6Trả lời trực tiếp 10 câu hỏi

1. Tại sao cần nâng Linux Kernel?

Trực tiếp: đáp ứng IPv6 Single-Stack (yêu cầu đấu thầu chính phủ Mỹ; IPv6 Ready Logo Phase 2, USGv6) — chuẩn mới cần kernel ≥ 5 ([SCH] 全体 D5–D7; [SRATT] 開発背景). Kèm theo: bảo mật (kernel/thư viện còn lỗ hổng, platform dùng lâu không nâng được — [SCH] D8–D9; [2SCD] C23–C24), theo kịp Chromium/Node.js ([2SCD] C10), và xây know-how nâng định kỳ (D21). 5.10 được chọn vì LTS/CIP tới 2031.

2. Kernel cũ và mới khác nhau thế nào?

4.4.8 = kernel Marvell LSP (armada-17.02) + KM, build bằng Linaro gcc 5.2.1; 5.10.205 = linux-stable + merge lại Marvell/KM, build bằng gcc 11.4.0. Khác biệt gây việc: API nội bộ (inode lock, generic_write_sync, clock flags, dw_pcie, syscall wrapper pt_regs, bootmem→memblock), hành vi (irqdomain, gpiochip một thiết bị cho 576 GPIO, kernel image trong vmalloc, TEXT_OFFSET=0, %p hash), cấu trúc thư mục (pci/host→controller, mv88e6xxx/, mtd/parsers), DT binding (syscon, ap80x.dtsi). Image ban đầu 30,6 MB vs 9,8 MB (MV config).

3. Ngoài kernel phải nâng gì?

Buildroot 2023.11; cross toolchain gcc 11.4.0/binutils 2.40/glibc 2.38/gdb 13.2; host gcc 13.2; RFS (157 package đổi version, OpenSSL hệ thống về 1.0.2u); initramfs (glibc + 32 .ko); KM3/Subset và mọi module cung cấp binary (Xorg, Qt, glibc, postgreSQL, haveged, iw…); Qt/Xorg build lại, giữ version; driver ngoài (Realtek Wi-Fi, Vivante GPU, Lineo hibernation) cần kiểm.

4. Từ source đến kernel Image diễn ra thế nào?

Trên host x86-64 (AWS): git clone linux-stable → git checkout (đã dùng origin/linux-5.10.y; tái lập chính xác nên dùng tag v5.10.205) → make ARCH=arm64 CROSS_COMPILE=s800-linux- defconfig (hoặc config MFP) → Kconfig sinh .config → make … -j4 cross-compile → vmlinux → objcopy → arch/arm64/boot/Image; make dtbs → emu800.dtb; make modules → .ko (copy vào initramfs). Với toolchain cũ phải áp a.patch. Chi tiết: Chương 07.

5. Port Marvell và KM customization thế nào?

Xác định base Marvell (commit đầu Diff C trong FUM git) → diff -rq với upstream 4.4.8 → phân loại Add new/Modify/Delete, kiểm "có trong 5.10.205?", lọc theo danh sách 1.954 file thực sự được build → Level 0–3 (Level 3: git log -p tìm commit đổi API) → merge/redesign trên 5.10.205 → build TC2016 rồi TC2023 → checklist merge sót 150 mục (FPT↔Sky). KM: lấy Diff C/D/Z, merge lên bản MV theo 5 bước (không xung đột / cần redesign / xung đột với file FPT / KM xoá file / KM thêm file), rồi recheck 502 điểm theo 5 góc nhìn (2025). Chi tiết: 08, 09.

6. Vấn đề kỹ thuật khó nhất?

(a) Merge Level 3 ở core (mm page_alloc — cuối cùng phải bỏ customization Marvell; irqdomain; printk); (b) boot không có log (console/UART/DT); (c) thay đổi hành vi upstream không thấy qua diff (TEXT_OFFSET, gpiochip, syscall wrapper, RT rwsem); (d) quy mô lỗi FW với gcc 11 (~hàng chục/hàng trăm nghìn) và rủi ro workaround -fpermissive; (e) hardening PIE/RELRO làm lộ bug runtime; (f) tương tác OSS khi rebase (OpenSSL 3, Chromium glibc).

7. Lỗi build/boot quan trọng và cách giải?

Build: MIGRATE_HIGHATOMIC (merge dở 4 commit) → về upstream; phy_get_mode 172 lỗi từ 1 header; API fs/btrfs/clk/amba; link sys_getpid, __inval_cache_range, arch_hibernation_header_save, QSPI, pcie-msb0125 (Makefile/thư mục); libmpfr.so.6 (host).

Boot: No.1 offset 0x80000; No.3–6/17/65 console; No.9/14–18/24 DT AP806; No.11 irqdomain; No.12/34/58 GPIO 576; No.7/44 PCIe dw_pcie; No.43/75 KM semaphore pt_regs; No.64 pipe treo (RT_RWSEM=n tạm); No.69 vfs_read sai đối số; No.91 glibc stack 16 KB. Bảng đầy đủ: 11, 15.

8. Kernel mới tích hợp vào MFP Firmware thế nào?

Image + DTB + initramfs (32 .ko từ kernel mới + glibc mới) + RFS mới (merge 3 điểm, mkrfs → RFS1/2/3.img) + KM3/Subset build bằng cùng toolchain → gói FW cập nhật qua USB_FW/NW_FW (Subset cũ không khởi động được FW mới "như dự kiến" ⇒ cần Subset mới). Các module binary-provided build lại và giao BSP. Xem 14, sơ đồ tích hợp.

9. Kết quả thực tế cuối cùng?

Đổi nền source kernel sang một version khác.

Upstream = kernel.org (linux-stable); vendor = upstream + patch của nhà cung cấp SoC.

Vendor kernel (Marvell LSP) hỗ trợ IP riêng của SoC nhưng thường dừng ở một version.

Nhánh kernel được bảo trì dài hạn.

Sơ đồ phụ thuộc đầy đủ (Host GCC → Buildroot → toolchain → kernel / FW / Qt → RFS / initramfs → firmware → phần cứng) được vẽ tách build-time và runtime tại Chương 20. Dưới đây là câu trả lời cho từng câu hỏi của nghiên cứu §4.1:

Kernel cần gì để build?

Source 5.10.205 + MV + KM, toolchain s800-linux- (gcc/as/ld), .config (defconfig hoặc config đã merge), host tools (make, bison, flex… theo Documentation/process/changes.rst — [KSTEP] mục 3).

Buildroot tạo ra gì?

(1) cross toolchain trong output/host, (2) RFS trong output/target và output/images/rootfs.tar ([BRB] Sheet1 A15–A16: "rfs: output/targetが相当すると思われる"; [BRLOG] dòng cuối sinh rootfs.tar.bz2).

Toolchain dùng thế nào?

Giải nén vào /opt/marvell/s800/toolchain; mọi build gọi CROSS_COMPILE=s800-linux- ([BRDIFF] BuildQT D8–D13; [KSTEP]).

Kernel image phụ thuộc gì?

Compiler/binutils (a.patch chứng minh), .config, DTS (boot No.4), offset nạp của U-Boot (boot No.1).

RFS liên hệ kernel?

RFS (userspace) gọi syscall của kernel; một số tool phụ thuộc đường dẫn/version kernel (FVT bug arping đổi /sbin→/usr/sbin [SRATT] FVT不具合振り返り H5).

Initramfs?

RFS nhỏ nạp sớm, chứa .ko USB/Wi-Fi/FAX/GPU để mount phân vùng thật (xem Ch.13).

Qt / userspace?

Qt/Xorg build bằng toolchain mới nhưng giữ version để không phải sửa KM3.

MFP FW lấy gì?

Kernel + DTB + initramfs + RFS (+ cramfs MFP1..4.img gắn ở /km… theo fstab) + KM3/Subset ([FMS] RFS_Comment_Ascii/rfs/after/etc/fstab).

12.1RFS là gì trong MFP này

Root File System (RFS)
Cây thư mục userspace (/bin, /sbin, /etc, /lib, /usr…) chứa lệnh, thư viện, file cấu hình.

([2SCD] C94–C102; [RFS] 用語 C4). RFS của IT6 nằm ở SVN SVN_Kernel_IT6/trunk/RFS/R-S800/rfs/ ([RFS] 概要 H8).

Vì sao quan trọngRFS chứa glibc và mọi thư viện — đổi toolchain là đổi ABI của mọi app.

RFS gồm 3 lớp:

  1. Phần do Buildroot sinhbusybox, glibc, openssl, alsa, cups, Xorg…
  2. KM customizationFile ASCII (/etc/fstab, inittab, profile, passwd…) và thư mục riêng (/ata01 HDD dosFS, /ata03 tài nguyên Emperor, /ata04 âm thanh/video, /ata0a SSD, /mfp USB phân vùng 2 chứa firmware tích hợp — [RFS] Other A5–B11).
  3. Binary do module khác cung cấppostgreSQL, Qt, Xorg, sbin/C, haveged, iw, libnvaccess.so… ([HO] List of binary provided modules).

Ảnh RFS đóng gói bằng mkrfs.sh thành RFS1.img (trừ /chromium, /usr), RFS2.img (/chromium), RFS3.img (/usr) và RFS_LIST ([RFS] Other C11).

18.2Giải thích cho người mới — gắn với ví dụ của chính dự án

Kernel Version Up khác Kernel Rebuild?

Rebuild = build lại cùng source (vd đổi config/compiler). Version Up = đổi nền source sang version khác ⇒ API nội bộ đổi, phải mang customization theo.

Ví dụ dự ánBuild 4.4.8 bằng gcc mới là rebuild; 4.4.8 → 5.10.205 là version up.
Version Up khác Porting?

Porting = đưa kernel/driver lên phần cứng mới; Version Up = cùng phần cứng, đổi version kernel. Dự án này là Version Up nhưng chứa nhiều việc "port lại" customization.

Ví dụ dự ángpio-pxa QZ "MergeAndRedesign".
Vendor kernel vs upstream kernel?

Upstream = kernel.org (linux-stable); vendor = upstream + patch của nhà cung cấp SoC (Marvell LSP) để hỗ trợ IP riêng, thường dừng ở một version.

Ví dụ dự án4.4.8 armada-17.02 vs linux-stable 5.10.205.
Vì sao driver cũ không build được trên kernel mới?

Kernel không có ABI/API nội bộ ổn định: hàm đổi chữ ký, struct đổi trường, file dời chỗ, hằng bị xoá.

Ví dụ dự áni_mutex, generic_write_sync, CLK_IS_ROOT, pcie_port→dw_pcie.
Vì sao compile OK chưa chắc boot?

Boot phụ thuộc bootloader, DTB, thứ tự probe, ngắt, clock — không kiểm được lúc compile.

Ví dụ dự ánNo.1 TEXT_OFFSET, No.11 IRQ, No.6 console.
Vì sao boot OK chưa chắc sản phẩm đúng?

Userspace/FW có hành vi riêng phụ thuộc libc, đường dẫn, timing.

Ví dụ dự ánFVT: arping path, Node.js PIE, FIPS binding.
Vì sao phải nâng Buildroot & toolchain?

RFS sinh bởi Buildroot; Buildroot mới đòi gcc mới; gói (mpd) đòi gcc ≥ 8.

Ví dụ dự án[BRDIFF] N176.
Vì sao kiểm RFS & initramfs?

Chúng chứa glibc + .ko gắn chặt với kernel/toolchain.

Ví dụ dự án32 .ko; glibc stack size.
Vì sao kiểm ABI & binary module?

Binary build bằng toolchain/glibc cũ có thể dùng lệnh/ký hiệu không còn.

Ví dụ dự ángrityinte undefined instruction; ENGINE_init OpenSSL 3.
Vì sao Device Tree gây lỗi boot?

Driver mới đòi binding mới (compatible, syscon cha, #clock-cells, #pinctrl-cells); node sai ⇒ driver không probe hoặc đổi thứ tự thiết bị.

Ví dụ dự ánNo.9, 15, 17, 18, 24.
Vì sao phải regression test?

20.1Tích hợp hệ thống — build-time và runtime

READ CAREFULLYKhông nhầm build dependency với runtime dependency

Nửa trên là build-time (artifact nào được tạo từ đâu, trên build server). Nửa dưới là runtime (thứ tự chạy trên MFP). Mũi tên đứt nối hai nửa: gói firmware được cài lên máy.

Gốc build-time

Toolchain gcc 11.4.0 (s800-linux-) là gốc của: Kernel Image + emu800.dtb, kernel modules (.ko), glibc 2.38 (+ KM min stack), Qt 5.3.0/Xorg (ATF), KM3 main FW/Subset, binary-provided modules (postgreSQL, haveged, iw…).

Điểm hội tụ

glibc + Qt + binary → RFS (RFS1/2/3.img); .ko + glibc → initramfs (busybox + glibc + 32 .ko + /init); Kernel + initramfs + RFS + KM3 → MFP firmware package (USB_FW / NW_FW update).

Runtime

MFP S800 (AP806 + Quartz + A800/PS-CPU/LPPP): U-Boot → kernel + DTB → driver built-in → initramfs /init → RFS init → libraries → MFP app (KM3, mfpapp, Chromium).
