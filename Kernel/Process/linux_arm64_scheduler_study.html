PDF chia thành 6 phần: 7.1 Scheduling Policy, 7.2 The Scheduling Algorithm, 7.3 Data Structures, 7.4 Functions Used by the Scheduler, 7.5 Runqueue Balancing in Multiprocessor Systems, 7.6 System Calls Related to Scheduling. Tóm tắt từng phần — đây là "concept" sẽ được map sang kernel hiện đại ở Chương 04.

7.1 — Scheduling Policy

  • Time-sharing: CPU chia "quantum" cho từng runnable process; timer interrupt làm việc chia sẻ này trong suốt với chương trình.
  • 3 lớp process: interactive (cần phản hồi 50–150ms), batch (không cần tương tác, bị phạt), real-time (yêu cầu độ trễ chặt, không bao giờ bị blocked bởi process priority thấp hơn).
  • Process Preemption: khi một process vào TASK_RUNNING, kernel so priority với current; nếu cao hơn → set TIF_NEED_RESCHED trên current → scheduler chạy khi timer interrupt handler kết thúc. Process bị preempt vẫn ở TASK_RUNNING, chỉ không giữ CPU nữa.
  • Quantum duration là đánh đổi: ngắn quá → overhead process-switch cao; dài quá → hệ thống "giật", nhưng lý thuyết không ảnh hưởng nhiều tới interactive process vì chúng vẫn preempt được batch process ngay lập tức nhờ priority cao hơn.

7.2 — The Scheduling Algorithm (O(1))

  • 3 scheduling classes: SCHED_FIFO, SCHED_RR (real-time), SCHED_NORMAL (conventional).
  • Static priority: 100 (cao nhất) → 139 (thấp nhất), đặt qua nice()/setpriority(). Base time quantum tính từ static priority: (140 − static_prio) × 20ms nếu <120, × 5ms nếu ≥120.
  • Dynamic priority = max(100, min(static_prio − bonus + 5, 139)); bonus (0–10) phụ thuộc average sleep time — process ngủ nhiều (interactive) được bonus dương (ưu tiên tăng), process CPU-bound liên tục được bonus âm.
  • Active / Expired arrays: mỗi runqueue giữ 2 tập prio_array_t (140 danh sách liên kết theo priority + bitmap). Process hết quantum bị chuyển từ active sang expired; khi active rỗng, đổi vai active ↔ expired bằng cách hoán đổi 2 con trỏ.

7.3 — Data Structures

  • struct runqueue per-CPU (qua this_rq()/cpu_rq(n)): active, expired, arrays[2], curr, idle, nr_running, sd (scheduling domain), migration_thread...
  • task_struct scheduling fields: thread_info->flags (chứa TIF_NEED_RESCHED), state, prio, static_prio, array (trỏ vào active hoặc expired), sleep_avg, time_slice, policy, cpus_allowed.

7.4 — Functions Used by the Scheduler

  • scheduler_tick() — mỗi tick: cập nhật time_slice; nếu hết quantum → refill + chuyển sang expired (batch) hoặc để lại active (interactive nếu chưa starve) + set TIF_NEED_RESCHED.
  • try_to_wake_up() — đổi state → TASK_RUNNING, chọn CPU đích (heuristic cache-affinity), gọi activate_task() → recalc_task_prio() tính lại dynamic priority từ sleep time, rồi resched_task() nếu priority cao hơn curr.
  • schedule() — hàm trung tâm: disable preempt → xử lý trạng thái prev (dequeue nếu ngủ) → nếu runqueue rỗng thì đổi vai active/expired → sched_find_first_bit() tìm priority list không rỗng đầu tiên → lấy process đầu danh sách làm next → context_switch().
  • load_balance() — cân bằng runqueue đa xử lý dựa trên scheduling domains phân cấp.

7.5 — Runqueue Balancing (SMP)

Giới thiệu scheduling domains (từ kernel 2.6.7): cây phân cấp các nhóm CPU, mỗi domain có nhiều sched_group; rebalance_tick() gọi load_balance() theo domain với tần suất khác nhau (thường xuyên hơn khi CPU idle); move_tasks()/can_migrate_task() di chuyển task từ runqueue bận nhất sang runqueue local.

7.6 — System Calls Related to Scheduling

nice(), getpriority()/setpriority(), sched_setscheduler()/sched_getscheduler(), sched_setparam()/sched_getparam(), sched_yield(), sched_get_priority_min/max(), sched_rr_get_interval(), sched_setaffinity()/sched_getaffinity().

💡 Vì sao active/expired array bị loại bỏ
O(1) scheduler đúng như tên gọi — chọn task trong O(1) bất kể số task runnable — nhưng phải trả giá bằng một cỗ máy heuristic phức tạp (sleep_avg, "interactive delta", "starvation" check trên expired array) để đoán process nào là interactive. Heuristic này khét tiếng khó tune và có nhiều pathological case (ví dụ X server bị đối xử tệ). CFS (Ingo Molnar, 2.6.23, 2007) bỏ hẳn việc "đoán loại process": chọn thẳng task có vruntime nhỏ nhất trong rbtree — O(log n) thay vì O(1), nhưng với n vài trăm task, log n ~ 8-9 phép so sánh, không đáng kể; đổi lại thuật toán đơn giản, dự đoán được, không cần bảng heuristic nào.

ARM64 Scheduler — Big Picture

🔧 ARM64 NOTE — 3 điểm khác x86 mà PDF không nhắc tới (vì PDF viết cho x86)
1) x86 dùng PIT/APIC-timer + interrupt vector cố định; ARM64 dùng ARM Generic Timer (thanh ghi hệ thống CNTV_CTL_EL0/CNTV_TVAL_EL0) phát PPI (Private Peripheral Interrupt) qua GIC (Generic Interrupt Controller), không phải dây IRQ0 kiểu x86 cũ.
2) x86 context switch dùng TSS + __switch_to_asm đổi ESP/segment; ARM64 dùng cpu_switch_to() — một hàm assembly tuân theo AAPCS64 calling convention, chỉ lưu callee-saved registers (x19-x28, fp, sp, lr) — xem c19.
3) x86 current đọc qua per-CPU segment (%gs); ARM64 "chiếm dụng" thanh ghi hệ thống SP_EL0 (vô dụng ở EL1) để giữ thẳng con trỏ task_struct* — xem c20.

struct rq — runqueue per-CPU

kernel/sched/sched.h:904

rq là gì? Mỗi CPU logic có đúng một struct rq — nó gom mọi trạng thái scheduler cục bộ của CPU đó: task đang chạy, 3 sub-runqueue (CFS/RT/DL), clock, load, scheduling domain. Mỗi CPU có rq riêng — đây là lý do CFS scale tốt theo số CPU: chọn task tiếp theo trên CPU0 không cần khoá rq của CPU1.

Lưu ở đâu / per-CPU thế nào? Khai báo DEFINE_PER_CPU_SHARED_ALIGNED(struct rq, runqueues) trong kernel/sched/core.c — dùng cơ chế per-CPU variable chung của kernel (không phải cái gì ARM64-riêng): mỗi CPU có bản sao vật lý riêng trong vùng bộ nhớ per-CPU; cpu_rq(n) = &per_cpu(runqueues, n), this_rq() = rq của CPU đang chạy code hiện tại. CPU0 và CPU1 có rq khác nhau đơn giản vì chúng là 2 bản sao khác nhau của cùng một vùng nhớ per-CPU — không có "chia sẻ" nào giữa chúng trừ khi code chủ động lock rq2 từ CPU0 (load balancing).

💡 Tại sao IRQ handler không gọi thẳng schedule()?
IRQ handler chạy với preempt_count += HARDIRQ_OFFSET (qua irq_enter()) — gọi schedule() trong trạng thái này sẽ BUG() (kernel có __might_sleep() assertion). Lý do sâu hơn: IRQ handler có thể đang chạy trên IRQ stack riêng (không phải kernel stack của task bị ngắt), và có thể đang giữ spinlock của driver — đổi task giữa chừng sẽ làm hỏng bất biến "process context mới được ngủ/switch". Vì vậy kernel tách làm 2 bước: (1) handler chỉ set cờ TIF_NEED_RESCHED, (2) schedule() thật sự chạy ở safe point sau khi handler kết thúc — xem c15.
🔧 ARM64 NOTE — "safe point" nằm ở đâu
Trên ARM64: nếu IRQ ngắt task đang ở EL0 (userspace), safe point luôn là ret_to_user (entry.S) — luôn luôn kiểm tra TIF_NEED_RESCHED, bất kể CONFIG_PREEMPT. Nếu IRQ ngắt lúc đang ở EL1 (giữa syscall khác, hoặc kernel code), safe point chỉ tồn tại nếu CONFIG_PREEMPT=y và preempt_count()==0 lúc đó — qua arm64_preempt_schedule_irq() → preempt_schedule_irq(). Board này build CONFIG_PREEMPT=y, CONFIG_PREEMPTION=y nên có preemption đầy đủ ở cả hai trường hợp.

Kernel Thread vs User Process — mm / active_mm

Ví dụ kernel thread trên board này: kworker/*, ksoftirqd/*, idle task (swapper/0, swapper/1), migration/stop task per-CPU.

💡 mm=NULL / active_mm — vẫn còn dùng trong 5.10.241
Kernel thread có task_struct->mm == NULL (không sở hữu address space riêng). Khi được chọn chạy, context_switch() (xem c18) KHÔNG đổi TTBR0 — nó "mượn" active_mm của task vừa chạy trước đó (enter_lazy_tlb): next->active_mm = prev->active_mm; mmgrab(...). Vì kernel thread chỉ chạy code kernel (nửa trên của address space, ánh xạ giống nhau ở mọi process), việc "mượn" TTBR0 cũ không sai — chỉ đơn giản không cần đổi, tiết kiệm hẳn phần MMU của context switch (xem chi tiết chi phí ở c21). 
user process A (mm=MM_A)  →  kernel thread K (mm=NULL, active_mm=MM_A mượn từ A)
     →  user process B (mm=MM_B)

Switch A→K:  switch_mm KHÔNG chạy (K->mm==NULL) → TTBR0 VẪN LÀ MM_A → 0 chi phí MMU
Switch K→B:  switch_mm CHẠY (B->mm=MM_B != K->active_mm=MM_A) → cpu_do_switch_mm bình thường

idle_sched_class: idle task (swapper/N) chạy trong cpu_startup_entry() (kernel/sched/idle.c:397) → vòng lặp do_idle() gọi schedule_idle() (:334) mỗi khi need_resched() — đây là task luôn tồn tại trên mỗi rq, đảm bảo pick_next_task() luôn có kết quả kể cả khi nr_running==0 (idle_sched_class luôn là "backstop" cuối cùng trong for_each_class).

Ghi chú (INFERENCE, chưa verify glibc source trong phiên này): theo hành vi ABI Linux đã biết, glibc trên AArch64 hiện thực nice() bằng cách gọi getpriority()/setpriority() ở userspace thay vì một syscall trực tiếp.

ARM64 SVC Entry — ví dụ sched_yield()

Trace tổng quát (giống hệt mọi syscall khác, xem thêm c22 cho phần exception entry): userspace đặt x8 = 124 (số hiệu sched_yield), svc #0 → HW nhảy VBAR_EL1+0x400 (el0_sync, khác el0_irq ở c22 vì đây là synchronous exception, không phải IRQ) → el0_sync đọc ESR_EL1.EC == 0x15 (SVC64) → el0_svc → el0_svc_common() → invoke_syscall() → sys_call_table[124](regs) → SYSCALL_DEFINE0(sched_yield) (core.c:6155).

💡 sched_yield() là ví dụ preemption VOLUNTARY (xem c14) tinh khiết nhất
Khác timer tick (involuntary, chỉ set cờ rồi đợi safe point) hay wakeup (đánh thức task khác), sched_yield() gọi schedule() trực tiếp trong thân syscall — vì đang ở process context với IRQ đã bật lại và không giữ lock nào, đây LÀ safe point, không cần qua cơ chế TIF_NEED_RESCHED.

Runtime Tracing & Debugging — quan sát scheduler thật

Hai công cụ có sẵn trong mọi kernel bật CONFIG_FTRACE/CONFIG_SCHEDSTATS (không cần cấu hình thêm nếu đã bật):

                           # nr_running, load, min_vruntime, từng task + vruntime
cat /proc/schedstat        # thống kê load-balance theo domain: lb_count, lb_balanced,
                             # lb_imbalance — đối chiếu với chương 28
🔬 ftrace — sched events
cd /sys/kernel/debug/tracing
echo 1 > events/sched/sched_switch/enable
echo 1 > events/sched/sched_wakeup/enable
echo 1 > events/sched/sched_wakeup_new/enable
echo 1 > events/sched/sched_process_fork/enable
echo 1 > events/sched/sched_process_exit/enable
echo 1 > tracing_on
cat trace     # mỗi dòng: sched_switch: prev_comm=A prev_pid=.. prev_state=..
              #            ==> next_comm=B next_pid=..

Thực nghiệm đối chiếu source ↔ runtime: viết 2 task (Task A sleep trên pipe rỗng, Task B write vào pipe để đánh thức A), bật sched_switch trace, so khớp thứ tự sự kiện với call chain ở Chương 25 — mỗi dòng sched_switch trong trace tương ứng đúng 1 lần context_switch() (c18) chạy xong.

📌 perf / trace-cmd / bpftrace
perf sched record + perf sched latency cho thống kê độ trễ scheduling per-task; trace-cmd record -e sched là wrapper tiện hơn cho ftrace ở trên; nếu kernel bật CONFIG_BPF, bpftrace -e 'tracepoint:sched:sched_switch { printf("%s -> %s\n", args->prev_comm, args->next_comm); }' cho cùng thông tin real-time không cần ghi file trace.
⚠️ WARNING — build kernel debug cho QEMU/board thật
Để dùng gdb/kgdb soi trực tiếp cấu trúc (struct rq, struct task_struct) cần build kernel với CONFIG_DEBUG_INFO=y (và lý tưởng CONFIG_GDB_SCRIPTS=y để dùng script vmlinux-gdb.py có sẵn — cho phép lx-ps, lx-dmesg ngay trong gdb). Board S800 thật cắm UART có thể cấu hình kgdboc=ttyS0,115200 trên cmdline; với QEMU -M virt -cpu cortex-a72 -kernel Image -append "console=ttyAMA0" + -s -S để gdb attach qua cổng 1234 từ lúc CPU reset — hữu ích để đặt breakpoint ngay tại cpu_switch_to và xem thanh ghi đổi theo từng bước ở Chương 19.

Mental Model tổng hợp

💡 5 câu trả lời cốt lõi (đọc lại nếu quên toàn bộ tài liệu)
1) Scheduler chọn task kế tiếp bằng cách nào? Duyệt 5 lớp theo thứ tự ưu tiên tuyệt đối cố định (stop/dl/rt/fair/idle); trong CFS, luôn lấy leftmost của rbtree theo vruntime.
2) Ai kích hoạt việc đổi task? KHÔNG BAO GIỜ trực tiếp từ IRQ handler — luôn set TIF_NEED_RESCHED rồi đợi safe point (ret_to_user, preempt_enable, hoặc voluntary schedule()).
3) current là gì? Nội dung thanh ghi SP_EL0 — không phải biến toàn cục, không cần khoá, mỗi CPU tự nhiên khác nhau.
4) Context switch thật sự đổi cái gì? 3 tầng tách biệt: 13 thanh ghi callee-saved (cpu_switch_to), con trỏ current (msr sp_el0), và address space (switch_mm/TTBR0+ASID) — không tầng nào đụng thanh ghi user (nằm an toàn trong pt_regs).
5) PDF và kernel hiện đại khác nhau ở đâu nhất? Toàn bộ cỗ máy heuristic "đoán interactive/batch" (active/expired array, sleep_avg, recalc_task_prio) của O(1) scheduler đã bị thay bằng nguyên tắc đơn giản: luôn chạy task có vruntime nhỏ nhất.
