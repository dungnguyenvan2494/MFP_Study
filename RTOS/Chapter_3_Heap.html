EXPLANATION

1 & 2. RTOS là gì, khác bare-metal ra sao?

RTOS (Real-Time Operating System) là một hệ điều hành nhỏ, chuyên dụng, chia sẻ một CPU cho nhiều "luồng công việc" (task) sao cho việc chuyển đổi giữa chúng xảy ra trong thời gian có thể dự đoán được. Một camera IP (như CV25) cần đồng thời đọc cảm biến ảnh, encode video, nghe lệnh network, nháy LED — RTOS giúp viết mỗi việc thành một task riêng, rồi tự lo việc luân phiên chạy chúng.

Bare-metalRTOS
Cấu trúc code1 vòng lặp while(1) xử lý tuần tựNhiều task độc lập, RTOS lo lịch chạy

Bộ nhớTự cấp phát tĩnhCó thể cấp phát động (heap) hoặc tĩnh
EXPLANATION

3–7. Task, Scheduler, Task Stack, TCB, Kernel Object

Task = một hàm C chạy độc lập, có stack riêng, được RTOS coi như một luồng thực thi ảo. Scheduler = lõi RTOS quyết định "task nào chạy trên CPU lúc này", được gọi định kỳ qua tick interrupt, khi task chủ động nhường CPU, hoặc khi ISR đánh thức một task priority cao hơn.

Task stack: mỗi task cần vùng nhớ riêng lưu biến local, địa chỉ trả về, và toàn bộ ngữ cảnh CPU khi bị tạm dừng giữa chừng — nếu dùng chung 1 stack như bare-metal, các task sẽ ghi đè lẫn nhau.

TCB (Task Control Block): struct mà RTOS dùng để "ghi nhớ mọi thứ về một task" — con trỏ đỉnh stack, priority, trạng thái... Mỗi lần gọi xTaskCreate(), RTOS cấp phát cho 2 thứ: TCB + stack.

Kernel object: các cấu trúc RTOS quản lý để task/ISR đồng bộ — queue, semaphore, mutex, event group, timer; task cũng là một kernel object. Mỗi object cần bộ nhớ riêng để lưu trạng thái.

EXPLANATION

8–10. Vì sao cần cấp RAM cho task? Vùng nhớ nào?

TCB, stack, queue buffer đều là dữ liệu — phải nằm ở đâu đó trong RAM. RTOS có 2 lựa chọn: cấp phát tĩnh (biến global/static, biết trước lúc compile) hoặc động (lúc runtime, "xin" một vùng RAM). Khi tạo 1 task, cần ít nhất TCB và Stack.

Phân biệt vùng nhớ
FLASH (không đổi lúc runtime) +---- Code (.text) +---- Read-only data (.rodata) RAM (thay đổi lúc runtime) +---- Global/static data (.data, .bss) +---- Heap <- vùng cấp phát động +---- Stack <- ngữ cảnh hàm/task +---- Free RAM

💡 CONCEPT — 4 khái niệm cốt lõi

Deterministic: một thao tác luôn mất cùng khoảng thời gian (hoặc có giới hạn trên biết trước), bất kể trạng thái hệ thống — sống còn với hệ real-time có deadline. Fragmentation: tổng bộ nhớ trống đủ, nhưng bị chia rải rác thành nhiều mảnh không liền kề, không mảnh nào đủ lớn cho yêu cầu mới. Memory exhaustion: hết RAM để cấp phát thêm — dễ xảy ra hơn nhiều trên MCU (vài trăm KB) so với PC. Execution time của mọi API (kể cả cấp phát) ảnh hưởng trực tiếp tới độ trễ phản hồi hệ thống.

LESSON 02

3.1 Introduction

PDF trang 1–2 · Vì sao FreeRTOS không dùng thẳng malloc()/free() chuẩn.

SOURCE — trang 1

Scope & Prerequisites

Chương này giả định người đọc đã quen: các giai đoạn compile/link của C project, khái niệm stack/heap, hàm chuẩn malloc()/free(). Chapter 3 sẽ nói về: (1) khi nào FreeRTOS cấp RAM, (2) 5 sơ đồ cấp phát bộ nhớ ví dụ, (3) nên chọn sơ đồ nào.

SOURCE — trang 1

Switching Between Static & Dynamic

Kernel object (task, queue, semaphore, event group) có thể tạo bằng bộ nhớ cấp phát tĩnh hoặc động. API tạo bằng static chỉ khả dụng khi configSUPPORT_STATIC_ALLOCATION = 1. API tạo bằng dynamic chỉ khả dụng khi configSUPPORT_DYNAMIC_ALLOCATION là 1 hoặc để trống (undefined). Cả hai có thể cùng bật.

SOURCE — trang 1–2

Vì sao malloc()/free() chuẩn có thể không phù hợp?

  • Không phải lúc nào cũng có sẵn trên hệ thống nhúng nhỏ.
  • Cài đặt có thể khá lớn, tốn code space.
  • Hiếm khi thread-safe.
  • Không deterministic — thời gian thực thi thay đổi giữa các lần gọi.
  • Có thể suffer fragmentation.
  • Có thể làm phức tạp cấu hình linker.
  • Có thể gây lỗi khó debug nếu heap "tràn" vào vùng nhớ biến khác.
💡 EXPLANATION

Đây là lý do FreeRTOS tách hẳn allocation ra khỏi core kernel — gọi là portable layer. FreeRTOS gọi pvPortMalloc()/vPortFree() thay vì malloc()/free() — cùng prototype, nhưng bạn chọn được cách hiện thực (hoặc tự viết) phù hợp với MCU của mình.

SOURCE — trang 2

Options for Dynamic Memory Allocation

Phiên bản FreeRTOS cũ dùng "memory pools" (đã bị loại bỏ vì lãng phí RAM trên hệ rất nhỏ). Ngày nay FreeRTOS coi allocation là một phần của portable layer, không phải core codebase — vì mỗi hệ nhúng có yêu cầu allocation/timing khác nhau. FreeRTOS cung cấp 5 cách hiện thực ví dụ: heap_1.c, heap_2.c, heap_3.c, heap_4.c, heap_5.c, nằm trong FreeRTOS/Source/portable/MemMang.

Kiến trúc Portable Layer
Application code │ xTaskCreate(), xQueueCreate() ... ▼ FreeRTOS kernel (core codebase) │ cần RAM cho TCB / stack / queue buffer ▼ pvPortMalloc() ◄── Portable layer (đổi được: heap_1..5 hoặc tự viết) │ ▼ configTOTAL_HEAP_SIZE bytes (mảng RAM tĩnh chứa "heap")

EXAMPLE

Ví dụ số — Fragmentation

Free blocks: [5 byte] [25 byte] [100 byte]. Yêu cầu lần lượt: 20, 80, 110 byte.

Yêu cầu 20 byte -> vừa vào block 25 -> OK (best-fit) hoặc block 100 (first-fit) Yêu cầu 80 byte -> chỉ block 100 đủ chỗ -> OK, tách còn ~20 byte free Yêu cầu 110 byte -> KHÔNG block nào đủ (blocks còn lại: 5, ~20, phần dư) dù tổng free ban đầu = 130 byte > 110 byte => THẤT BẠI do FRAGMENTATION, không phải do thiếu RAM tổng
⚠ WARNING

Đây chính là lý do câu hỏi "tại sao allocation thất bại dù tổng free heap vẫn còn nhiều?" luôn dẫn tới cùng một câu trả lời: fragmentation — kiểm tra bằng vPortGetHeapStats() (xem Lesson 10), so sánh xAvailableHeapSpaceInBytes với xSizeOfLargestFreeBlockInBytes.

LESSON 04

pvPortMalloc() & vPortFree()

SOURCE

Ý tưởng

pvPortMalloc() có cùng prototype với malloc() chuẩn; vPortFree() có cùng prototype với free(). Cả hai là hàm public, ứng dụng có thể gọi trực tiếp, không chỉ FreeRTOS kernel mới gọi được.

Application → Heap
Application │ ▼ pvPortMalloc() │ ▼ FreeRTOS Heap Manager (heap_1..5 hoặc tự viết) │ ▼ Heap (mảng RAM tĩnh, hoặc malloc() chuẩn với heap_3) │ ▼ RAM vật lý
EXAMPLE

Ví dụ dùng trực tiếp trong ứng dụng

app_example.c
void *ptr = pvPortMalloc(100);

if (ptr != NULL)
{
    /* Cấp phát thành công — dùng vùng nhớ 100 byte tại ptr */
}
else
{
    /* Thất bại — có thể do hết heap hoặc fragmentation */
}

vPortFree(ptr);   /* Trả lại RAM cho heap (nếu heap đó hỗ trợ free) */

Giải thích từng dòng: dòng 1 xin 100 byte; ptr == NULL nghĩa là thất bại — luôn phải kiểm tra trước khi dùng; vPortFree(ptr) chỉ có tác dụng thật sự với heap hỗ trợ free (heap_2/3/4/5 — không phải heap_1).

LESSON 05

3.2.1 — heap_1

PDF trang 2–3 · Đơn giản nhất, không free, luôn deterministic.

SOURCE

Concept

Nhiều hệ nhúng nhỏ chỉ tạo task/kernel object một lần trước khi scheduler chạy, không bao giờ xóa. heap_1.c hiện thực một pvPortMalloc() rất cơ bản và không implement vPortFree(). Ứng dụng không bao giờ xóa task/object có thể dùng heap_1 — kể cả hệ thống safety-critical vốn cấm dynamic allocation, vì heap_1 luôn deterministic và không thể fragment.

Cách hiện thực: chia nhỏ dần một mảng uint8_t tĩnh (configTOTAL_HEAP_SIZE). Mỗi task dynamically-created tốn 2 lần gọi pvPortMalloc() (TCB + stack).

EXPLANATION

Vì sao "không free" = "luôn deterministic"?

Fragmentation chỉ xảy ra khi bạn cấp phát rồi giải phóng liên tục các block khác kích thước. Nếu không bao giờ free, không "lỗ hổng" nào xuất hiện — chỉ đi thẳng một chiều từ đầu tới cuối mảng. Logic cực đơn giản ("lấy con trỏ hiện tại, cộng kích thước, trả về") → thời gian thực thi gần như hằng số.

Source Code (minh họa logic — INFERENCE)

heap_1.c (giản lược)
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
static size_t xNextFreeByte = 0;

void *pvPortMalloc( size_t xWantedSize )
{
    void *pvReturn = NULL;

    if ( (xNextFreeByte + xWantedSize) <= configTOTAL_HEAP_SIZE )
    {
        pvReturn = &ucHeap[ xNextFreeByte ];
        xNextFreeByte += xWantedSize;
    }
    return pvReturn;
}
/* vPortFree() KHONG duoc implement trong heap_1.c */
⚠ COMMON MISTAKE

Dùng heap_1 cho ứng dụng có tạo/xóa task hoặc queue động theo thời gian chạy → RAM cạn dần, allocation thất bại sau một thời gian, rất khó tái hiện lúc test ngắn.

LESSON 06

3.2.2 — heap_2 (Best-Fit)

PDF trang 3–4 · Có free(), nhưng không khuyến khích cho thiết kế mới.

SOURCE

Concept

"Heap_2 is superseded by heap_4 ... kept for backward compatibility and is not recommended for new designs." Heap_2 chia nhỏ mảng tĩnh giống heap_1, dùng thuật toán best-fit, và có implement vPortFree().

Best-fit: pvPortMalloc() luôn chọn block free gần khít nhất với số byte yêu cầu. Ví dụ PDF: free blocks 5/25/100 byte, yêu cầu 20 byte → chọn block 25-byte (nhỏ nhất mà vẫn đủ), tách thành 20-byte (trả về) + ~5-byte (free, dư ra do heap_2 lưu metadata trong vùng heap nên thực tế nhỏ hơn 5 chẵn).

"Unlike heap_4, heap_2 does not combine adjacent free blocks ... more susceptible to fragmentation ... However, fragmentation is not an issue if the allocated and subsequently freed blocks are always the same size."

LESSON 07

3.2.3 — heap_3 (Wrapper quanh malloc/free)

PDF trang 5 · Toàn bộ nội dung PDF về heap_3 (rất ngắn gọn).

SOURCE — toàn văn

"Heap_3.c uses the standard library malloc() and free() functions, so the linker configuration defines the heap size, and the configTOTAL_HEAP_SIZE constant is not used. Heap_3 makes malloc() and free() thread-safe by temporarily suspending the FreeRTOS scheduler for the duration of their execution."

EXPLANATION

Vì sao cần?

Nếu buộc phải dùng malloc() chuẩn (thư viện bên thứ 3 gọi cứng), heap_3 đảm bảo an toàn đa nhiệm bằng cách tạm dừng scheduler trong lúc malloc()/free() chạy — không task nào chen ngang giữa lúc dữ liệu quản lý heap nội bộ đang bị sửa. Đánh đổi: toàn hệ thống "đứng" trong lúc đó, và vì malloc() chuẩn không deterministic, thời gian "đứng" cũng không xác định trước.

Task A gọi pvPortMalloc(50) │ ├─► vTaskSuspendAll() // scheduler ngừng chuyển task khác ├─► malloc(50) // gọi C library chuẩn └─► xTaskResumeAll() // scheduler hoạt động lại
LESSON 08

3.2.4 — heap_4 (First-Fit + Coalescing)

PDF trang 5–7 · Heap được khuyến nghị phổ biến nhất.

SOURCE

Concept

Heap_4 dùng thuật toán first-fit: pvPortMalloc() dùng block đầu tiên (theo thứ tự trong mảng) đủ lớn để chứa yêu cầu. Ví dụ PDF: free blocks 5/200/100 byte (theo thứ tự), yêu cầu 20 byte → chọn block 200-byte (đầu tiên đủ điều kiện), tách 20-byte + ~180-byte dư.

Khác heap_2, heap_4 combines (coalesces) adjacent free blocks thành 1 block lớn hơn, giảm nguy cơ fragmentation. "Heap_4 is not deterministic but is faster than most standard library implementations of malloc() and free()."

LESSON 09

3.2.5 & 3.2.6 — heap_5 (Multiple Memory Regions)

PDF trang 7–10 · Gộp nhiều vùng RAM rời rạc thành một heap logic.

SOURCE

Concept

"Heap_5 uses the same allocation algorithm as heap_4 ... can combine memory from multiple separated memory spaces into a single heap. Heap_5 is useful when the RAM ... does not appear as a single contiguous block in the system's memory map."

vPortDefineHeapRegions() khởi tạo heap_5 — heap duy nhất cần khởi tạo tường minh, kernel object không thể tạo động trước khi gọi hàm này.

HeapRegion_t
void vPortDefineHeapRegions( const HeapRegion_t * const pxHeapRegions );

typedef struct HeapRegion
{
    uint8_t *pucStartAddress;   /* dia chi bat dau 1 khoi RAM */
    size_t   xSizeInBytes;      /* kich thuoc khoi do (byte) */
} HeapRegion_t;

Quy tắc bắt buộc: mảng phải sắp xếp theo địa chỉ tăng dần, kết thúc bằng phần tử có pucStartAddress = NULL.

Ví dụ Memory Map (PDF Figure 3.4)

3 vùng RAM rời rạc → 1 heap logic
heap_5 │ ┌───────────┼───────────┐ ▼ ▼ ▼ RAM1 RAM2 RAM3 0x00010000 0x00020000 0x00030000 65K bytes 32K bytes 32K bytes
⚠ WARNING — chồng lấn RAM

Nếu hard-code toàn bộ RAM1 vào xHeapRegions[] (Listing 3.3) trong khi linker đã dùng một phần RAM1 cho biến khác → chồng lấn (overlap), lỗi cực khó debug. Giải pháp đúng (Listing 3.4): khai báo một mảng biến ucHeap[] để linker tự tính ranh giới — heap_5 chỉ quản lý đúng vùng đó, không thể overlap, và nếu ucHeap quá lớn thì chương trình sẽ không link được (lỗi phát hiện lúc build).

Listing 3.4 — cách an toàn
#define RAM2_START_ADDRESS ( ( uint8_t * ) 0x00020000 )
#define RAM2_SIZE ( 32 * 1024 )
#define RAM3_START_ADDRESS ( ( uint8_t * ) 0x00030000 )
#define RAM3_SIZE ( 32 * 1024 )

#define RAM1_HEAP_SIZE ( 30 * 1024 )
static uint8_t ucHeap[ RAM1_HEAP_SIZE ];   /* linker tu dat vao RAM1 */

const HeapRegion_t xHeapRegions[] =
{
    { ucHeap,             RAM1_HEAP_SIZE },
    { RAM2_START_ADDRESS, RAM2_SIZE },
    { RAM3_START_ADDRESS, RAM3_SIZE },
    { NULL,               0 }   /* Marks the end of the array. */
};

int main( void )
{
    vPortDefineHeapRegions( xHeapRegions );
    /* Add application code here. */
}

configAPPLICATION_ALLOCATED_HEAP cho phép ứng dụng tự khai báo mảng ucHeap (thay vì để nó nằm sẵn trong heap_n.c) — hữu ích khi cần đặt heap vào vùng RAM nhanh cụ thể.

Listing 3.5 (GCC) / 3.6 (IAR)
/* GCC - dat vao section ".my_heap" */
uint8_t ucHeap[ configTOTAL_HEAP_SIZE ] __attribute__( ( section( ".my_heap" ) ) );

/* IAR - dat vao dia chi tuyet doi */
uint8_t ucHeap[ configTOTAL_HEAP_SIZE ] @ 0x20000000;
SOURCE

xPortGetFreeHeapSize() & xPortGetMinimumEverFreeHeapSize()

xPortGetFreeHeapSize() trả số byte free hiện tại — không phải thông tin fragmentation, và không implement cho heap_3. xPortGetMinimumEverFreeHeapSize() trả số byte free thấp nhất từng đạt được kể từ khi chạy — chỉ heap_4 và heap_5 mới có. Dùng để tối ưu configTOTAL_HEAP_SIZE.

EXAMPLE

Ví dụ số theo dõi qua thời gian

Initial free heap = 100 KB Task A allocates 10 KB -> free = 90 KB, min-ever-free = 90 KB Task B allocates 20 KB -> free = 70 KB, min-ever-free = 70 KB Task A frees 10 KB -> free = 80 KB, min-ever-free = 70 KB (KHONG tang lai!) Task C allocates 5 KB -> free = 75 KB, min-ever-free = 70 KB

min-ever-free chỉ giảm hoặc giữ nguyên, không bao giờ hồi phục dù bạn free RAM — nó ghi nhớ điểm thấp nhất trong lịch sử.

vPortGetHeapStats()

Heap_4 và heap_5 implement, điền đầy đủ HeapStats_t:

HeapStats_t
typedef struct xHeapStats
{
    size_t xAvailableHeapSpaceInBytes;      /* Tong free (sum tat ca block) */
    size_t xSizeOfLargestFreeBlockInBytes;  /* Block free LON NHAT */
    size_t xSizeOfSmallestFreeBlockInBytes; /* Block free NHO NHAT */
    size_t xNumberOfFreeBlocks;             /* So block free hien tai */
    size_t xMinimumEverFreeBytesRemaining;  /* Giong xPortGetMinimumEverFreeHeapSize() */
    size_t xNumberOfSuccessfulAllocations;  /* Tong so lan pvPortMalloc() thanh cong */
    size_t xNumberOfSuccessfulFrees;        /* Tong so lan vPortFree() thanh cong */
} HeapStats_t;
⚠ IMPORTANT — Phát hiện fragmentation

Nếu xAvailableHeapSpaceInBytes lớn nhưng xSizeOfLargestFreeBlockInBytes nhỏ → heap đang phân mảnh.

SOURCE

Per-task stats, Malloc Failed Hook, Fast Memory

Nếu configTRACK_TASK_MEMORY_ALLOCATIONS = 1, vTaskGetInfo() có thêm: số lần task gọi pvPortMalloc()/vPortFree(), số byte đang chiếm dụng, mức dùng heap tối đa.

pvPortMalloc() trả NULL khi thất bại. Nếu configUSE_MALLOC_FAILED_HOOK = 1, hàm vApplicationMallocFailedHook() được gọi — và object đó không được tạo. PDF lưu ý: coi thất bại là fatal error (như nhiều demo) không phải best practice cho production.

pvPortMallocStack()/vPortFreeStack() (mặc định gọi thẳng pvPortMalloc/vPortFree) có thể map sang hàm ứng dụng riêng để lấy stack từ vùng "fast memory" tách biệt heap chính — vì stack bị truy cập tần suất rất cao.

void vApplicationGetIdleTaskMemory( StaticTask_t **ppxIdleTaskTCBBuffer,
                                     StackType_t **ppxIdleTaskStackBuffer,
                                     uint32_t *pulIdleTaskStackSize )
{
    static StaticTask_t xIdleTaskTCB;
    static StackType_t uxIdleTaskStack[ configMINIMAL_STACK_SIZE ];

    *ppxIdleTaskStackBuffer = uxIdleTaskStack;
    *pulIdleTaskStackSize = configMINIMAL_STACK_SIZE;
}
⚠ COMMON MISTAKE

Nếu buffer trong hàm này không khai báo static, chúng bị cấp phát trên stack và biến mất khi hàm return → dangling pointer, crash ngẫu nhiên cực khó debug. Đây là điểm PDF nhấn mạnh riêng bằng comment trong code.

EXPLANATION

heap_1: đơn giản nhất, không free, dùng khi chỉ tạo object một lần lúc khởi động. heap_2: best-fit, có free nhưng không gộp block — chỉ ổn khi kích thước alloc/free lặp lại cố định; không khuyến khích cho thiết kế mới. heap_3: wrapper quanh malloc()/free() chuẩn, thread-safe qua suspend scheduler. heap_4: first-fit + coalescing, lựa chọn phổ biến nhất. heap_5: giống heap_4 nhưng gộp nhiều vùng RAM rời rạc.
