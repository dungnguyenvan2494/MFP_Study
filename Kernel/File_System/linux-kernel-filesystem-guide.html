VFS (Virtual File System) là lớp trừu tượng trung tâm cho phép Linux hỗ trợ hàng chục filesystem khác nhau (ext4, xfs, btrfs, tmpfs, procfs, NFS...) đằng sau một tập API thống nhất: open/read/write/close/stat/.... Không có VFS, mỗi syscall sẽ phải biết cách nói chuyện với từng filesystem cụ thể — không thể mở rộng được. VFS giải quyết bài toán này bằng polymorphism kiểu C: mỗi object (file, inode, dentry, super_block) mang theo một bảng con trỏ hàm (*_operations) do filesystem cụ thể cài đặt; VFS chỉ gọi qua con trỏ, không biết — và không cần biết — mình đang nói chuyện với ext4 hay tmpfs.

CHAPTER 02

VFS Architecture

★★☆☆☆Requires: 01 Overview

VFS không phải là một filesystem — nó không lưu dữ liệu trên disk. Nó là một tập object model + registry sống hoàn toàn trong RAM, đóng vai trò trung gian bắt buộc giữa syscall và filesystem thật. Ba lý do VFS tồn tại:

  1. Tính đa dạng filesystem — kernel phải hỗ trợ hàng chục filesystem (ext4, xfs, btrfs, vfat, nfs, tmpfs, procfs...) qua một API duy nhất.
  2. Namespace thống nhất — mọi filesystem được mount vào một cây thư mục duy nhất bắt đầu từ /, bất kể nó nằm trên disk, RAM, hay mạng.
  3. Cache tập trung — dcache (dentry cache) và inode cache là cơ chế chung cho mọi filesystem, filesystem không phải tự cài lại logic cache pathname.

🧠 MENTAL MODEL
Nghĩ về VFS như một interface Java/abstract class trong C: mỗi struct object (file, inode, super_block, address_space) mang theo một con trỏ tới bảng hàm ảo (f_op, i_op, s_op, a_ops). Khi VFS gọi file->f_op->read_iter(...), nó đang gọi "virtual method" — implementation thật nằm ở ext4, tmpfs, hay bất kỳ filesystem nào cài đặt struct file đó.

CHAPTER 04

File Descriptor

★★☆☆☆Requires: 03 Core structs

Một fd (file descriptor, số nguyên nhỏ) là chỉ số vào một mảng riêng của process, KHÔNG phải con trỏ vào struct file trực tiếp — lớp gián tiếp này cho phép mỗi process có bảng fd độc lập trong khi vẫn share cùng struct file nếu dup()/fork().

get_unused_fd_flags()
Source: fs/file.c  |  Subsystem: VFS
Purpose
Tìm 1 slot trống trong fdtable của process hiện tại, đánh dấu đã dùng trong open_fds bitmap, KHÔNG gắn struct file vào — chỉ "đặt chỗ".
Caller
do_sys_openat2() (fs/open.c) — gọi trước khi path lookup hoàn tất, để tránh leak fd nếu bị lỗi giữa chừng.
Callee
alloc_fd()
Output
Số fd >= 0, hoặc -EMFILE nếu vượt RLIMIT_NOFILE.
Next step
do_filp_open() để lấy struct file* thật, sau đó fd_install().
fd_install()
Source: fs/file.c  |  Subsystem: VFS
Purpose
Gắn struct file* đã mở thành công vào slot fd đã được get_unused_fd_flags() đặt chỗ trước đó — publish nó cho userspace thấy qua fd.
Caller
do_sys_openat2(), sau khi do_filp_open() trả về thành công.
Reference counting
Không tăng refcount thêm — struct file vừa alloc đã có refcount 1, giờ chuyển quyền sở hữu (ownership transfer) cho fdtable.
fget() / fput()
Source: fs/file.c, fs/file_table.c  |  Subsystem: VFS
Purpose
fget(fd): tra fdtable theo fd, tăng f_count, trả về struct file* an toàn dùng ngoài giữ fd lock (dùng bởi mọi syscall thao tác trên fd: read/write/ioctl/...). fput(file): giảm f_count, nếu về 0 thì free qua file_free() (RCU-delayed).
Locking
fget() dùng RCU read-side + atomic_long_inc_not_zero() để tránh race với close() đang giải phóng file ở CPU khác.
Reference counting
f_count là atomic_long_t — tăng ở mọi fget()/dup(), giảm ở mọi fput()/close(). Khi về 0: gọi f_op->release(), giải phóng dentry/mnt reference qua path_put().

CHAPTER 05

Pathname Lookup

★★★★☆Requires: 04, 06 Dcache, 07 Inode

Đây là cơ chế biến một chuỗi ký tự như "/home/user/test.txt" thành struct path { dentry, vfsmount }. Kernel đi qua từng component (home, user, test.txt) một, mỗi bước tra dcache trước — chỉ chạm filesystem thật khi cache miss.

link_path_walk()
Source: fs/namei.c:2113  |  Subsystem: VFS
Purpose
Duyệt toàn bộ pathname, tách theo /, gọi walk_component() cho từng phần trừ phần cuối cùng (last component được xử lý riêng tuỳ flag LOOKUP_PARENT).
Caller
path_lookupat(), path_openat(), path_mountpoint().
Callee
walk_component() → lookup_fast()/__lookup_slow(); xử lý ., ..; theo symlink qua get_link().
Important structs
struct nameidata — mang trạng thái duyệt hiện tại (path hiện tại, depth symlink, flags).
Locking
Ưu tiên chạy trong RCU-walk mode (không lock, không tăng refcount — nhanh); rơi về ref-walk mode (có lock, có refcount) khi gặp trường hợp không an toàn cho RCU (vd cần block, cần theo symlink phức tạp).
Error paths
-ENOENT (component không tồn tại), -ENOTDIR (component giữa đường không phải thư mục), -ELOOP (quá nhiều symlink — giới hạn MAXSYMLINKS).
Next step
Component cuối cùng → trả về struct path hoàn chỉnh cho caller (vd path_openat()).
lookup_fast()
Source: fs/namei.c:1465  |  Subsystem: VFS
Purpose
Tra dcache cho 1 component, cố gắng tìm dentry đã có sẵn trong RAM — đường đi nhanh (fast path), không chạm filesystem.
Callee
__d_lookup_rcu() (RCU-walk) hoặc __d_lookup() (ref-walk) — xem chương 06.
Output
Dentry nếu hit (có thể là negative dentry — biết chắc file không tồn tại, cũng là 1 dạng "hit"); NULL/lỗi nếu miss.
Next step
Hit → dùng ngay dentry đó, tiếp tục component kế. Miss → __lookup_slow().
__lookup_slow()
Source: fs/namei.c:1529  |  Subsystem: VFS → FS
Purpose
Dcache miss — phải hỏi filesystem thật: có tên component này trong thư mục cha không?
Callee
parent_inode->i_op->lookup(dir, dentry, flags) — vd ext4_lookup() đọc directory block/htree trên disk (qua page cache/buffer cache), tìm entry khớp tên, rồi iget_locked() nạp/tạo inode tương ứng.
Important structs
Tạo struct dentry mới (negative trước, rồi d_add() gắn inode nếu tìm thấy) qua d_alloc_parallel().
Locking
inode->i_rwsem (đọc) trên thư mục cha để tránh race với create/unlink song song.
Next step
Dentry mới được d_add() vào dcache — lần lookup sau cùng tên sẽ hit fast path.
⚙ absolute vs relative path
path_init() chọn điểm bắt đầu: bắt đầu bằng / → task->fs->root; ngược lại → task->fs->pwd (cwd) hoặc dfd (với *at() syscalls như openat). chdir() chỉ đổi fs->pwd, không đổi filesystem thật.
⚙ symlink vs hard link
Symlink: một inode riêng (S_ISLNK) chứa chuỗi path đích — get_link() trả về path đó, link_path_walk() lặp lại resolution trên path mới. Hard link: không có inode riêng — chỉ là một dentry/tên khác trỏ vào cùng inode (i_nlink++). Xem 16 unlink().
🧠 MENTAL MODEL — mount namespace & struct path
Một pathname không resolve thành 1 dentry đơn — nó resolve thành struct path { dentry, vfsmount }, vì trên đường đi có thể băng qua ranh giới mount (vd /home là 1 mount point riêng). path_init()/link_path_walk() tự động "nhảy" qua mount point (follow_mount()), nên với người dùng, cây thư mục trông liền mạch dù thực chất là nhiều filesystem ghép lại.

CHAPTER 06

Dentry & Dcache

★★★☆☆Requires: 03

Dcache là bảng hash toàn cục ánh xạ (parent dentry, tên) → dentry, giúp tránh phải hỏi lại filesystem mỗi lần resolve cùng một pathname. Không có dcache, MỖI lần open() đều phải đọc directory block từ disk — cực kỳ chậm.

d_lookup() / __d_lookup()
Source: fs/dcache.c:2335 / 2365  |  Subsystem: VFS
Purpose
Tra bảng hash dcache toàn cục theo (parent, qstr name), trả về dentry nếu có, tăng reference count của nó.
Locking
__d_lookup() dùng rcu_read_lock() để duyệt hash chain không khoá, chỉ lock (dentry->d_lockref.lock) đúng candidate để verify tên khớp và tăng refcount an toàn (seqlock retry nếu bị race).
Output
Dentry với refcount +1 (caller phải dput() sau khi dùng xong), hoặc NULL.
d_alloc() / d_alloc_parallel()
Source: fs/dcache.c:1791, 2540  |  Subsystem: VFS
Purpose
Cấp phát 1 struct dentry mới (chưa có inode — "negative"), gắn vào d_parent->d_subdirs. d_alloc_parallel() còn xử lý trường hợp nhiều thread cùng lookup 1 tên song song (in-lookup hash) để không tạo trùng.
Caller
__lookup_slow() khi dcache miss.
d_add() / d_instantiate()
Source: fs/dcache.c:2702 / 1976  |  Subsystem: VFS
Purpose
Gắn inode vào 1 dentry vừa alloc (biến negative dentry thành positive) — d_instantiate() thêm dentry vào inode->i_dentry alias list; d_add() = d_instantiate() + rehash vào bảng hash toàn cục để lookup sau tìm thấy.
Caller
Filesystem's ->lookup(), ->create(), ->mkdir(), sau khi gọi iget_locked()/tạo inode mới.
dput()
Source: fs/dcache.c:864  |  Subsystem: VFS
Purpose
Giảm reference count của dentry. Về 0 → KHÔNG free ngay — đưa vào LRU list để có thể tái sử dụng nếu lookup lại sớm (đây là lý do dcache "nhanh" ngay cả sau khi không còn ai giữ reference).
Reference counting
d_lockref (kết hợp spinlock + count, tối ưu hoá bằng cmpxchg cho trường hợp không tranh chấp).
Next step
Dưới áp lực bộ nhớ, shrinker (prune_dcache_sb()) sẽ evict dentry ở cuối LRU → gọi iput() trên inode liên quan.

CHAPTER 23

JBD2 — Journaling

★★★★☆Requires: 22

JBD2 (Journaling Block Device v2) giải quyết bài toán metadata consistency khi crash giữa chừng: một thao tác như create() cần sửa NHIỀU block khác nhau (inode bitmap, inode table, directory block) — nếu crash sau khi ghi block 1 nhưng trước block 2, filesystem rơi vào trạng thái không nhất quán. JBD2 buộc mọi thay đổi metadata phải ghi vào journal (log tuần tự, ghi nhanh) trước, rồi mới "checkpoint" (ghi thật) vào vị trí cuối cùng — nếu crash giữa chừng, lần mount sau replay journal để hoàn tất hoặc rollback toàn bộ transaction, không bao giờ để lại trạng thái nửa vời.

💡 KEY IDEA
Journal biến N lần ghi rải rác (chậm, seek nhiều) thành 1 lần ghi tuần tự vào vùng journal (nhanh) + ghi lại sau (có thể gộp/trễ). Đây là lý do ext4 với journaling không nhất thiết chậm hơn ext2 không journal cho workload ghi nhiều metadata — trade-off là double-write (ghi 2 lần: journal rồi checkpoint) đổi lấy consistency đảm bảo.

  9. Interrupt: driver ISR → blk_mq_complete_request → bio->bi_end_io → đánh dấu trang Uptodate, unlock_page, đánh thức reader đang chờ trong generic_file_buffered_read.
