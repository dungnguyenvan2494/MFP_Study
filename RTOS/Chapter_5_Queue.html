EXPLANATION

Một Task là một đoạn code chạy độc lập, có stack và context riêng, được scheduler cấp phát thời gian CPU. Một task chỉ là một hàm C chạy trong vòng lặp vô hạn, không bao giờ return.

Scheduler & Task State

EXPLANATION

Scheduler là phần lõi của RTOS, quyết định task nào được chạy tại mỗi thời điểm. FreeRTOS dùng giải thuật priority-based pre-emptive: task có priority cao hơn luôn được ưu tiên chạy khi nó ở trạng thái sẵn sàng (Ready); nếu hai task cùng priority, scheduler chia thời gian round-robin giữa chúng.

Ready / Running / Blocked / Suspended

Ready - san sang chay, cho scheduler cap CPU Running - dang thuc su chay tren CPU (chi 1 task Running tren 1 core) Blocked - dang cho mot su kien (vd: cho data tu Queue, cho Semaphore, vTaskDelay) Suspended - bi "dong bang" boi vTaskSuspend(), khong duoc scheduler xet toi cho den khi vTaskResume()
Task State Machine — click vào một trạng thái
EXPLANATION

READY: task sẵn sàng chạy, chỉ chờ scheduler cấp CPU. Có thể có nhiều task Ready cùng lúc.

EXPLANATION

RUNNING: task đang thực sự chiếm CPU. Chỉ có đúng 1 task Running tại một thời điểm trên 1 core.

INFERENCE

Đây là điểm quan trọng nhất để hiểu Queue: khi task gọi xQueueReceive() mà Queue đang rỗng (và có chỉ định block time), task rời Running, chuyển sang Blocked, nhường CPU cho task khác. Khi có dữ liệu, task tự động Blocked → Ready.

EXPLANATION

SUSPENDED: bị "đóng băng" bởi vTaskSuspend(), scheduler hoàn toàn bỏ qua task này cho đến khi vTaskResume() được gọi.

IPC — Inter-Task Communication

EXPLANATION

IPC là cơ chế để các task (hoặc ISR) trao đổi dữ liệu với nhau an toàn, vì task không được phép truy cập thẳng vào biến cục bộ (stack) của task khác.

IPC — luồng dữ liệu cơ bản
EXPLANATION

Nếu không có IPC và hai task cần chia sẻ dữ liệu, lập trình viên buộc phải dùng một global variable dùng chung. Vấn đề:

  • Task A và Task B có thể truy cập global_data cùng lúc (race condition) nếu không có cơ chế bảo vệ.
  • Không có cơ chế thông báo: Task B không biết khi nào Task A đã cập nhật xong dữ liệu — phải polling liên tục (tốn CPU).
  • Không có buffering: nếu Task A ghi 2 lần liên tiếp trước khi Task B đọc, giá trị đầu bị mất (ghi đè).
  • Không có đồng bộ hoá trạng thái: Task B không thể "chờ" dữ liệu mới mà không tốn CPU (busy-wait).
INFERENCE

Đây chính là lý do RTOS cần Queue: Queue giải quyết cả 4 vấn đề trên cùng lúc — sẽ được giải thích chi tiết ở các lesson tiếp theo.

Queue by Copy vs Queue by Reference

SOURCE

(5.2.1) Tài liệu nêu 2 cơ chế: (1) Queue by copy —

"the data sent to the queue is copied byte for byte into the queue"
; (2) Queue by reference —
"the queue only holds pointers to the data sent to the queue, not the data itself."

SOURCE

FreeRTOS chọn queue by copy làm mặc định vì:

  • Không ngăn cản việc dùng nó như queue by reference — khi data quá lớn, vẫn có thể copy con trỏ vào queue.
  • Một biến stack (local variable) có thể gửi thẳng vào queue, kể cả khi biến đó không còn tồn tại sau khi hàm chứa nó return.
  • Không cần cấp phát buffer trước để gửi dữ liệu.
  • Sending task có thể dùng lại ngay biến/buffer vừa gửi.
  • Sender và Receiver hoàn toàn decoupled — không ai cần biết ai sở hữu dữ liệu hay ai phải free.
  • RTOS chịu toàn bộ trách nhiệm cấp phát bộ nhớ lưu data.
  • Hệ thống có memory protection: queue by copy cho phép data đi qua ranh giới bảo vệ.

EXAMPLE

Queue tạo để chứa int32_t. Hai instance của task này chạy đồng thời, một gửi 100, một gửi 200 liên tục, không dùng block time (vì receiver có priority cao hơn nên queue gần như luôn rỗng khi gửi).

static void vSenderTask( void *pvParameters )
{

    BaseType_t xStatus;

    /* Task param dùng để truyền giá trị 100 hoặc 200 vào từng instance. */

    {
        /* Gửi vào tail. Không block vì queue lẽ ra không bao giờ đầy. */
        xStatus = xQueueSendToBack( xQueue, &lValueToSend, 0 );

        if( xStatus != pdPASS )

            /* Lỗi: queue đầy — không nên xảy ra vì chỉ 1 item tối đa. */
            vPrintString( "Could not send to the queue.\r\n" );
        }
    }
}

static void vReceiverTask( void *pvParameters )
{
    int32_t lReceivedValue;
    BaseType_t xStatus;
    const TickType_t xTicksToWait = pdMS_TO_TICKS( 100 );

    for( ;; )
    {
        /* Luôn phải rỗng vì task này nhận priority cao hơn 2 sender. */

        {
            vPrintString( "Queue should have been empty!\r\n" );

        /* Block tối đa 100ms chờ dữ liệu, nếu queue đang rỗng. */
        xStatus = xQueueReceive( xQueue, &lReceivedValue, xTicksToWait );

        if( xStatus == pdPASS )
        {
            vPrintStringAndNumber( "Received = ", lReceivedValue );
        }
        else
        {
            vPrintString( "Could not receive from the queue.\r\n" );
        }
    }
}

Block Time & Task State

5.2.3 Blocking on Queue Reads

SOURCE

"When a task attempts to read from a queue, it can optionally specify a 'block' time. This is the time the task is kept in the Blocked state to wait for data to become available from the queue, if the queue is already empty. A task that is in the Blocked state waiting for data to become available from a queue is automatically moved to the Ready state when another task or interrupt places data into the queue. The task will also be moved automatically from the Blocked state to the Ready state if the specified block time expires before data becomes available."

5.2.4 Blocking on Queue Writes

SOURCE

"Just as it can when reading from a queue, a task can optionally specify a block time when writing to a queue. In this case, the block time is the maximum time the task will be held in the Blocked state to wait for space to become available on the queue, should the queue already be full."

Ảnh hưởng của Block Time lên Task State (liên hệ với lesson Scheduler)
EXPLANATION

Task rời Running sang Blocked khi gọi xQueueReceive() trên queue rỗng, hoặc xQueueSend...() trên queue đầy, với xTicksToWait > 0. Trong lúc Blocked, task không hề tiêu tốn CPU — scheduler chạy task khác. Task quay lại Ready (rồi có thể Running nếu priority cao nhất) qua 1 trong 2 sự kiện: (1) có dữ liệu/khoảng trống xuất hiện, hoặc (2) block time hết hạn (timeout, trả về errQUEUE_EMPTY/errQUEUE_FULL).

Multi-task

Multiple Readers / Multiple Writers

SOURCE

(5.2.2)

"Queues are objects in their own right and can be accessed by any task or ISR that knows of their existence. Any number of tasks can write to the same queue, and any number of tasks can read from the same queue. In practice, it is very common for a queue to have multiple writers, but much less common for a queue to have multiple readers."

Quy tắc unblock khi có nhiều Reader chờ (5.2.3)

SOURCE

"Queues can have multiple readers, so it is possible for a single queue to have more than one task blocked on it waiting for data. When this is the case, only one task is unblocked when data becomes available. The task that is unblocked is always the highest priority task that is waiting for data. If two or more blocked tasks have equal priority, then the task that is unblocked is the one that has been waiting the longest."

Quy tắc unblock khi có nhiều Writer chờ (5.2.4)

SOURCE

"Queues can have multiple writers, so it is possible for a full queue to have more than one task blocked on it waiting to complete a send operation. When this is the case, only one task is unblocked when space on the queue becomes available. The task that is unblocked is always the highest priority task that is waiting for space. If two or more blocked tasks have equal priority, then the task that is unblocked is the one that has been waiting the longest."

Pointer Queue & Ownership — Working With Large or Variable-Sized Data

SOURCE

(5.5.1 Queuing Pointers)

"If the size of the data stored in the queue is large, then it is preferable to use the queue to transfer pointers to the data, rather than copy the data itself into and out of the queue byte by byte. Transferring pointers is more efficient in both processing time and the amount of RAM required to create the queue."

SOURCE

"However, when queuing pointers, extreme care must be taken to ensure that:"

  • The owner of the RAM being pointed to is clearly defined. Chỉ Sending task được truy cập bộ nhớ trước khi gửi pointer vào queue; chỉ Receiving task được truy cập sau khi nhận pointer từ queue.
  • The RAM being pointed to remains valid. Nếu bộ nhớ cấp phát động, phải có đúng 1 task chịu trách nhiệm free nó — không task nào được truy cập sau khi đã free.
  • A pointer should never be used to access data that has been allocated on a task stack — dữ liệu đó sẽ không còn hợp lệ sau khi stack frame thay đổi (hàm chứa nó return).

Debugging Queue Issues

INFERENCE

Các case dưới đây suy ra trực tiếp từ những rule/behavior đã có SOURCE ở các lesson trước — mỗi case trỏ lại đúng phần tài liệu liên quan. Không có case nào bịa thêm hành vi ngoài tài liệu.

1. xQueueCreate() trả về NULL

Nguyên nhân: không đủ heap để cấp phát 2 khối RAM (data structure + storage area) — xem lesson Queue Creation, 5.3.1. Fix: kiểm tra configTOTAL_HEAP_SIZE, giảm uxQueueLength/uxItemSize, hoặc dùng xQueueCreateStatic() với RAM tĩnh.

2. Send liên tục trả errQUEUE_FULL

Nguyên nhân: Receiver priority thấp hơn Sender và không kịp rút bớt (giống setup Example 5.2), hoặc Receiver bị block/đứng ở chỗ khác, hoặc uxQueueLength đặt quá nhỏ. Fix: kiểm tra priority theo đúng bảng "ai được unblock" (lesson Multiple Readers/Writers), tăng queue length nếu hệ thống vốn có burst.

3. Receive liên tục trả errQUEUE_EMPTY dù Sender đang chạy

Nguyên nhân: Sender gửi nhầm queue handle, hoặc Sender bị Blocked/Suspended ở nơi khác nên chưa từng gọi Send. Fix: log lại giá trị handle ở cả 2 đầu, kiểm tra Sender có thực sự tới được dòng xQueueSendToBack() không.

4. Dữ liệu nhận được là rác / giá trị không hợp lệ

Nguyên nhân kinh điển: Dangling pointer — queue một địa chỉ của biến stack local, hàm chứa nó đã return trước khi Receiver đọc (xem lesson Pointer Queue & Ownership). Fix: không bao giờ queue con trỏ trỏ vào biến cục bộ; dùng buffer cấp phát động/pool hoặc static.

5. Dùng chung 1 buffer bị 2 task ghi đè lẫn nhau

Nguyên nhân: vi phạm rule "owner of the RAM being pointed to is clearly defined" (5.5.1) — cả sender và receiver cùng truy cập buffer cùng lúc. Fix: chỉ 1 phía được truy cập tại 1 thời điểm: sender ngừng đụng vào buffer ngay sau khi gửi pointer, receiver mới được đụng vào sau khi nhận.

6. Memory leak dần theo thời gian khi dùng Pointer Queue

Nguyên nhân: không task nào gọi free/release buffer sau khi dùng xong (thiếu bước như prvReleaseBuffer() ở Listing 5.15). Fix: luôn xác định rõ đúng 1 task chịu trách nhiệm free bộ nhớ được trỏ tới.

7. xQueueOverwrite() assert / lỗi khi queue length > 1

Nguyên nhân: xQueueOverwrite() "must only be used with queues that have a length of one" (5.7.1) — dùng nhầm trên queue thường. Fix: chỉ dùng Overwrite với Mailbox (length=1); dùng xQueueSendToBack() cho queue nhiều phần tử.

8. Mailbox "không cập nhật" ở phía đọc

Nguyên nhân: code dùng nhầm xQueueReceive() thay vì xQueuePeek() để đọc mailbox → item bị xoá, các reader khác/lần đọc sau không còn thấy giá trị (5.7.2 lưu ý rõ nếu Receive thì "mailbox would be left empty"). Fix: luôn Peek khi đọc Mailbox, chỉ Overwrite khi ghi.

9. Gọi API Queue trong ISR bị lỗi/crash

Nguyên nhân: gọi thẳng xQueueSendToBack()/xQueueReceive()/xQueuePeek()/xQueueOverwrite() từ interrupt service routine — tài liệu note rõ ở mỗi API "Never call ... from an interrupt service routine". Fix: dùng bản ...FromISR() tương ứng (Chapter 7).

10. Đọc nhầm queue không thuộc Queue Set / đọc trước khi Select trả về

Nguyên nhân: vi phạm note ở 5.6.4: "Do not read data from a queue or semaphore that is a member of a set unless the handle... has first been returned from a call to xQueueSelectFromSet()". Fix: chỉ đọc queue/semaphore thành viên đúng khi handle của nó vừa được Select trả về, và chỉ đọc đúng 1 item mỗi lần được trả.

11. Thêm queue vào Set nhưng bị từ chối (pdFAIL)

Nguyên nhân: (5.6.3) queue/semaphore phải rỗng khi thêm vào set, và chỉ được thuộc 1 set tại 1 thời điểm — thêm 1 queue đã có dữ liệu hoặc đã thuộc set khác sẽ fail. Fix: add vào set ngay sau khi tạo (trước khi bất kỳ ai gửi dữ liệu), và không add cùng 1 queue vào 2 set.

12. Quên kiểm tra return value xStatus sau Send/Receive

Nguyên nhân: bỏ qua pdPASS/errQUEUE_FULL/errQUEUE_EMPTY (như các ví dụ vPrintString cảnh báo lỗi ở Listing 5.6/5.7) khiến lỗi bị "nuốt" âm thầm. Fix: luôn kiểm tra xStatus, log lỗi khi thao tác không thành công — nhất là khi dùng block time = 0 hoặc hữu hạn.

Trace: xQueueSendToBack() / xQueueSendToFront()

  1. Task gọi xQueueSendTo...(xQueue, pvItemToQueue, xTicksToWait).

Trace: xQueueReceive()

  1. Task gọi xQueueReceive(xQueue, pvBuffer, xTicksToWait).
  2. Nếu queue có item → copy item ở head ra pvBuffer, xoá item đó khỏi queue (head trỏ tới item kế tiếp).
  3. Nếu có task khác đang Blocked chờ Send (queue vừa hết đầy) → theo rule "highest priority, rồi tới longest waiting" (5.2.4), task đó Ready/Running.
  4. Trả về pdPASS.
  5. Nếu queue rỗng: hoặc trả errQUEUE_EMPTY ngay, hoặc Task Blocked rồi retry bước 2 khi có data hoặc timeout → errQUEUE_EMPTY.

Cheat Sheet — 1 trang

Quyết định nhanh: dùng cơ chế nào?

Chỉ cần giá trị mới nhất, không cần lịch sử?→ dùng Mailbox (length=1) + xQueueOverwrite() / xQueuePeek()
Nhiều nguồn gửi, 1 nơi nhận, cần biết nguồn nào?→ 1 Queue chứa structure có field ID nguồn (Figure 5.4 pattern)
Data lớn hoặc kích thước thay đổi?→ Pointer Queue (nhớ rule ownership 5.5.1) hoặc pattern IPStackEvent_t
Phải chờ nhiều queue/semaphore cùng lúc, không muốn polling?→ Queue Set (chỉ khi thực sự cần)
Trường hợp còn lại (đa số)?→ Queue by Copy thường (FIFO, xQueueSendToBack/xQueueReceive)

Ghi nhớ cốt lõi

  • Nhiều task chờ cùng 1 queue → chỉ unblock priority cao nhất; bằng nhau → chờ lâu nhất.
  • xTicksToWait=0 → không bao giờ Block. portMAX_DELAY → Block vô hạn.
  • Không bao giờ queue pointer trỏ vào biến stack.
  • Không bao giờ gọi API queue thường (không …FromISR) trong ISR.
  • xQueueOverwrite()/Mailbox chỉ dùng với queue length = 1.
  • Đọc Mailbox → dùng Peek, không dùng Receive (kẻo làm rỗng mailbox).

Glossary

Queue
Object trong RAM giữ 1 dãy các fixed-size data item; length và item size cố định lúc tạo.
Queue Item
1 đơn vị dữ liệu được lưu trong 1 slot của queue.
Queue Length
Số item tối đa 1 queue có thể chứa cùng lúc (uxQueueLength).
Item Size
Kích thước byte của mỗi item (uxItemSize), cố định khi tạo queue.
FIFO
First In First Out — ghi vào tail, đọc ra từ head; hành vi mặc định của Queue.
Send
Thao tác ghi dữ liệu vào queue (xQueueSendToBack/Front/xQueueSend).
Receive
Thao tác đọc và xoá dữ liệu khỏi queue (xQueueReceive).
Block Time
Thời gian tối đa (xTicksToWait) task chịu Blocked để chờ data/chỗ trống.
Blocking
Trạng thái task rời Running sang Blocked khi Receive-rỗng hoặc Send-đầy với block time > 0.
Multiple Writers
Nhiều task cùng Send vào 1 queue; khi Blocked chờ chỗ trống, unblock theo priority rồi longest-waiting.
Multiple Readers
Nhiều task cùng Receive từ 1 queue; khi Blocked chờ data, unblock theo priority rồi longest-waiting.
Queue Set
Tập hợp nhiều queue/semaphore để 1 task chờ dữ liệu từ bất kỳ thành viên nào mà không polling.
Queue by Copy
Dữ liệu được copy byte-for-byte vào vùng nhớ riêng của queue. Mặc định của FreeRTOS.
Queue by Reference
Queue chỉ giữ pointer trỏ tới dữ liệu thật, không copy dữ liệu.
Queue Pointer
Kỹ thuật queue-by-reference: gửi địa chỉ 1 buffer qua queue thay vì toàn bộ dữ liệu.
Variable-sized Data
Kỹ thuật dùng 1 struct (VD IPStackEvent_t) với field kiểu + void* để mang bất kỳ kiểu/kích thước dữ liệu nào qua cùng 1 queue.
Mailbox
Queue có length = 1; dữ liệu ở lại cho tới khi bị ghi đè (không "đi qua" như queue thường).
Peek
xQueuePeek() — đọc item ở head mà không xoá; nền tảng để đọc Mailbox.
Overwrite
xQueueOverwrite() — ghi vào queue length=1, ghi đè item cũ nếu đầy, luôn thành công.
Handle
Biến kiểu QueueHandle_t/QueueSetHandle_t tham chiếu tới 1 queue/set đã tạo.
Task State
Running / Ready / Blocked — trạng thái task, thay đổi trực tiếp bởi hành vi Send/Receive trên Queue.
Priority
Mức ưu tiên của task; quyết định ai được unblock trước khi nhiều task cùng chờ 1 queue.
