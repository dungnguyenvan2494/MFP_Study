CHAPTER 01

Big Picture

Concept

Build kernel Linux không phải là "chạy make rồi ra file chạy được". Nó là một pipeline nhiều tầng, mỗi tầng dùng một công cụ khác nhau, sinh ra một artifact trung gian khác nhau, và artifact đó lại là input cho tầng kế tiếp. Toàn bộ handbook này chỉ xoay quanh một câu hỏi duy nhất cho mọi file bạn gặp sau khi build: file này từ đâu ra, tool nào tạo, input là gì, và ai tiêu thụ nó tiếp theo?

Toàn bộ trích đoạn Makefile/Kconfig/linker-script trong tài liệu này lấy trực tiếp từ repository thực tế Kernel/Src trong workspace (kernel ARM64, cấu trúc Kbuild hiện đại — xem Chapter 09). CHAPTER 02

Kernel Source Tree

Concept

Source tree của kernel được tổ chức theo subsystem, không theo platform. Mỗi thư mục top-level có một Makefile và (thường) một Kconfig riêng, được top-level Makefile gọi đệ quy thông qua biến obj-y/core-y/drivers-y.

CHAPTER 03

Make Entry Point

Concept

Top-level Makefile (trong bản mainline đầy đủ, nằm tại gốc source tree) là "nhạc trưởng": nó không tự biên dịch file nào, mà điều phối Kconfig, rồi include scripts/Kbuild.include, rồi đệ quy xuống từng thư mục thông qua scripts/Makefile.build.

Lệnh build ARM64 điển hình

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- Image

Ba biến then chốt truyền vào make:

BiếnÝ nghĩaẢnh hưởng
ARCHChọn cây arch/<ARCH>/ sẽ được includeQuyết định arch/arm64/Makefile, arch/arm64/Kconfig được dùng thay vì x86/arm
CROSS_COMPILEPrefix của toolchain (aarch64-linux-gnu-)CC = $(CROSS_COMPILE)gcc, LD = $(CROSS_COMPILE)ld… (xem Chapter 30)
O=build (tuỳ chọn)Thư mục output tách biệt sourceXem Chapter 31

Thứ tự thực thi khái quát (top-level Makefile mainline)

1. Parse ARCH/CROSS_COMPILE, include arch/arm64/Makefile
↓
2. Target %config? → chạy Kconfig (scripts/kconfig/*)
↓
3. include .config, include/config/auto.conf
↓
4. Sinh include/generated/autoconf.h (nếu .config đổi)
↓
5. vmlinux-dirs := init usr arch/arm64 kernel mm fs … drivers
↓ mỗi thư mục
6. $(Q)$(MAKE) $(build)=$(dir) → scripts/Makefile.build
↓
7. scripts/link-vmlinux.sh → vmlinux
↓
8. $(MAKE) -C arch/arm64/boot Image (objcopy)

Source Code

scripts/Makefile.build — engine thật sự chạy trong từng thư mục con (đây là file có thật trong repo, dòng đầu):

scripts/Makefile.build
# SPDX-License-Identifier: GPL-2.0
# ==========================================================================
# Building
# ==========================================================================

src := $(obj)

PHONY := __build
__build:

src := $(obj) nghĩa là: mỗi lần Makefile.build được include lại (cho từng thư mục), obj được set bằng đường dẫn thư mục hiện tại — đây là kỹ thuật "một file Makefile, gọi đệ quy hàng trăm lần với biến khác nhau" thay vì viết Makefile riêng cho mỗi thư mục.

Common Mistakes

⚠ "Chạy make Image mà không set ARCH thì vẫn build ra kernel ARM64"
Sai. Không set ARCH, Makefile mặc định dùng uname -m của máy build (thường là x86_64) → toàn bộ arch/x86 được include, ra binary x86, không chạy được trên board ARM64. Luôn set ARCH + CROSS_COMPILE tường minh khi cross-compile.

Summary

Top-level Makefile không "biết" cách compile file .c — nó chỉ biết cách gọi đúng thứ tự các Makefile con, đúng ARCH, đúng cấu hình. Việc dịch thật sự nằm ở scripts/Makefile.build (Chapter 06).

CHAPTER 04

Kconfig

Concept

Kconfig là ngôn ngữ mô tả các lựa chọn cấu hình (feature nào có thể bật/tắt) và quan hệ phụ thuộc giữa chúng (A cần B, A loại trừ C…). Kconfig không build gì cả — nó chỉ sinh ra một tập giá trị (.config) mà Kbuild sẽ đọc.

Source Code thực tế

Trích từ arch/arm64/Kconfig trong repo (định nghĩa symbol gốc ARM64):

arch/arm64/Kconfig
# SPDX-License-Identifier: GPL-2.0-only
config ARM64
	def_bool y
	select ACPI_CCA_REQUIRED if ACPI
	select ACPI_GENERIC_GSI if ACPI
	select ARCH_HAS_DEBUG_WX
	select ARCH_BINFMT_ELF_STATE
	select ARCH_HAS_DEBUG_VIRTUAL
	...
  • config ARM64 — khai báo symbol CONFIG_ARM64.
  • def_bool y — mặc định luôn y khi arch này được chọn (không hỏi người dùng).
  • select X if Y — nếu Y đúng thì ép X=y (khác với depends on, select ép chiều xuôi, không hỏi lại).

Summary

Kconfig = WHAT to build. Nó trả lời "feature này có được đưa vào kernel không, và nếu có thì dưới dạng built-in hay module" — câu trả lời được lưu ở .config (Chapter 05).

CHAPTER 05

.config

Concept

.config là kết quả phẳng (flattened) của toàn bộ cây Kconfig: một file text gồm các dòng CONFIG_FOO=y/=m hoặc # CONFIG_FOO is not set. Từ file text này, Kbuild sinh ra hai dạng khác để compiler/Makefile dùng được.

File Anatomy

.config (trích đoạn minh hoạ)
#
# Automatically generated file; DO NOT EDIT.
# Linux/arm64 5.10.x Kernel Configuration
#
CONFIG_ARM64=y
CONFIG_64BIT=y
CONFIG_MMU=y
CONFIG_MVPP2=m
# CONFIG_MVPP2_PTP is not set
CONFIG_ARM64_VA_BITS_48=y
CONFIG_CROSS_COMPILE="aarch64-linux-gnu-"

Kconfig → C flow (CONFIG_FOO=y)

Kconfig (khai báo symbol)
↓ người dùng chọn y
CONFIG_FOO=y
↓ lưu vào
.config
↓ scripts/kconfig/confdata.c → sinh
include/generated/autoconf.h
↓ chứa dòng
#define CONFIG_FOO 1
↓ file .c include header này (gián tiếp qua <linux/kconfig.h>)
#ifdef CONFIG_FOO ... #endif
↓
compiler dịch nhánh code được bật
↓
binary chứa (hoặc không chứa) tính năng FOO

Flow riêng cho CONFIG_FOO=m

CONFIG_FOO=m
↓
include/config/auto.conf: CONFIG_FOO=m (dùng bởi Makefile, không phải .h)
↓
Makefile: obj-$(CONFIG_FOO) → obj-m += foo.o
↓
foo.o build riêng, KHÔNG vào built-in.a
↓ ld -r (modpost link)
foo.ko (module nạp runtime bằng insmod/modprobe)

Điểm khác biệt cốt lõi: với =y, macro CONFIG_FOO tồn tại ở compile-time (ảnh hưởng đến source qua #ifdef). Với =m, symbol chủ yếu được Makefile dùng để định tuyến file vào obj-m thay vì obj-y — code bên trong file đó thường không có #ifdef CONFIG_FOO bao quanh toàn bộ (vì cả bản build-in lẫn module dùng chung source), mà dùng module_init()/module_exit() làm entry point.

Ba file sinh ra từ .config

FileĐịnh dạngNgười tiêu thụ
.configText KEY=VALUECon người, make menuconfig
include/config/auto.confText, cú pháp Makefile hợp lệinclude trực tiếp bởi Makefile/scripts/Makefile.build (điều khiển obj-y vs obj-m)
include/generated/autoconf.hC header, #define CONFIG_FOO 1#include gián tiếp trong mọi file .c qua <linux/kconfig.h>, điều khiển #ifdef
Common Mistake

Sửa tay include/generated/autoconf.h hoặc include/config/auto.conf để "bật nhanh" một CONFIG — build có thể chạy được một lần, nhưng lần build tiếp theo Kbuild phát hiện .config không khớp header đã sinh (qua timestamp/checksum) và sẽ ghi đè lại theo .config. Luôn sửa qua .config/menuconfig, không sửa file generated.

Summary

.config là nguồn sự thật (source of truth) duy nhất; auto.conf và autoconf.h chỉ là hai "bản dịch" của nó sang ngôn ngữ Make và ngôn ngữ C.

CHAPTER 06

Kbuild

Concept

Kbuild là tập quy ước (không phải một binary riêng) nằm trong scripts/Makefile.build, scripts/Makefile.lib… cho phép mỗi thư mục chỉ cần khai báo biến (không cần viết rule biên dịch) để mô tả file nào build, build thành gì, với cờ gì.

Source Code — ví dụ driver thật trong repo

drivers/net/ethernet/marvell/mvpp2/Makefile
# SPDX-License-Identifier: GPL-2.0
#
# Makefile for the Marvell PPv2 driver.
#
obj-$(CONFIG_MVPP2) := mvpp2.o

mvpp2-y := mvpp2_main.o mvpp2_prs.o mvpp2_cls.o mvpp2_debugfs.o
mvpp2-$(CONFIG_MVPP2_PTP) += mvpp2_tai.o

Đọc rule này: nếu CONFIG_MVPP2=y hoặc =m, Kbuild tạo một "object hợp nhất" tên mvpp2.o (built-in) hoặc mvpp2.ko (module) từ 4 file .o liệt kê trong mvpp2-y; nếu CONFIG_MVPP2_PTP=y, cộng thêm mvpp2_tai.o vào — đây chính là composite object / multi-object module.

Đệ quy xuống thư mục con

Từ init/Makefile (file thật trong repo) — minh hoạ obj-y có điều kiện lồng nhau bằng ifneq:

endif
obj-$(CONFIG_GENERIC_CALIBRATE_DELAY) += calibrate.o

Debugging

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- V=1 drivers/net/ethernet/marvell/mvpp2/

V=1 in ra command line gcc/ld đầy đủ thay vì rút gọn kiểu CC drivers/…/mvpp2_main.o — công cụ debug quan trọng nhất của Kbuild (xem thêm Chapter 46).

Summary

Kbuild = HOW to build. Nó đọc obj-y/obj-m (được điều khiển bởi giá trị CONFIG từ Chapter 05) và với mỗi file quyết định: build vào built-in hay module hay bỏ qua hoàn toàn.

foo.s

CHAPTER 08

ELF Object (.o)

Concept

foo.o là một file ELF loại ET_REL (relocatable) — không phải executable. Nó chứa code/data đã dịch nhưng mọi tham chiếu tới hàm/biến ở file khác đều là "chỗ trống chờ điền" (relocation), vì địa chỉ cuối cùng chỉ được biết sau khi linker gộp toàn bộ kernel.

CHAPTER 09

built-in.a

Concept

Kbuild hiện đại (từ khoảng Linux 4.13, được tinh chỉnh thêm ở 5.2+) không link các .o trong một thư mục lại với nhau bằng ld -r. Thay vào đó, nó gom chúng vào một thin archive (ar với cờ T) tên built-in.a — archive này chỉ chứa con trỏ tới các file .o gốc, không copy nội dung, nên rất nhẹ và nhanh.

Source Code thật (repo này)

Nghĩa là built-in.a có tính đệ quy: drivers/net/built-in.a không chỉ chứa .o trực tiếp trong drivers/net/, mà còn "gồng gánh" luôn drivers/net/ethernet/built-in.a, rồi drivers/net/ethernet/marvell/built-in.a… xuống tận lá của cây thư mục.

Vì là thin archive, built-in.a chỉ vài trăm byte — nó chỉ lưu đường dẫn tương đối tới từng .o, không lưu nội dung. Do đó không thể copy built-in.a sang máy khác một mình — phải mang theo cả cây .o tương ứng.

Common Mistakes

⚠ "built-in.a chính là kernel, chỉ cần chạy nó là boot được"
built-in.a là archive trung gian ở cấp thư mục — chưa được resolve symbol chéo giữa các subsystem, chưa có linker script định vị bộ nhớ, chưa có entry point boot. Chỉ vmlinux (Chapter 13) — sản phẩm của việc link toàn bộ built-in.a — mới là kernel hoàn chỉnh.

Summary

built-in.a = "hộp gom .o theo thư mục", dùng cơ chế thin-archive để build nhanh và tránh phải resolve symbol quá sớm. Toàn bộ các archive này sẽ được link-vmlinux.sh link thẳng (không qua bước built-in.o trung gian) — xem Chapter 10 cho bối cảnh lịch sử.

CHAPTER 10

built-in.o (mô hình cũ, để hiểu lịch sử & các tài liệu cũ)

Concept

Trước khi có cơ chế built-in.a thin-archive (Chapter 09), Kbuild dùng incremental linking: mỗi thư mục gọi ld -r (relocatable link) để gộp tất cả .o trong thư mục — kể cả built-in.o của các thư mục con — thành một file .o tổng duy nhất tên built-in.o.

  • Rebuild cục bộ rẻ hơn: sửa 1 file trong drivers/net/ethernet/marvell/mvpp2/ không kéo theo việc re-link toàn bộ drivers/net/built-in.o khổng lồ.
Common Mistake

Tài liệu/blog cũ (viết trước ~2017) mô tả pipeline là foo.o → built-in.o (mỗi thư mục) → vmlinux. Với kernel hiện đại (bao gồm baseline 5.10.x và repo trong workspace này), bước built-in.o trung gian không còn tồn tại — thay vào đó là foo.o → built-in.a → vmlinux trực tiếp (Chapter 11). Hiểu cả hai giúp đọc đúng tài liệu theo từng thời kỳ kernel.

Summary

built-in.o là artifact của mô hình incremental linking cũ — hữu ích để hiểu lịch sử Kbuild, nhưng không xuất hiện trong build hiện đại; vai trò của nó nay do built-in.a (không thật sự link) đảm nhiệm.

CHAPTER 11

Concept

Bước link cuối cùng gom tất cả built-in.a ở cấp top-level (không phải từng file .o lẻ) thành một executable ELF duy nhất: vmlinux. Việc này do script scripts/link-vmlinux.sh điều phối, gọi $(LD) thật sự.

Why It Matters (embedded)

Với board thật, oops/panic log chỉ in ra địa chỉ hex (vì kernel chạy là Image, không có DWARF). Muốn biết chính xác dòng code gây lỗi, bạn cần giữ lại vmlinux đúng bản build (cùng commit, cùng .config) làm "bản đồ giải mã" — đây là lý do CI/CD kernel luôn lưu artifact vmlinux song song với Image đem lên board.

Sai bản vmlinux khi decode crash

Summary

DWARF là "phần mở rộng" đi kèm ELF, không ảnh hưởng đến việc kernel chạy — nhưng là công cụ debug hậu-boot quan trọng nhất, và nó biến mất hoàn toàn ở bước objcopy (Chapter 17).

Concept

Đây là ranh giới quan trọng nhất trong toàn bộ pipeline: vmlinux ≠ Image. Chúng khác định dạng, khác kích thước, khác mục đích, và chỉ file thứ hai mới thật sự được nạp lên board.

CHAPTER 18

ARM64 Image Header

Concept

Khác với raw binary thuần tuý, Image của ARM64 có một header cố định 64 byte ở đầu file (định nghĩa tại Documentation/arm64/booting.rst trong kernel) để bootloader biết cách nạp nó — dù bản thân Image không phải ELF.

Summary

ARM64 Image header là "hợp đồng tối thiểu" giữa kernel và bootloader — đủ để bootloader biết nạp bao nhiêu byte, ở đâu, và xác nhận đây đúng là kernel ARM64 chứ không phải rác.

CHAPTER 22

Module Linking

Concept

Module trải qua hai lần link, khác với built-in chỉ link một lần (vào vmlinux). Lần 1 gộp các .o thành phần; lần 2 (sau modpost) nhúng thêm metadata bắt buộc để kernel runtime chấp nhận nạp nó.

Build Flow chi tiết

mvpp2_main.o + mvpp2_prs.o + mvpp2_cls.o + mvpp2_debugfs.o
↓ ld -r (link lần 1, gộp thành 1 relocatable object)
mvpp2.o
↓ scripts/mod/modpost đọc TẤT CẢ module .o cùng lúc
mvpp2.mod.c (sinh ra: __this_module, MODULE_INFO, danh sách symbol cần)
↓ gcc -c
mvpp2.mod.o
↓ ld -r mvpp2.o mvpp2.mod.o (link lần 2)
mvpp2.ko

Vì sao không thể chỉ link 1 lần?

Vì mvpp2.mod.c (chứa struct module, thông tin license, danh sách symbol dependency) chỉ có thể sinh ra sau khi modpost đã đọc và phân tích toàn bộ object của module — nó cần biết trước những gì module này export và những gì nó cần từ bên ngoài. Do đó buộc phải: link thô → phân tích → sinh thêm code → link lại.

Summary

Link module là quy trình hai giai đoạn bất đối xứng: giai đoạn 1 gộp code người viết, giai đoạn 2 (sau modpost) gắn thêm "hộ chiếu" (metadata) để kernel runtime tin tưởng nạp module.

initrd vs initramfs

Concept

Hai cơ chế cũ/mới thường bị dùng lẫn tên dù cơ chế khác hẳn nhau.

initrd (cũ)initramfs (hiện đại)
Định dạngFilesystem image thật (ext2, romfs…)cpio archive (không phải filesystem image có block device)
Cách kernel dùngMount như một block device ảo (/dev/ram0) rồi mount filesystem đóGiải nén thẳng vào tmpfs (RAM-backed, không qua block layer)

Why It Matters

Khi đọc tài liệu/DTS cũ thấy node chosen { linux,initrd-start = ...; linux,initrd-end = ...; } — tên biến vẫn giữ "initrd" theo lịch sử, nhưng nội dung file trỏ tới trong 99% hệ thống hiện đại (bao gồm baseline 5.10.x) là cpio archive của initramfs, không phải filesystem image thật. Tên biến không phản ánh đúng cơ chế thực tế nữa — đây là nguồn nhầm lẫn phổ biến.

Summary

initrd = block device + filesystem thật (cách cũ, nặng). initramfs = cpio giải nén thẳng vào tmpfs (cách hiện đại, nhẹ, không phụ thuộc filesystem driver).

CHAPTER 28

Device Tree — DTS / DTSI / DTB / DTC

Concept

Trên ARM64 (không có BIOS/ACPI table đầy đủ như x86 ở hầu hết board embedded), kernel cần được cho biết phần cứng board có gì (bao nhiêu UART, địa chỉ MMIO của mỗi IP, IRQ số mấy…) — thông tin này nằm trong Device Tree, hoàn toàn tách biệt khỏi code kernel.

Pipeline DTS → DTB

board.dts (nguồn text, include .dtsi dùng chung SoC)
↓ cpp (preprocess #include, giống C)
board.dts.tmp
↓ dtc (Device Tree Compiler)
board.dtb (binary, Flattened Device Tree)
↓ bootloader nạp DTB vào RAM, truyền địa chỉ qua register x0 (ARM64 boot protocol)
kernel parse DTB lúc early boot → sinh device objects

Source Code thật (repo)

/ {
	model = "Globalscale Marvell ESPRESSOBin Board V7";
	compatible = "globalscale,espressobin-v7", "globalscale,espressobin",
		     "marvell,armada3720", "marvell,armada3710";

	aliases {
		ethernet1 = &switch0port3;
	};
};
  • /dts-v1/; — khai phiên bản DTS (bắt buộc, luôn là v1 hiện nay).
  • #include "armada-3720-espressobin.dtsi" — .dtsi (Device Tree Source Include) chứa phần chung của cả họ board, board .dts chỉ override/thêm phần riêng — mô hình kế thừa giống OOP.
  • compatible — chuỗi driver dùng để match (thay thế PCI vendor/device ID kiểu x86) — đây là cơ chế chính kernel dùng để tìm đúng driver cho từng node.

⚠ "DTB được CPU thực thi như code"
Sai hoàn toàn. DTB là dữ liệu thuần (giống một file cấu hình nhị phân), không chứa bất kỳ lệnh máy nào. CPU không bao giờ "chạy" DTB — kernel (code C thật, đã compile) đọc/parse cấu trúc DTB như đọc một file JSON/XML, rồi dùng dữ liệu đó để khởi tạo driver tương ứng. DTB hoàn toàn thụ động — nó mô tả phần cứng, không điều khiển gì cả.

Summary

Device Tree tách "mô tả phần cứng" ra khỏi "code driver" — cùng một kernel Image có thể chạy trên nhiều board khác nhau chỉ bằng cách đổi DTB, không cần build lại kernel.

Concept

Common Mistakes

"quên ARCH, chỉ set CROSS_COMPILE"

Nếu chỉ set CROSS_COMPILE mà quên ARCH, Makefile vẫn include arch/$(uname -m)/Makefile (thường là x86) trong khi compiler lại là aarch64-gcc — kết quả build lỗi ngay từ những dòng cấu hình đầu tiên (cờ CFLAGS không tương thích) hoặc tệ hơn, một số phần build "qua được" nhưng object sai kiến trúc.

Summary

Cross compilation trong Kbuild chỉ là việc thay một prefix chuỗi — toàn bộ độ phức tạp thật sự nằm ở việc toolchain đó phải support đúng ISA + ABI của target, và ARCH phải luôn đi kèm CROSS_COMPILE.

Concept

Common Mistakes

"WARNING: modpost: missing MODULE_LICENSE()"

Module thiếu MODULE_LICENSE() vẫn build được (chỉ warning), nhưng lúc insmod kernel sẽ "taint" (đánh dấu bẩn) — giới hạn một số API GPL-only và làm oops log ghi rõ "kernel tainted", gây khó khăn khi báo lỗi lên upstream.

Summary

modpost là "cổng kiểm tra chất lượng" cuối cùng trước khi object trở thành built-in/module chính thức — nó bắt lỗi liên kết ở build-time thay vì để runtime mới phát hiện.

CHAPTER 37

Module Versioning — Module.symvers & CONFIG_MODVERSIONS

Concept

Module.symvers không chỉ liệt kê tên symbol — với CONFIG_MODVERSIONS=y, mỗi symbol còn có một CRC 32-bit tính từ chữ ký hàm (kiểu tham số, kiểu trả về). Đây là cơ chế "version symbol" giúp phát hiện module build từ header khác kernel đang chạy, ngay cả khi vermagic tổng thể trùng khớp.

File Anatomy

Module.symvers (định dạng 4 cột, tab-separated)
0x3a1c9e0f	mvpp2_register_port	drivers/net/ethernet/marvell/mvpp2/mvpp2	EXPORT_SYMBOL_GPL
0x7bd2f1aa	register_netdev		vmlinux				EXPORT_SYMBOL
0x1f4e8c33	kmalloc_trace		vmlinux				EXPORT_SYMBOL_GPL
CộtÝ nghĩa

Vì sao cần CRC thay vì chỉ tên?

Hai bản kernel có thể cùng tên hàm mvpp2_register_port nhưng chữ ký khác nhau (thêm 1 tham số, đổi kiểu trả về) — nếu chỉ so tên, module cũ vẫn "nạp được" nhưng đọc sai stack/register khi gọi → crash khó hiểu. CRC (tính từ AST chữ ký hàm) đảm bảo phát hiện sai khác này trước khi nạp, thay vì crash runtime.

Build Flow (out-of-tree module dùng Module.symvers của kernel chính)

↓ copy Module.symvers vào thư mục build của module ngoài cây (out-of-tree)
make -C /path/to/kernel M=$(pwd) modules
↓ modpost đọc lại Module.symvers này để kiểm tra CRC khớp
module.ko — chỉ nạp được đúng vào kernel đã sinh ra Module.symvers đó

Summary

Module.symvers là "sổ cái phiên bản API nội bộ" của một bản build kernel cụ thể — nó biến việc "module không tương thích" từ một lỗi runtime khó chẩn đoán thành một lỗi build-time/load-time rõ ràng.

/*
 * Kernel startup entry point.
 * ---------------------------
 *
 * The requirements are:
 *   MMU = off, D-cache = off, I-cache = on or off,
 *   x0 = physical address to the FDT blob.
 *
 * This code is mostly position independent so you call this at
 * __pa(PAGE_OFFSET + TEXT_OFFSET).
 */

Ba yêu cầu này chính là "hợp đồng" mà U-Boot (BL33) phải tuân thủ tuyệt đối trước khi nhảy vào kernel: tắt MMU, tắt D-cache, và đặt địa chỉ vật lý của DTB vào thanh ghi x0 — đây là toàn bộ "tham số dòng lệnh" duy nhất mà bootloader truyền cho kernel ARM64 (không có argc/argv như userspace).

SYM_CODE_START(primary_entry)
	bl	preserve_boot_args
	bl	el2_setup			// Drop to EL1, w0=cpu_boot_mode

	bl	__create_page_tables

	b	__primary_switch

Summary

Từ lúc cấp điện tới start_kernel() là một chuỗi bàn giao quyền điều khiển qua ít nhất 5–6 chương trình độc lập (BootROM, BL1, BL2, BL31, U-Boot, head.S), mỗi chương trình chỉ tin tưởng chương trình ngay trước nó và chỉ có trách nhiệm chuẩn bị đúng môi trường tối thiểu cho chương trình kế tiếp.

CHAPTER 48

GCC vs Clang

Concept

Kernel hỗ trợ build bằng cả GCC và Clang (LLVM) — cùng một source tree, cùng cơ chế Kbuild, chỉ khác biến CC. Khác biệt nằm ở chất lượng chẩn đoán, tốc độ build, và một số tính năng chỉ 1 trong 2 hỗ trợ.

Commands

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- Image # GCC (mặc định)
make ARCH=arm64 CC=clang LLVM=1 Image

LLVM=1 không chỉ đổi CC — nó đổi luôn LD→ld.lld, AR→llvm-ar, NM→llvm-nm, OBJCOPY→llvm-objcopy… vì binutils GNU và LLVM binutils không phải lúc nào cũng tương thích 100% ở mọi cờ.

Tốc độ buildThường chậm hơn LLVM ở một số benchmarkThường nhanh hơn, đặc biệt với LTO/ThinLTO

Why It Matters

Build cùng một source bằng cả 2 compiler là kỹ thuật phát hiện bug tiềm ẩn cực tốt: code dựa vào undefined behavior (UB) thường được GCC và Clang tối ưu khác nhau, nên nếu build ra hành vi khác nhau giữa hai compiler → gần như chắc chắn có UB trong code cần sửa, không phải lỗi compiler.

Summary

GCC và Clang không "cạnh tranh thay thế" nhau trong kernel — chúng bổ trợ: GCC là baseline ổn định, Clang là công cụ phát hiện vấn đề + build nhanh cho CI/thử nghiệm.

CHAPTER 49

Reproducible Build

Concept

Reproducible build nghĩa là: build cùng source, cùng .config, cùng toolchain, ở hai máy/thời điểm khác nhau → ra byte-for-byte giống hệt nhau. Đây là yêu cầu quan trọng cho bảo mật chuỗi cung ứng (supply chain) — cho phép bên thứ ba xác minh binary phát hành đúng khớp source công bố.

Công cụ như ccache tăng tốc rebuild bằng cách cache kết quả compile theo hash (nội dung file + cờ compiler) — hoàn toàn tương thích với triết lý reproducible build (khác timestamp-based cache dễ sai). Dùng với Kbuild chỉ cần export CC="ccache aarch64-linux-gnu-gcc" hoặc set CROSS_COMPILE qua wrapper.

Summary

Reproducible build không tự nhiên có được — nó đòi hỏi loại bỏ tường minh mọi nguồn "ngẫu nhiên/môi trường" (thời gian, hostname, đường dẫn) khỏi quy trình build, điều Kbuild đã chuẩn bị sẵn cơ chế override.

CHAPTER 50

Embedded Vendor Kernel / BSP

Concept

Repo trong workspace này là ví dụ điển hình của một Board Support Package (BSP): kernel Linux gần-mainline được vendor thêm board support (defconfig, driver riêng, patch), đóng gói kèm firmware tầng thấp (ATF, BootROM) — nhưng không nhất thiết giữ nguyên vẹn mọi file "hành chính" (license, top Makefile) như checkout mainline chính thức.

Đặc điểm nhận diện BSP vendor (áp dụng cho repo này)

Firmware tầng thấp đi kèm trong cùng repoBootROM/, atf/atf_s800/ — bình thường đây là project riêng biệt (TF-A upstream), được vendor gộp vào cùng monorepo để đồng bộ version

Why It Matters

Hiểu rằng đây là BSP (không phải mainline thuần) giải thích được nhiều "bất thường" nếu so với tài liệu kernel.org: tên defconfig lạ, thư mục plat-km không chuẩn, boot chain qua ATF thay vì mô tả chung chung "U-Boot boot thẳng kernel". Khi debug BSP, luôn ưu tiên tra cứu theo đúng vendor tree thay vì giả định hành vi giống hệt mainline — nhiều hành vi (đặc biệt boot flow, layout partition) là quyết định riêng của vendor.

Summary

BSP = mainline kernel + vendor board support + đôi khi cả firmware tầng thấp, đóng gói theo nhu cầu vendor — không phải bản sao 1:1 của kernel.org, và một số quy ước (top-level file, tên board) có thể khác hẳn tài liệu chính thức.

CHAPTER 51

Module Installation

Concept

Build ra .ko chưa đủ để hệ thống dùng được — cần "install" đúng vị trí chuẩn (/lib/modules/<version>/) kèm các file index (modules.dep, modules.alias…) để modprobe tự động resolve dependency.

Build Flow

mvpp2.ko, mvpp2x.ko, … (đã build)
↓ make modules_install INSTALL_MOD_PATH=/path/to/rootfs
/lib/modules/<KERNELRELEASE>/kernel/drivers/net/ethernet/marvell/mvpp2/mvpp2.ko
↓ depmod -a (thường tự chạy cuối modules_install)
modules.dep, modules.alias, modules.symbols, modules.order (index cho modprobe)

Commands

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules_install INSTALL_MOD_PATH=/path/to/rootfs
depmod -b /path/to/rootfs $(KERNELRELEASE)

File Anatomy — modules.dep

kernel/drivers/net/ethernet/marvell/mvpp2x/mvpp2x.ko:
kernel/drivers/net/ethernet/marvell/mvpp2/mvpp2.ko: kernel/drivers/net/ethernet/marvell/mvpp2x/mvpp2x.ko

Dòng thứ 2 đọc là: "để nạp mvpp2.ko, phải nạp mvpp2x.ko trước" — modprobe đọc file này để tự resolve thứ tự, còn insmod (thấp cấp hơn) không đọc modules.dep, phải nạp tay đúng thứ tự.

Common Mistakes

insmod trực tiếp mà bỏ qua dependency

insmod mvpp2.ko khi mvpp2x.ko chưa nạp → lỗi "unknown symbol" (Chapter 23) dù chính module đó hoàn toàn đúng — vì insmod không tự tìm/nạp dependency như modprobe.

Summary

"Build xong" ≠ "cài đặt xong" — modules_install + depmod là bước bắt buộc để hệ thống thật (dùng modprobe/udev) tự động nạp đúng module đúng thứ tự.

CHAPTER 57

Common Misconceptions

Tổng hợp toàn bộ hiểu lầm đã cảnh báo rải rác ở các chapter trước, cộng thêm một số bổ sung — mỗi box nêu rõ nhận định sai và sự thật chính xác.

⚠ "vmlinux luôn là file boot trực tiếp"
Sai với hầu hết hệ thống thực tế. vmlinux là ELF đầy đủ dùng cho debug/sinh artifact khác; bootloader ARM64 nạp Image (raw binary có header riêng), không phải vmlinux. Xem Chapter 13, 16.
⚠ ".o là file executable"
.o có ELF type ET_REL (relocatable), còn symbol undefined, không có Program Header — không thể "chạy" theo bất kỳ nghĩa nào. Xem Chapter 08.
⚠ "built-in.a là kernel"
built-in.a chỉ là archive trung gian cấp thư mục, chưa resolve symbol chéo giữa subsystem, chưa có linker script/entry point. Phải qua bước link cuối (scripts/link-vmlinux.sh) mới thành vmlinux hoàn chỉnh. Xem Chapter 09, 11.
⚠ "DTB được CPU thực thi"
DTB là dữ liệu thuần (giống JSON/XML nhị phân), không chứa lệnh máy. CPU không bao giờ "chạy" DTB — kernel (code C đã compile) đọc/parse nó. Xem Chapter 28.
⚠ "Image luôn là file ELF"
Sau objcopy -O binary -S, Image không còn ELF header/magic (\x7fELF) — nó là raw binary với header ARM64 riêng (magic "ARM\x64" ở offset 0x38), hoàn toàn khác định dạng ELF. Xem Chapter 17, 18.
⚠ "U-Boot compile kernel"
U-Boot (BL33) không tham gia bước biên dịch kernel — nó chỉ là bootloader nạp Image/DTB/initramfs đã build sẵn vào RAM rồi nhảy vào entry point. Việc build kernel hoàn toàn thuộc về Kbuild/toolchain (gcc/ld/objcopy), độc lập với U-Boot. Xem Chapter 43, 44.
⚠ "CONFIG_FOO=m nghĩa là code bị bao trong #ifdef CONFIG_FOO giống như =y"
Với =y, macro tồn tại ở compile-time ảnh hưởng #ifdef. Với =m, symbol chủ yếu điều khiển Makefile (routing vào obj-m) — code bên trong dùng chung cho cả build-in lẫn module, phân biệt qua module_init()/module_exit(), không phải #ifdef CONFIG_FOO bao quanh toàn file. Xem Chapter 05.
⚠ "objcopy nén file"
objcopy chỉ loại bỏ metadata ELF (section header, symtab, debug info) — không chạy thuật toán nén nào. Nén thật sự (gzip/lz4/xz…) là bước riêng biệt sau đó. Xem Chapter 17, 19.
⚠ "System.map và /proc/kallsyms luôn giống hệt nhau"
Chỉ đúng nếu cùng một bản build đang chạy đúng khớp System.map đó. /proc/kallsyms còn có thể chứa thêm symbol của module đã nạp runtime — thứ System.map (sinh lúc build vmlinux, trước khi có module nào chạy) không hề biết tới. Xem Chapter 24, 25.
⚠ "initrd và initramfs là một, chỉ khác tên gọi theo thời gian"
Khác cơ chế hoàn toàn: initrd là block device + filesystem image thật (cần driver ramdisk + filesystem driver), initramfs là cpio giải nén thẳng vào tmpfs (không qua block layer). Tên biến DTB/bootloader vẫn giữ "initrd" theo lịch sử dù nội dung trỏ tới là cpio initramfs hiện đại. Xem Chapter 27.

Basic Nền tảng

.i = C sau preprocess (macro đã expand). .s = assembly con người đọc được. .o = ELF relocatable, máy đọc được nhưng chưa có địa chỉ cuối cùng.
Kconfig quyết định WHAT to build (feature nào bật/tắt), Kbuild quyết định HOW to build (thứ tự, cờ, rule biên dịch).
.config chính nó, include/config/auto.conf (Makefile đọc), include/generated/autoconf.h (C #ifdef đọc).
obj-y luôn built-in, obj-m luôn module, obj-$(CONFIG_X) resolve động thành y/m/rỗng tuỳ .config.
vmlinux = ELF đầy đủ (debug/symbol), dùng debug. Image = raw binary tối giản + header ARM64, dùng để boot thật.
Chuyển vmlinux (ELF) thành Image (raw binary), loại bỏ section/metadata không cần lúc chạy.
Bảng ánh xạ địa chỉ ↔ tên symbol, sinh bằng nm từ vmlinux sau khi link.

Mô tả phần cứng board (địa chỉ MMIO, IRQ, thiết bị…) dưới dạng dữ liệu, để cùng 1 kernel Image chạy được nhiều board khác nhau.

Nhanh hơn (không cần resolve symbol lúc archive), cho phép linker cuối garbage-collect object không dùng, rebuild cục bộ rẻ hơn.
Lần 1 để có địa chỉ cuối cùng, sau đó scripts/kallsyms sinh bảng symbol dựa trên địa chỉ đó, rồi phải link lại lần 2 để nhúng bảng symbol vào vmlinux.
2 lần: lần 1 lúc link vmlinux (kiểm tra symbol built-in, sinh Module.symvers phần built-in), lần 2 khi build module (sinh *.mod.c, kiểm tra symbol module cần).
Phát hiện module build từ header/chữ ký hàm khác kernel đang chạy — an toàn hơn so với chỉ so tên symbol.
Section phục vụ linker/debugger (chi tiết), Segment phục vụ loader/CPU lúc chạy (gộp nhóm, chỉ có ở executable, không có ở .o).
Kbuild theo dõi mọi header transitively-included trong file .cmd (deps_*) — bất kỳ .o nào include header đó (trực tiếp/gián tiếp) đều rebuild.
initrd = block device + filesystem image thật (cần driver). initramfs = cpio giải nén thẳng vào tmpfs (không qua block layer).
clean: xoá build artifact, giữ .config. mrproper: xoá thêm .config + generated headers. distclean: xoá thêm cả file backup editor.
Tách output khỏi source tree — giữ git sạch, cho phép nhiều build song song từ cùng 1 checkout, source có thể mount read-only.
Device Tree Compiler — input .dts (text), output .dtb (binary Flattened Device Tree); cũng decompile ngược .dtb → .dts.

Advanced Nâng cao

OBJS link với --whole-archive (bắt buộc đưa toàn bộ, code lõi như init/); LIBS link có điều kiện, chỉ kéo symbol thật sự được tham chiếu — giống thư viện tĩnh truyền thống.
MMU = off, D-cache = off, I-cache = on hoặc off, và x0 = physical address of the FDT blob (địa chỉ vật lý của DTB).
Kiến trúc ARM64 giao trách nhiệm giải nén cho bootloader (U-Boot/BL33) thay vì kernel tự mang decompressor — khác mô hình self-extracting của x86/ARM32 zImage.
mvpp2.mod.c (chứa metadata) chỉ có thể sinh sau khi modpost phân tích toàn bộ object của module — nên buộc phải: link thô → phân tích → sinh code → link lại. Built-in không cần bước "phân tích rồi sinh thêm code" tương tự vì không cần metadata module.
U-Boot = BL33, chạy ở EL2/EL1 non-secure, SAU khi BL31 (EL3 runtime) đã thiết lập PSCI và chuyển quyền xuống — không phải bootloader đầu tiên chạy trên chip.
Cho phép hạn chế một số API chỉ dùng được bởi module tuyên bố license GPL-compatible — cơ chế kỹ thuật hỗ trợ chính sách license của dự án kernel.

Kernel Hacking Chuyên sâu

Tìm tên hàm trong link map (-Map=vmlinux.map, Chapter 40) — nếu vắng mặt dù có trong .o gốc, nó đã bị loại vì không được tham chiếu (và bật gc-sections).
Timestamp (__DATE__/__TIME__), path build tuyệt đối trong debug info, hostname/username nhúng vào UTS_VERSION. Khắc phục bằng KBUILD_BUILD_TIMESTAMP/USER/HOST cố định và -fdebug-prefix-map.
Vì repo dùng Kbuild hiện đại (xác nhận qua scripts/link-vmlinux.sh dùng KBUILD_VMLINUX_OBJS/LIBS và scripts/Makefile.build dòng 405 tạo built-in.a) — mô hình built-in.o thuộc về Kbuild trước ~4.13, chỉ còn giá trị lịch sử/tài liệu.
Dùng đúng bản vmlinux (cùng commit + .config) đã lưu song song lúc build CI, chạy addr2line -e vmlinux -f -i <địa_chỉ> hoặc gdb vmlinux để map địa chỉ về file:dòng — vmlinux/Image phải khớp đúng build vì layout linker khác nhau giữa các build.
BootROM là mask ROM ghi cứng trên chip lúc sản xuất (không thể update qua phần mềm), trong khi BL1/BL2/BL31 (atf_s800) là firmware nạp được, có thể cập nhật qua flash — hai tầng tin cậy khác nhau về khả năng thay đổi.
CONFIG_SMP, CONFIG_PREEMPT/_RT, và phiên bản GCC dùng để build — vermagic nhúng cả 3 yếu tố này, không chỉ số version kernel.

Bài kiểm tra cuối cùng cho chính bạn

Sau khi đọc xong handbook này, với bất kỳ file nào gặp được sau một lần build kernel, bạn phải trả lời ngay lập tức không cần tra cứu:

  1. File này từ đâu ra — tool nào tạo, rule nào (Makefile/dòng nào) kích hoạt?

  4. Artifact tiếp theo lấy nó làm input như thế nào?
  5. Nếu là file boot — CPU/bootloader nào thật sự đọc/thực thi nó, và ở giai đoạn nào của chuỗi Power-On → start_kernel() (Chapter 44)?
