static void rcu_report_qs_rnp(unsigned long mask, struct rcu_node *rnp,
			      unsigned long gps, unsigned long flags)
{
	for (;;) {
		if ((!(rnp->qsmask & mask) && mask) || rnp->gp_seq != gps) {
			raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
			return;
		}
		WRITE_ONCE(rnp->qsmask, rnp->qsmask & ~mask);
		if (rnp->qsmask != 0 || rcu_preempt_blocked_readers_cgp(rnp)) {
			raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
			return;
		}
		mask = rnp->grpmask;
		if (rnp->parent == NULL) break;
		raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
		rnp = rnp->parent;
		raw_spin_lock_irqsave_rcu_node(rnp, flags);
	}
	rcu_report_qs_rsp(flags); /* releases rnp->lock. */
}

16. Common Misconceptions🔗

❌ "RCU là một loại lock"

✅ Đúng: rcu_read_lock()/unlock() không cầm bất kỳ lock nào ở fast path (Chapter 1) — không loại trừ writer, chỉ đánh dấu vùng code.
🔎 Nguồn: __rcu_read_lock() (tree_plugin.h:374) chỉ tăng 1 biến per-task.

❌ "Reader không bao giờ bị preempt"

✅ Đúng (PREEMPT_RCU): reader có thể bị preempt — theo dõi qua blkd_tasks (Chapter 5).
🔎 Nguồn: rcu_note_context_switch() xử lý case rcu_preempt_depth() > 0.

❌ "synchronize_rcu() chỉ đơn giản là sleep"

✅ Đúng: nó là call_rcu() + wait_for_completion() — dựa hoàn toàn vào guồng máy GP/callback (Chapter 7).
🔎 Nguồn: __wait_rcu_gp() (update.c:369).

❌ "call_rcu() free object ngay lập tức"

✅ Đúng: callback chỉ chạy sau khi GP hoàn tất, qua rcu_do_batch(), có thể trễ đáng kể (Chapter 6).
🔎 Nguồn: rcu_segcblist 4-segment (rcu_segcblist.h:29-56).

❌ "RCU thay thế mọi spinlock/rwlock"

✅ Đúng: RCU chỉ giải quyết vấn đề reader-writer/reclaim — writer-writer vẫn cần tự đồng bộ (Chapter 8).
🔎 Nguồn: comment list_add_rcu(): "caller must take whatever precautions... such as holding appropriate locks".

❌ "RCU tự động quản lý object lifetime"

✅ Đúng: RCU chỉ đảm bảo "chưa free trong khi còn reader cũ" — caller vẫn phải chủ động gọi call_rcu()/synchronize_rcu() đúng lúc (Chapter 6, 8).

❌ "RCU đảm bảo mọi memory access đều an toàn"

✅ Đúng: RCU chỉ đảm bảo ordering cho con trỏ publish/dereference đúng cách qua rcu_assign_pointer()/rcu_dereference() (Chapter 2) — truy cập trực tiếp không qua API này hoàn toàn không được bảo vệ.

18B. rcu_gp_kthread() — TREE_RCU Grace Period Coordinator🔗

SOURCE STUDY

rcu_gp_kthread() là thread trung tâm điều khiển vòng đời Grace Period của TREE_RCU. Hàm không trực tiếp thực hiện mọi công việc của RCU; thay vào đó, nó đóng vai trò state-machine coordinator, điều phối ba pha chính:

01Grace Period Startrcu_gp_init()
02Quiescent Statercu_gp_fqs_loop()
03Grace Period Endrcu_gp_cleanup()

rcu_gp_kthread()

        ├── rcu_bind_gp_kthread()

        └── outer for (;;)
              │
              ├── inner for (;;)

CODE

Đây là bước chuẩn bị trước khi GP kthread đi vào vòng lặp vô hạn. Ở high level, GP kthread được thiết lập CPU-affinity/binding phù hợp với housekeeping và trạng thái CPU hotplug của hệ thống.

Không nên kết luận nó bind cứng vào một CPU cụ thể chỉ từ call site này. Muốn biết chính xác CPU nào được chọn, phải đọc implementation của rcu_bind_gp_kthread() trong đúng kernel version đang phân tích.

    break;

Nếu trả về true: break chỉ thoát inner loop, không thoát outer loop. Sau đó thread đi vào rcu_gp_fqs_loop().

        ↓

        ↓

Nếu trả về false: thread không break mà thực hiện các bước retry:

Sau đó quay lại đầu inner loop và tiếp tục chờ/thử lại. Lý do chính xác khiến rcu_gp_init() trả false phải được xác định từ implementation của rcu_gp_init() trong kernel version đang dùng.

18B.11 — Memory barrier: comment đang nói gì?

/* Locking provides needed memory barrier. */

Ý của comment là ordering cần thiết được cung cấp bởi các thao tác locking bên trong đường rcu_gp_init(). Không nên hiểu rằng bản thân:

if (rcu_gp_init())

tự động tạo ra memory barrier riêng tại call site. Muốn xác định lock cụ thể, phải mở implementation của rcu_gp_init() và trace các thao tác lock/unlock tương ứng.

Sau khi rcu_gp_init() thành công, thread thoát inner loop và bước vào pha theo dõi Quiescent State. fqs là force quiescent state.

18B.21 — Những điểm cần nhớ khi đọc source

✓ DONE_GPS ≠ GP done: chỉ là done waiting for grace-period start.
✓ WAIT_GPS ≠ chờ QS: đây là request-wait phase.
✓ WAIT_FQS ↔ DOING_FQS: đây mới là vùng theo dõi/force Quiescent State.
✓ rcu_gp_kthread() không trực tiếp xử lý toàn bộ callback: không thấy rcu_do_batch() trong coordinator flow này.
✓ RCU_GP_IDLE là trạng thái khởi tạo của rcu_state.gp_state; trong flow đang xét, sau CLEANED thread quay lại WAIT_GPS, không trực tiếp set lại IDLE.
✓ Ba hàm trung tâm: rcu_gp_init() → rcu_gp_fqs_loop() → rcu_gp_cleanup().
Kết luận:
rcu_gp_kthread() là state-machine coordinator của TREE_RCU. Nó chờ request mở GP, gọi rcu_gp_init() để khởi tạo, gọi rcu_gp_fqs_loop() để theo dõi/force QS cho tới khi GP đủ điều kiện kết thúc, sau đó gọi rcu_gp_cleanup() và quay lại chờ GP tiếp theo.

M, N. rcu_node hierarchy & rcu_data

[CONCEPT + SOURCE] rcu_data là per-CPU (định nghĩa DEFINE_PER_CPU_SHARED_ALIGNED(struct rcu_data, rcu_data), chứa cblist (segcblist riêng CPU đó, tree.c:3018 dùng this_cpu_ptr), gp_seq local, dynticks counter. Q. MEMORY ORDERING

[SOURCE + CONCEPT] rcu_assign_pointer(p, v) = smp_store_release(&p, v) (định nghĩa chuẩn trong include/linux/rcupdate.h, cần kiểm tra lại số dòng chính xác trong tree này — tôi chưa đọc trực tiếp file đó ở lượt này). Ý nghĩa: mọi ghi vào *v (khởi tạo object mới) phải hoàn tất trước khi con trỏ p được công bố — nếu không, reader khác có thể thấy con trỏ mới nhưng đọc dữ liệu object chưa init xong.

rcu_dereference(p) = tương đương READ_ONCE(p) + address-dependency barrier (trên kiến trúc yếu như Alpha cần smp_read_barrier_depends; trên ARM64/x86 dependency ordering tự nhiên đã đủ nên là no-op) — đảm bảo mọi đọc sau vào *p (ví dụ use(obj)) thấy đúng nội dung mà rcu_assign_pointer đã publish.

CPU0 (Writer)                    CPU1 (Reader)
obj->value = 42;                 rcu_read_lock();
rcu_assign_pointer(global_obj,   p = rcu_dereference(global_obj);
                    obj);        // p->value LUÔN thấy = 42, không bao giờ
   [smp_store_release]           // thấy giá trị chưa init, nhờ release/dependency
                                  use(p);
                                  rcu_read_unlock();

[INFERENCE] RCU không đảm bảo CPU1 thấy giá trị mới ngay lập tức (không có "broadcast"), chỉ đảm bảo: nếu CPU1 thấy con trỏ mới, nó chắc chắn thấy toàn bộ nội dung object đã init xong (visibility có điều kiện, không phải ordering tức thời toàn cục).

U. RACE CONDITION: call_rcu() trên CPU0 // kfree() trên CPU1

Đây chính là Case A đã phân tích kỹ ở lượt trước. Tóm gọn lại trong bối cảnh flow đầy đủ này:

  • Bị bắt bởi: CONFIG_DEBUG_OBJECTS_FREE, tại debug_check_no_obj_freed() được gọi từ bên trong kfree() trên CPU1 (mm/slub.c:1534) — vì tại thời điểm đó object vẫn ACTIVE (chưa qua rcu_do_batch()/debug_rcu_head_unqueue()).
  • Không bị bắt bởi: RCU core tự nó — rdp->cblist trên CPU0 vẫn còn giữ con trỏ head trỏ vào vùng nhớ vừa bị free trên CPU1. Khi GP hoàn tất và rcu_do_batch() chạy trên CPU0, nó sẽ dereference rhp->func (đã bị corrupt vì memory bị free/reuse) → UAF thật sự, crash hoặc gọi hàm rác — đây là hậu quả thật của race này nếu DEBUG_OBJECTS_FREE không được bật (production build thường không bật).
  • Không có lock nào trong RCU core ngăn được race này ở mức logic — nó là lỗi của người dùng API (free trước khi callback chạy), RCU tin tưởng tuyệt đối rằng con trỏ đã enqueue là hợp lệ tới khi callback tự giải phóng nó.
